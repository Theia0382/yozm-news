# ADR-0095: 사건 묶기 평가는 운영자 API 의 결과를 날짜 단위 전수 라벨과 견주는 운영자 도구로 한다

## 맥락

- 사건 묶기의 사건 기준 · 시간 창 · 임베딩 모델과 큰 사건 기준은 정답 라벨을 붙인 표본으로 정한다 — 묶음 정확도(B-cubed F1)와 큰 사건 판정 정밀도([ADR-0026](0026-event-clustering-with-local-embeddings-and-jev.md)).
- 배정 · 재판정 · 병합 · 큰 사건의 판정 규칙은 모두 `event` 의 `domain` 이 정본이고, 결과는 기사가 들어온 순서와 회차 흐름(같은 회차의 앞 기사가 연 사건, 병합 회차)에 따라 달라진다. 애매한 구간은 Jev 가 판정한다.
- 운영자 API 가 사건 목록 · 사건별 배정 기사, 지금 기준의 큰 사건, 제안 기준의 큰 사건 미리보기, 지금 사건 배정 기준을 낸다.
- 사건 배정 기준은 설정이라 인스턴스마다 다르고, 임베딩 모델을 바꾸면 다시 맞춰야 한다([ADR-0090](0090-article-embedding-defaults-to-an-in-app-local-model-with-an-openai-compatible-api-by-setting.md)). 운영자에게 기준을 정답과 견주는 수단은 없었다 — 큰 사건 기준의 미리보기와 화면을 읽는 요령뿐이다.
- 기준이 바뀌면 재판정은 저장된 점수 · 확률 안에서만 다시 판정하고, 닫힌 사건은 재판정하지 않는다([ADR-0081](0081-event-assignment-criteria-in-settings-and-rejudgement-within-stored-scores.md) · [ADR-0087](0087-closed-event-assignments-are-not-rejudged-and-closing-and-merging-are-not-undone.md)). 사건 · 배정을 비우고 다시 묶는 기능은 제품에 없다.
- 일부 기사에만 라벨을 붙이면, 라벨 기사가 라벨 밖 기사와 잘못 묶인 것은 B-cubed 정밀도에 드러나지 않는다. 큰 사건 판정은 조회 기간 안 기사를 모두 센다.

## 결정

- **평가는 운영자가 자기 인스턴스에서 쓰는 도구로 한다.** 저장소의 `tools/event-eval` 이다. 개발팀이 기본값을 정할 때도 측정 인스턴스의 운영자로서 같은 도구를 쓴다.
- **도구는 판정 규칙을 계산하지 않는다.** 시스템의 결과를 운영자 API 로 받아 라벨과 견준다 — 묶음은 사건별 배정 기사, 큰 사건은 지금 기준의 목록과 제안 기준의 미리보기다. 기준을 비교할 때는 기준을 바꾼 시스템의 결과마다 다시 잰다.
- **표본은 날짜 단위 전수다.** 시간대의 하루(또는 이어진 며칠)에 발행된 기사 전부에 라벨을 붙인다. 묶음 정확도는 라벨 기사(뺀 기사 제외)로 세고, 배정이 없는 기사는 그 기사 혼자인 묶음으로 센다.
- **큰 사건의 정답은 라벨러가 정답 사건 × 날짜로 표시한다.** 정밀도는 날짜마다 시스템이 낸 큰 사건을 그 사건의 그날 라벨 기사에서 가장 많은 정답 사건과 견준다. 동률은 틀림으로 세고 95% Wilson 구간을 함께 낸다.

## 결과

- 재는 것이 실제 시스템이다 — Jev 판정 · 병합 · 들어온 순서가 결과에 들어 있다. 도구는 운영자 API 의 응답 계약에 기대고, 도구가 읽는 필드를 저장소의 API 명세와 대조하는 시험이 CI 에서 돈다.
- 운영자가 정직하게 비교하는 사건 배정 기준은 재판정이 다시 판정하는 범위다 — 위 기준 내리기, 확률 기준, 아래 기준 올리기처럼 띠가 넓어지지 않는 변경이고, 표본 사건이 열려 있을 때다. 시간 창, 아래 기준 내리기, 위 기준을 올려 넓어지는 띠, 임베딩 모델끼리의 비교는 사건을 비우고 다시 묶어야 하는데 그 기능이 없다. 개발팀은 측정 인스턴스에서 직접 비우고 채우기로 다시 묶어 비교하고, 그 절차는 공개 문서에 두지 않는다.
- 이 도구로 재지 않는 것이 있다. 병합 전후의 묶음 정확도는 병합 전 소속이 운영자 API 에 없어 재지 못한다. 큰 사건의 다른 집계는 시스템에 없어 도구가 계산하면 판정 규칙의 사본이 된다. 닫는 기간 · 최대 기간은 닫기가 마지막으로 기사가 붙은 시각 · 사건을 연 시각(벽시계) 기준이라 다시 묶어도 표본에 작용하지 않는다. 이 셋은 앱이 그 값을 내도록 바꿀 때 함께 정한다.
- 전수라 라벨 양이 크다. 표본 구간 밖(앞뒤 날) 기사와의 잘못된 묶음은 여전히 보이지 않는다. 운영자의 라벨 시트는 운영자 API 로 만들어 시트를 만들 때 사건에 배정된 기사만 담으므로, 끝내 배정되지 않은 기사는 표본에서 빠진다.
- 운영자의 라벨에는 검수가 없다. 표본 밖 운영 분포의 품질은 증명하지 못한다([테스트 전략](../qa/test-strategy.md) ⑪).

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 도구가 저장한 기사 표현 · 판정 확률로 배정 · 병합을 다시 돌린다(오프라인 재생기) | 회차 흐름의 사본이다. 띠에 새로 든 후보의 판정 확률이 없어 결과가 실제 시스템과 어긋난다 |
| 사건을 골라 그 기사에만 라벨을 붙인다 | 라벨 밖 기사와의 잘못된 묶음이 보이지 않아 정밀도가 과대평가된다. 큰 사건 판정이 세는 기사와 라벨 범위가 맞지 않는다 |
| 여러 날 가운데 주제 몇 개만 전수로 붙인다 | 다른 주제 기사와의 잘못된 묶음이 보이지 않고, 큰 사건 판정은 주제 밖 소스까지 센다. 표본 경계가 평가 결과(태그)에 기댄다 |
| 정답 묶음에 지금 큰 사건 규칙을 적용해 정답 큰 사건을 유도한다 | 판정 규칙의 사본이고, 기준값이 맞는지는 말하지 못한다 |
| 라벨 시트에 시스템의 사건을 함께 싣는다 | 라벨러가 시스템 묶음을 따라가 정답이 시스템을 닮는다 |
