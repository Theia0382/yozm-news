# ADR-0170: 요청 제한은 `user` 의 PostgreSQL 테이블에 고정 창마다 한 문장으로 세고, 한도는 코드 상수 정책 표 하나다

- 상태: 승인
- 날짜: 2026-11-15
- 근거: [이슈 #152](https://github.com/Theia0382/yozm-news/issues/152) — 셈 · 정책 표 · 정리 `bc453f5`
- 관련: [ADR-0130](0130-sign-in-failure-delays-count-per-digest-of-the-submitted-normalized-email-regardless-of-account.md)(같은 꼴 — 실패 기록도 다이제스트 키의 DB 행이고 작업 역할이 지운다)

## 맥락

- 역할을 나눠 `web` 프로세스를 여럿 띄워도 한도가 성립해야 한다. 상태 저장소는 PostgreSQL 하나다.
- 대상(IP · 사용자 ID)은 개인정보다.
- 한도 값을 정할 운영 데이터가 아직 없다. 소수가 함께 쓰는 인스턴스다.

## 결정

- **기록은 `user` 의 PostgreSQL 테이블이다.** 키(동작 · 축 · 대상의 SHA-256)와 고정 창 시작마다 한 행이고, 요청 하나는 규칙마다 `INSERT … ON CONFLICT DO UPDATE … RETURNING` 한 문장으로 1을 더해 더한 수를 받는다 — 트랜잭션 · 명시 잠금 없이 여러 프로세스가 함께 더해도 빠지지 않는다.
- **창은 고정 창이다**(유닉스 기원부터 창 길이로 나눈 칸). 더한 수가 한도보다 크면 그 창 끝까지 거부한다. 요청은 결과와 무관하게 센다. IPv6 은 앞 64비트로 묶어 센다.
- **한도는 코드 상수 정책 표 하나(`RequestLimits`)다** — 동작마다 축(클라이언트 주소 · 세션 사용자) · 한도 · 창. 운영 설정으로 열지 않는다. 값은 측정 전 목표값이다.
- **끝난 창은 작업 역할의 반복 작업이 10분마다 지운다.**

## 결과

- 새 의존성 없이 실패 기록과 같은 꼴로 선다. 요청마다 규칙 수만큼 DB 문장이 하나씩 는다.
- 창 경계 앞뒤로 한도의 두 배까지 몰릴 수 있다 — 한도가 작고 실패 지연 · 봇 차단이 위에 있어 받아들인다.
- 공유 IP 가 큰 환경(학교 · 회사 NAT)의 운영자가 값을 바꾸려면 이미지를 다시 빌드해야 한다 — 운영 데이터가 반대를 보이면 상수 하나를 바꾸거나 그때 설정으로 연다.
- IPv4 주소의 다이제스트는 되돌리기 쉬워 IP 주소를 보관하는 것으로 고지한다. 보관은 창이 끝난 뒤 정리까지다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 프로세스 메모리(Caffeine 등) | `web` 을 여럿 띄우면 한도가 프로세스 수만큼 는다 |
| Bucket4j 의 PostgreSQL 저장 | 새 의존성 · 라이브러리의 테이블 꼴을 Flyway 로 옮겨 적어야 하고, 필요한 산식(창 안 횟수)이 작다 |
| 미끄러지는 창(앞 창을 무게 매겨 더함) | 행 둘을 읽고 다시 시도할 때의 산식이 복잡해진다 — 몰림이 줄어드는 이득이 작다 |
| 요청마다 기록(로그)을 남겨 센다 | 요청마다 행이 생긴다 |
| 한도를 운영 설정(환경 변수)으로 연다 | 근거 데이터 없이 설정 십여 개와 그 검증 · 문서가 는다 |
