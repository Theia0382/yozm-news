# ADR-0171: 로그인 · 복구의 사용자 축은 이메일별 실패 지연이고, 요청 제한은 IP 로만 센다

- 상태: 승인
- 날짜: 2026-11-15
- 근거: [이슈 #152](https://github.com/Theia0382/yozm-news/issues/152) — 정책 표 `bc453f5`
- 관련: [ADR-0130](0130-sign-in-failure-delays-count-per-digest-of-the-submitted-normalized-email-regardless-of-account.md)(보충 — 결과 절의 "IP 별 요청 제한이 함께 줄인다"를 이 ADR 이 구현한다), [ADR-0144](0144-recovery-code-failures-are-delayed-on-the-sign-in-schedule-in-a-separate-record-and-current-password-checks-share-the-sign-in-record.md)(복구 코드 실패의 기록)

## 맥락

- 악용 방지 표는 로그인 · 복구 코드 사용에 "사용자 · IP별 요청 제한"을 정했다. 두 경로는 세션이 없는 공개 처리기라 "사용자"는 제출된 이메일이다.
- 이메일 축에는 이미 실패 지연이 있다 — 제출된 이메일마다 연속 실패를 세고, 계정 유무와 무관하다.
- 실패 지연은 남의 이메일로 일부러 틀려 그 사람의 로그인을 늦추는 길을 남긴다(ADR-0130 결과).

## 결정

- **로그인 · 복구의 사용자 축은 실패 지연이다.** 새 요청 제한은 클라이언트 주소로만 센다(로그인 10분 30회 · 복구 1시간 10회 — 값의 정본은 user Spec).
- 이메일별 요청 수 제한을 따로 두지 않는다.

## 결과

- 같은 이메일 키의 장치가 둘이 되지 않는다. 이메일로 세는 요청 제한이 만들 새 잠금 길(남이 그 이메일의 한도를 써 버리는 것)도 없다.
- 남의 로그인 늦추기는 IP 제한 · 봇 차단으로 비용이 오를 뿐 막히지 않는다 — 여러 주소를 쓰는 공격자는 15분마다 실패 한 번으로 대기를 상한에 붙여 둘 수 있다. 그동안 피해자의 비밀번호 변경도 같은 대기에 걸리고, 복구 코드 실패는 따로 세므로 복구 코드로는 비밀번호를 다시 정할 수 있다. 봇 차단을 켜면 실패 한 번마다 사람 확인이 필요하다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 이메일별 요청 수 제한을 따로 둔다 | 같은 키의 장치가 둘이 되고, 성공한 로그인까지 세는 제한은 대입 방어에 보태는 것이 없으며, 남이 한도를 써 버리는 새 잠금이 생긴다 |
| 실패 기록의 키를 이메일 × IP 로 바꾸고 이메일 전체에 더 높은 상한을 둔다 | 남의 로그인 늦추기를 거의 막지만 ADR-0130 을 다시 열고, 여러 IP 로 나눈 대입이 IP 마다 지연 없는 실패를 받으며, 기록 · 일정이 둘로 는다 |
