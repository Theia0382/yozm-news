# ADR-0229: 관심사 히스토리의 기간은 관심 설정 시간대의 월요일 시작 주 · 1일 시작 월이고, 공개 조회는 정해 둔 기간 또는 부르는 쪽의 기준 시각 목록을 받는다

- 상태: 승인
- 날짜: 2026-11-18
- 근거: [이슈 #189](https://github.com/Theia0382/yozm-news/issues/189) — 화면 · 변화 리포트가 기간 경계를 정하는 자리와 화면의 기간 고르기를 정함. 구현 커밋 `77bfe43` · `86e0cc0` · `bb602eb` · `95bb4cd` · `27a151a`
- 관련: [ADR-0180](0180-user-settings-changes-publish-no-event-and-consumers-query.md)(소비자의 작업이 조회를 연다 — 시간대 조회를 엶), [ADR-0192](0192-reader-screens-are-composed-by-the-reader-module-over-module-public-queries.md)(`reader` 는 판정하지 않는다), [ADR-0225](0225-interest-history-values-read-only-the-window-before-each-reference-time-and-the-period-in-progress-is-measured-at-the-call.md)(기간 값의 계산)

## 맥락

- 관심사 히스토리는 주 · 월 단위로 보인다. 변화 리포트도 관심도의 변화와 새로 생긴 관심 · 사라진 관심을 입력으로 쓰는데, 리포트의 주간 경계는 사용자가 고른 요일이다.
- 기간 경계(시간대 · 주의 시작 · 진행 중 기간)는 판단이라 판정이 없는 `reader` 에 둘 수 없다.
- 관심 설정에 시간대가 있고(일정의 기준), 화면의 시각 표기는 브라우저 시간대다.
- 기간 수가 많을수록 요청 하나의 읽기가 커진다.

## 결정

- **기간은 관심 설정의 시간대에서 주는 월요일 00:00, 월은 1일 00:00 에 시작한다.** `user` 가 시간대 조회(`UserTimezones`)를 연다 — 설정 행이 없으면 계정을 만들 때의 기본값이다.
- **공개 조회는 둘이고 한 핵심을 쓴다** — 화면용 `recent(user, span)` 은 기간 경계를 `digest` 의 `domain` 이 정하고, 리포트용 `at(user, references)` 는 부르는 쪽이 기준 시각 목록을 넘긴다(맨 앞은 견줌용).
- **화면은 정해 둔 기간 가운데 하나를 고른다** — 주 · 월 전환과 단위별 드롭다운(주 13 · 26 · 52, 월 12 · 24 · 36). 단위를 바꾸면 그 단위의 기본값(주 13 · 월 12)으로 가고, 처음 화면은 13주다. 쪽 넘김은 없다 — 요청 하나의 읽기 상한이 가장 긴 선택지로 정해진다. 선택지의 정본은 서버의 기간 목록이다.

## 결과

- 화면의 "이번 주"와 리포트 · 다이제스트 일정이 같은 시간대로 끊긴다. 기기마다 기간이 달라지지 않는다.
- 리포트는 자기 경계(사용자가 고른 요일)로 `at` 을 부른다 — 리포트 작업이 경계 계산을 따로 가진다.
- 52주 · 36개월보다 오래된 기간은 화면에서 볼 수 없다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 브라우저 시간대를 요청 매개변수로 받는다 | 같은 사용자라도 기기마다 기간 값이 다르고 리포트와 경계가 어긋난다 |
| 공개 조회를 `recent` 하나만 열고 리포트용은 리포트 작업이 더한다 | 리포트가 같은 조회를 쓰는지가 이 작업에서 확인되지 않는다 |
| `at` 하나만 열고 경계 계산 함수를 공개해 `reader` 가 엮는다 | 시간대 읽기 · 경계 계산 · 조회의 순서가 화면 쪽에 놓이고, 계산 함수가 공개 API 가 된다 |
| 드롭다운 하나에 여섯 선택지 · 기본 13주 | 단위마다 기본값을 두기로 한 것과 맞지 않는다 |
| 쪽 넘김으로 그 앞 기간을 본다 | 드롭다운으로 기간 수를 고르는 쪽을 택했다 |
