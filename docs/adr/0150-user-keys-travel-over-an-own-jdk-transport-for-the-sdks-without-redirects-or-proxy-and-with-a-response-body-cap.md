# ADR-0150: 사용자 키가 가는 전송은 SDK 의 HTTP 클라이언트를 JDK `HttpClient` 로 직접 구현한다 — 리다이렉트 · 프록시 없음, 응답 본문 상한

- 상태: 승인
- 날짜: 2026-11-14
- 근거: [이슈 #148](https://github.com/Theia0382/yozm-news/issues/148) — Spring AI 의 HTTP 클라이언트 빌더와 두 SDK 의 HTTP 클라이언트 인터페이스를 jar 에서 확인
- 관련: [ADR-0149](0149-llm-calls-use-spring-ai-2-without-the-starter-and-build-sdk-clients-with-explicit-address-key-and-log-level-and-close-them.md)(SDK 클라이언트를 직접 조립한다)

## 맥락

- Spring AI 가 주는 전송은 OkHttp 이고 리다이렉트를 따른다. 전송을 만드는 빌더에는 리다이렉트를 끄는 손잡이가 없다 — OpenAI 쪽은 끌 길이 없고, Anthropic 쪽은 SDK 의 요청별 선택지로만 끌 수 있어 Spring AI 의 채팅 모델이 보내는 요청에는 닿지 않는다. 두 쪽 모두 응답 본문의 상한이 없다. OkHttp 는 다른 호스트로 리다이렉트될 때 `Authorization` 헤더만 떼는 것으로 알려져 있다 — Anthropic 의 키는 `x-api-key` 헤더에 실린다.
- 운영자 키가 가는 외부 호출(`evaluation` 의 Jev · 외부 임베딩)은 JDK `HttpClient` 로 리다이렉트 없음 · 프록시 없음 · 응답 본문 상한 · 마감을 건다.
- 두 SDK 의 HTTP 클라이언트는 메서드 셋(동기 실행 · 비동기 실행 · 닫기)의 공개 인터페이스이고, SDK 의 클라이언트 옵션이 어떤 구현이든 받는다.
- 사용자 키는 이 서비스가 맡은 값 가운데 가장 민감하다.

## 결정

- **공급자로 가는 전송은 `llm` 이 JDK `HttpClient` 로 직접 구현한다.** 전송의 정본은 하나이고, SDK 마다 그 SDK 의 HTTP 클라이언트 인터페이스를 이 전송으로 구현한 얇은 구현을 둔다.
- 전송은 **리다이렉트를 따르지 않고, 프록시를 쓰지 않고, 응답 본문을 상한까지만 받고, 마감을 헤더와 본문 전부에 건다.** 리다이렉트 응답과 상한을 넘은 본문은 실패다.

규칙은 [llm Spec](../specs/llm.md#공급자-클라이언트) llm-R13 에 있다.

## 결과

- 사용자 키가 가는 길의 방어가 운영자 키가 가는 길과 같다. 공급자가 다른 호스트로 돌려도 키가 따라가지 않는다.
- OkHttp 가 실행 경로에서 빠진다(Spring AI 의 jar 가 의존하므로 classpath 에는 남는다).
- 프록시를 거쳐야만 밖으로 나갈 수 있는 호스트에서는 LLM 호출이 되지 않는다 — Jev · 임베딩 호출과 같은 제약이다.
- SDK 의 HTTP 클라이언트 계약이 판 올림으로 바뀌면 구현이 따라간다. Spring AI 의 전송이 주던 관측(요청 측정)은 없다.
- 응답을 조각으로 받는 호출(스트리밍)은 이 전송으로 하지 않는다 — 본문을 끝까지 받은 뒤 넘긴다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| Spring AI 가 주는 OkHttp 전송을 그대로 쓰고 리다이렉트 추종 · 본문 상한 없음을 감수한다 | 주소가 공급자 호스트로 고정이라 실제 위험은 공급자 쪽 사고에 한정되지만, 사용자 키의 길이 운영자 키의 길보다 느슨해진다. 이미 있는 방어를 쓰지 않을 이유가 구현 비용뿐이다 |
