# ADR-0039: 코드 주석은 Spec · ADR · 문서가 덮지 않는 것만 담고 그 위치를 가리키며, Javadoc 형식은 javac 과 javadoc 이 빌드에서 검사한다

- 상태: 승인
- 날짜: 2026-10-30
- 근거: [이슈 #45](https://github.com/Theia0382/yozm-news/issues/45) — 기점 `ffaf6d4` 에서 백엔드 main 142파일 · 테스트 86파일의 주석을 전수 집계하고 세 Spec · 개발 인프라 문서와 대조, javac 25 doclint 와 `javadoc` 의 판정을 시험 파일과 저장소에서 실측. 빌드 검사 `114e6dd`
- 관련: [ADR-0034](0034-module-spec-as-public-interface-specification-and-docs-by-kind.md)(문서 체계 — 클래스 내부 상세는 Javadoc), [ADR-0036](0036-module-spec-holds-internal-structure-and-port-declarations-in-eight-sections.md)(Spec 의 내부 구조 · 절 번호 고정 — 이 ADR 이 그 결과에 남은 겹침을 정리한다), [ADR-0016](0016-containerized-checks.md)(검사 정의), [ADR-0013](0013-architecture-patterns.md)(모듈 경계)

## 맥락

- 주석 규칙은 CONTRIBUTING 의 한 줄("모듈의 공개 API 는 Javadoc 을 쓴다. 현재 동작만, 이슈 번호에 기대지 않고")뿐이었다. 실제로는 최상위 타입 142개 가운데 140개에 Javadoc 이 있었고, 첫 문장 형식(명사구 · 서술문)과 태그 쓰임(`@param` 171 · `@return` 17 · `@throws` 28)이 섞여 있었다.
- Spec(ADR-0034 · ADR-0036)이 생기기 전에는 Javadoc 이 유일한 설명 자리였다. 그래서 Javadoc 이 Spec 이 가진 지식을 거의 그대로 다시 적고 있었다 — 규칙 본문(같은 기사 판정 순서 · 제목 비교 키 · 정규 URL), 공개 타입의 필드 뜻, 포트 계약, 구성 요소의 책임, 설계 이유. 주석이 Spec 의 절 · 규칙 식별자 · ADR 번호를 가리키는 곳은 0곳이었다.
- 인프라 · 설정 파일의 주석도 같은 구도였다 — 같은 불변식이 파일 주석과 개발 인프라 문서의 불변식 표에 함께 있었다.
- javac 의 doclint 는 깨진 참조 · HTML · 잘못된 `@param` 이름을 오류로 잡지만, 알 수 없는 태그(`@retrun` 같은 오타)는 잡지 않는다. `javadoc` 도구는 잡는다. 기점의 형식 오류는 테스트 Javadoc 1건이었다. 문서화 누락 검사(missing)를 public 수준에서만 켜도 경고가 324건이었고, 대부분 `@param` · `@return` 을 기계적으로 채우라는 것이었다.

## 결정

- **주석은 다른 층이 덮지 않는 것만 담는다.** 동작 · 계약과, 코드가 그 모양이어야 하는 외부 제약 사실(한 문장)을 담는다. 설계 판단은 ADR 번호로, Spec 의 규칙 본문 · 책임 서술은 Spec 위치와 규칙 식별자로 가리킨다. 판별 기준은 "코드나 환경이 바뀌면 이 문장이 거짓이 되는가"다.
- **Spec 이 정본인 코드 요소의 Javadoc 은 한 줄 요약과 Spec 위치를 둔다.** 모듈 공개 타입 · 포트(그 멤버 포함)는 요약과 위치만 둔다. Spec 의 내부 구조 절에 이름이 오른 구성 요소는 요약 · 위치에 Spec 에 없는 클래스 안쪽 상세를 더한다. 요약 한 줄은 Spec 의 책임 한 줄과 겹쳐도 된다 — 문서 위계의 셋째 예외다.
- **Spec 위치는 절 번호까지 쓰고, 규칙 식별자를 함께 쓴다**(`docs/specs/article.md §4 · article-R3 ~ article-R6`). 고정된 좌표는 절 번호와 규칙 식별자 둘이다. 하위 절 제목은 쓰지 않는다.
- **Javadoc 을 반드시 쓰는 대상과 쓰지 않는 대상은 판단 기준으로 정하고, 리뷰가 본다.** 빌드는 누락을 검사하지 않는다.
- **테스트는 지키는 Spec 규칙을 테스트 클래스 Javadoc 의 식별자로 가리킨다.** 규칙 문장은 다시 쓰지 않고 시험 방법을 담는다. 메서드 단위는 한 클래스 안에서 규칙이 갈릴 때만 쓴다.
- **인프라 · 설정 파일의 주석에도 같은 원칙을 쓴다.** 그 자리의 제약 한 문장과 문서 위치를 두고, 불변식 · 지키는 장치 · 이유는 개발 인프라 · 운영 문서 · ADR 이 갖는다.
- **Javadoc 형식은 빌드가 두 곳에서 검사한다.** 모든 Java 컴파일에 javac `-Xdoclint:all,-missing` 을 건다. main · 테스트 소스의 `javadoc` 태스크(`-Xdoclint:all,-missing -Werror -private`)를 `check` 에 잇는다. `-Werror` 는 `javadoc` 에만 건다.

규칙의 문면은 [CONTRIBUTING.md §7](../../CONTRIBUTING.md#7-코드)이 정본이다.

## 결과

- 같은 지식의 사본이 "무엇인가" 한 문장(코드 요소의 요약 · 구성 파일의 제약 문장)으로 줄어든다. 규칙을 바꾸는 변경은 Spec 하나를 고치고, 주석은 위치만 가리키므로 따라 고칠 문장이 없다.
- Spec 내부 구조 절의 구성 요소 줄이 다는 규칙 식별자와 그 클래스 Javadoc 의 식별자는 같은 대응의 사본이다. 구성 요소의 책임을 옮기는 변경이 Spec 과 코드를 함께 고치지 않으면 어긋난다 — 리뷰가 본다.
- 구성 파일 주석은 문서를 경로와 제목으로 가리킨다. 개발 인프라 · 운영 문서의 제목은 Spec 의 절 번호처럼 고정된 좌표가 아니라, 제목을 바꾸면 주석이 조용히 낡는다 — 리뷰가 본다.
- 코드 주석이 가리키는 Spec 위치 · 규칙 식별자 · ADR 번호 · 문서 제목이 실제로 있는지는 기계가 확인하지 않는다.
- 깨진 참조 · HTML 은 컴파일에서 드러난다. 그래서 배포 이미지 빌드(`bootJar`)와 개발 실행(`bootRun`)도 그 오류로 멈춘다. 태그 오타와 doclint 경고는 `check` 에서만 드러난다.
- `check` 가 Javadoc HTML 을 만든다. 산출물은 쓰지 않고 `build/` 아래에만 남는다. 기점에서 두 태스크의 소요는 합쳐 약 3초다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 구성 요소 Javadoc 에 Spec 위치와 안쪽 상세만 두고 요약 문장도 두지 않는다 | 사본은 없지만 IDE 호버 · 리뷰 diff 에서 클래스가 무엇인지 알려 주지 않는다. 공개 타입만 요약을 갖는 비대칭이 생긴다 |
| 책임 · 규칙 서술을 Javadoc 에도 그대로 두고 리뷰가 맞춘다 | 규칙 본문의 사본이 남는다. 지금 값이 같아도 사본이고, 어긋남은 리뷰 하나에 기댄다 |
| Spec 위치를 하위 절(`§3 FetchedArticle` · `§4 domain/poll`)까지 쓴다 | 하위 절 제목은 고정 대상이 아니다. 패키지 이름 · 하위 절을 바꾸면 주석이 조용히 낡는다 |
| Java `public` 멤버 전부에 Javadoc 을 요구하고 doclint missing 을 켜 빌드가 강제한다 | 기점 324건을 채워야 하고, 대부분 자명한 `@param` · `@return` 이다. Java `public` 은 모듈 경계와 무관하다 — 패키지 사이에서 쓰려고 `public` 인 `domain` 타입이 많다 |
| 테스트 메서드마다 규칙 식별자를 단다 | 테스트 메서드 446개 가운데 해당분에 메서드 Javadoc 을 새로 써야 한다. 메서드 이름이 이미 행동을 말한다 |
| javac doclint 만 쓴다 | 태그 오타(`@retrun`)와 알 수 없는 태그가 통과한다. doclint 경고(빈 `<p>`)는 출력만 되고 남는다 |
| javac 에 `-Werror` 를 건다 | 태그 오타는 여전히 통과한다. javac 의 모든 경고(기본으로 켜진 `removal` 등)가 실패가 되어, 라이브러리를 올리다 주석과 무관한 이유로 빌드가 멈춘다 |
| `javadoc` 검사 태스크만 쓰고 javac 에는 옵션을 걸지 않는다 | 잡는 범위는 같고, 형식 오류가 배포 빌드를 멈추지 않는다. 대신 컴파일 · IDE 에서 형식 오류를 보지 못하고 `check` 에서만 본다 |
| 인프라 · 설정 주석은 내용 원칙만 따르고, 문서와의 경계는 따로 정한다 | 같은 불변식이 파일 주석과 문서 표에 함께 남는다. 경계를 맡을 다른 결정이 없었다 |
| 문서 검사(`docs`)가 코드 주석의 Spec 위치 · 규칙 식별자 · ADR 번호를 확인한다 | 문서 검사의 대상이 공개 마크다운 밖으로 넓어지고 검사기 코드가 는다. 이번에는 두지 않았다 |
