# ADR-0049: 피드 요청의 차단 대역을 IPv6 예약 공간과 로컬 NAT64 접두까지 넓힌다

- 상태: 승인
- 날짜: 2026-11-01
- 근거: [이슈 #46](https://github.com/Theia0382/yozm-news/issues/46) — IANA IPv4 · IPv6 Special-Purpose Address Registry(2025-10-09)와 IPv6 Address Space registry(2025-10-23)를 차단 표와 대조했고, Apache HttpClient 5.6.5 에서 IPv6 리터럴 URL 도 연결 관리자의 이름 해석기를 지나는 것을 확인했다. 구현 `4ae2e94`
- 관련: [ADR-0031](0031-feed-request-blocks-internal-addresses-with-apache-httpclient-deadline.md)(내부 주소 기본 차단 — 이 ADR 이 막는 종류를 넓힌다)

## 맥락

- ADR-0031 은 "루프백 · 사설 · 링크 로컬 · 공유 · 문서용 · 벤치마크 · 멀티캐스트 · 예약 대역과 IPv6 의 같은 종류"를 막기로 했다. 그러나 표에는 IPv6 벤치마크(`2001:2::/48`)와 RFC 9637 의 IPv6 문서용(`3fff::/20`)이 없었고, IPv4 는 예약 대역(`240.0.0.0/4`)을 막지만 IPv6 예약 공간은 막지 않았다.
- registry 가 전역 도달 불가로 적었지만 ADR-0031 이 종류 이름을 대지 않은 대역도 열려 있었다 — 6a44 relay(`192.88.99.2/32`), 더미 접두(`100:0:0:1::/64`), SRv6 SID(`5f00::/16`), 로컬 NAT64 접두(`64:ff9b:1::/48`).
- 로컬 NAT64 접두는 잘 알려진 접두(`64:ff9b::/96`)와 달리 사설 IPv4 를 담지 말라는 제한이 없다(RFC 8215 §5). 또 RFC 8215 §5 는 주소 안의 IPv4 위치를 가정하지 말라고 하고, 접두 길이는 운영자가 정한다 — 주소만 보고 품은 IPv4 를 꺼낼 수 없다.
- IPv6 예약 공간은 인터넷에서 라우팅되지 않지만, IETF Review 로 할당될 수 있다(RFC 9812). 지금까지 실제로 할당된 것은 `5f00::/16`(SRv6 SID — 전역 도달 불가) 하나다.

## 결정

- **IPv6 IETF 예약 공간을 막는다** — `::/8` 을 뺀 예약 블록 전부(`100::/8` 부터 `fe00::/9` 까지). 폐기 접두 · 더미 · SRv6 SID 는 이 블록 안이라 함께 막힌다. `::/8` 은 잘 알려진 NAT64 를 품으므로 통째로 막지 않고, 그 안의 미지정 · 루프백 · 로컬 NAT64 만 막는다.
- **로컬 NAT64 접두 `64:ff9b:1::/48` 은 통째로 막는다.** 이 접두를 DNS64 에 쓰는 망은 허용 목록으로 연다 — 연 대역에서는 사설 IPv4 로 가는 경로도 함께 열린다.
- **종류 이름이 없어도, registry 가 전역 도달 불가로 적은 개별 할당이고 피드가 있을 수 없는 대역이면 막는다** — 6a44 relay `192.88.99.2/32` 와 위의 IPv6 대역(더미 · SRv6 SID · 로컬 NAT64).
- **전역 도달 가능한 특수 목적 대역은 막지 않는다** — AS112 · AMT · PCP · TURN · DNS-SD anycast · ORCHIDv2 · DET. IETF 프로토콜 할당 `2001::/23` 은 통째로 막지 않고 하위 대역(Teredo · 벤치마크)만 막는다. 폐기되어 registry 가 속성을 비워 둔 `192.88.99.0/24` · `2001:10::/28` 도 막지 않는다.
- 대역 표의 정본은 그대로 `AddressPolicy.BLOCKED` 다.

## 결과

- 피드 URL 이나 리다이렉트가 위 대역으로 가면 `BLOCKED_ADDRESS` 로 실패한다.
- 로컬 NAT64 접두로 DNS64 를 돌리는 IPv6 전용 망의 인스턴스는, 허용 목록에 그 접두를 열기 전까지 IPv4 피드를 받지 못한다.
- IETF 가 예약 공간 일부를 전역 유니캐스트로 열면 그 대역의 피드가 `BLOCKED_ADDRESS` 가 된다. 표를 고치기 전에는 허용 목록으로 연다.
- `::/8` 안의 나머지 예약 공간(예: `0:0:1::`)은 열린 채다. 운영자가 자기 전역 접두 안에 둔 NAT64(망 고유 접두)는 주소로 알아볼 수 없어 막지 못한다.
- registry 에 새 특수 목적 대역이 생기면 차단 표에 넣을지를 이 ADR 의 기준(전역 도달 불가인 개별 할당이고 피드가 있을 수 없는지)으로 다시 판정한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| IPv6 예약 공간을 막지 않는다 | IPv4 는 예약 대역을 막는데 IPv6 만 열린다. 망 안에서 예약 공간을 무단으로 쓰면 요청이 닿고, 그 사실이 드러나지 않는다 |
| 로컬 NAT64 접두를 막지 않는다(RFC 8215 의 기본 동작 권고대로) | 이 접두로 번역하는 망에서는 피드 URL · 리다이렉트로 사설 IPv4 에 닿을 수 있다 |
| 로컬 NAT64 접두에서 품은 IPv4 를 꺼내 판정한다 | IPv4 의 위치를 주소로 알 수 없고, RFC 8215 가 그 가정을 하지 말라고 한다 |
| `2001::/23` 을 통째로 막는다 | 하위 할당 다수(AMT · ORCHIDv2 · DET · anycast)가 전역 도달 가능한 서비스 주소다 |
| 막는 기준을 ADR-0031 이 이름을 댄 종류로 한정한다 | 6a44 relay · 더미 · SRv6 SID 처럼 피드가 있을 수 없는 전역 도달 불가 대역이 이름이 없다는 이유만으로 열린다 |
