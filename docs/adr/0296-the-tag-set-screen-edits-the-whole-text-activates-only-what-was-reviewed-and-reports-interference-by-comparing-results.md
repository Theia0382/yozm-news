# ADR-0296: 태그 체계 화면은 원문 전체를 고치는 한 페이지이고, 확인한 원문 · 재평가 기간 그대로만 확인 대화상자를 거쳐 활성화하며, 끼어든 활성화는 활성화 결과를 확인 결과와 견줘 알린다

- 상태: 승인
- 날짜: 2026-11-23
- 근거: [이슈 #81](https://github.com/Theia0382/yozm-news/issues/81) — 태그 체계는 운영자 API(버전 목록 · 버전 원문 · 확인 · 활성화)로만 바꿀 수 있었다. 확인 응답에는 대조한 기준 버전이 없고, 활성화 응답은 새 버전의 ID · 번호를 싣는 것을 확인
- 관련: [ADR-0062](0062-tag-set-versions-from-operator-text-activated-forward-with-key-lineage-and-recent-reevaluation.md)(보충 — 결정이 들이지 않은 편집 화면), [ADR-0055](0055-tag-and-store-thresholds-change-with-history-and-warn-instead-of-blocking.md)(태그 기준 · 저장 기준은 원문이 아니라 태그 기준 화면에서 바꾼다), [ADR-0175](0175-tag-preferences-follow-tag-set-activation-events-and-are-rewritten-to-active-keys.md)(계보 없이 지운 키의 선호 해제), [ADR-0183](0183-admin-paths-open-with-admin-account-sessions-and-keep-the-operator-token-as-an-optional-script-bearer-with-csrf-only-for-sessions.md)(화면은 계정 세션, 스크립트는 운영자 토큰으로 같은 API 를 부른다)

## 맥락

- 체계 변경은 원문 전체를 확인해 변경 목록 · 재평가 대상 기사 수를 본 뒤 활성화하는 두 단계다. 초안을 저장하지 않고, 확인은 아무것도 쓰지 않는다. 활성화는 그 순간의 활성 버전과 다시 대조하므로, 확인 뒤 다른 활성화가 끼면 결과(판별자 · 변경 목록)가 확인과 달라질 수 있다(ADR-0062).
- 활성화는 되돌릴 수 없다. 버전은 앞으로만 켜고, 계보 없이 지운 키의 사용자 선호는 해제되고 알림이 간다(ADR-0175). 재평가 기간을 정하면 그 기간의 기사마다 평가 비용이 들고 그동안 새 기사의 평가가 늦어진다.
- 확인 응답은 대조한 기준 버전을 싣지 않는다. 활성화 응답은 새 버전의 ID · 번호를 싣는다.
- 기본 체계 원문은 약 250줄 · 11,000자다. 원문 문제는 경로 · 줄:열 · 문구로 온다.
- 태그 기준 화면은 미리 본 값 그대로일 때만 저장하고, 미리보기 뒤 끼어든 변경을 저장 결과로 알린다.

## 결정

- **화면은 `/admin/tag-sets` 한 페이지다.** 버전 목록(번호 · 활성 · 만든 이 · 만든 시각), 고른 버전의 원문(읽기 전용), 새 버전 편집(원문 · 재평가 기간 · 확인 · 활성화)을 차례로 둔다. 운영자 메뉴에는 "태그 기준" 앞에 "태그 체계"로 둔다.
- **편집기는 원문 전체를 글자로 고친다.** 처음에는 활성 버전의 원문을 넣는다. 어느 버전의 원문이든 편집기로 불러올 수 있다 — 되돌리기는 예전 버전의 원문을 불러와 새 버전으로 낸다. 고친 원문을 다른 원문으로 바꿀 때는 묻는다. 고친 원문은 화면 밖에 저장하지 않는다.
- **활성화는 마지막 확인이 활성화할 수 있다(`READY`)고 답한 원문 · 재평가 기간 그대로일 때만 누를 수 있고, 확인 대화상자를 거친다.** 대화상자는 계보 없이 지운 키 수와 재평가 기간 · 대상 기사 수를 다시 보인다. 확인 뒤 원문 · 기간을 고치면 확인 결과는 남기되 낡았다고 표시하고 활성화를 막는다. 활성화한 원문은 다시 확인할 때까지 거듭 활성화하지 않는다.
- **끼어든 활성화는 활성화 결과를 확인 결과와 견줘 알린다.** 활성화의 판별자가 확인의 판별자와 짝이 맞지 않거나(`READY` ↔ `ACTIVATED` · `UNCHANGED` ↔ `UNCHANGED` · `INVALID_TAG_SET` ↔ `INVALID_TAG_SET`) 변경 목록 · 문제 목록이 다르면, 확인 뒤 다른 활성화가 끼어 결과가 달라졌다고 알리고 활성화 결과를 정본으로 보인다. 확인 응답에 기준 버전을 더하지 않는다.
- **원문 문제의 줄:열을 누르면 편집기의 그 자리로 간다.** 열은 코드 포인트로 센다 — 서버의 YAML 읽기와 같다.
- **활성화한 뒤 다음 원문은 새 버전의 원문에서 시작하게 한다.** 활성화 결과에 새 버전의 원문을 편집기로 불러오는 단추를 두고, 계보 절은 그 버전에만 속한다고 알린다.

## 결과

- 운영자가 curl 없이 태그 체계를 바꾼다. 스크립트는 운영자 토큰으로 같은 API 를 계속 쓴다.
- 끼어든 활성화가 결과를 바꾸지 않았으면(같은 판별자 · 같은 변경 목록) 알리지 않는다 — 운영자가 판단한 근거가 그대로라서다. 기준 버전 번호로 견주지 않으므로 끼어든 활성화 자체를 빠짐없이 알리지는 않는다.
- 화면을 떠나면 고친 원문을 잃는다 — 초안 저장이 없다(ADR-0062).
- 문제의 줄:열은 확인한 원문의 자리라, 확인 뒤 편집기를 고쳤으면 어긋날 수 있다 — 그때 화면은 확인 결과가 낡았다고 표시한다.
- 백엔드 · 운영자 API 명세는 바뀌지 않는다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 태그를 하나씩 더하고 지우는 구조 편집 폼 | 원문 검증기와 같은 규칙을 화면이 두 번째로 갖는다 — ADR-0062 가 같은 이유로 구조 편집 연산을 버렸다 |
| 확인 응답에 기준 버전(ID · 번호)을 더해 새 버전 번호가 기준 + 1 인지로 끼어듦을 판정한다 | `tag` 의 공개 결과 타입과 운영자 API 명세가 바뀌고, 결과가 그대로인 끼어듦까지 알린다 — 운영자가 판단할 근거는 결과다 |
| 화면이 연 때의 버전 목록의 활성 번호와 새 버전 번호를 견준다 | 목록은 확인보다 먼저 읽어 낡을 수 있다 — 확인이 이미 새 활성 버전과 대조했어도 끼어들었다고 알린다 |
| 확인 없이 바로 활성화하는 단추 | 활성화는 되돌릴 수 없고 선호 해제 · 재평가 비용이 따른다 — 변경 목록과 재평가 대상 수를 먼저 봐야 한다 |
| 확인 뒤 원문을 고치면 확인 결과를 지운다 | 문제 목록을 보며 고치는 동안 목록이 사라진다 — 낡았다고 표시하고 활성화만 막는다 |
| 버전 원문 · 편집을 따로 페이지로 둔다(`/admin/tag-sets/{ID}` · `/new`) | 되돌리기는 원문 보기에서 편집으로 바로 잇는 일이고, 버전은 많지 않아 목록 · 원문 · 편집이 한 화면에 든다 |
| 브라우저 저장소에 고친 원문을 남긴다 | 남긴 원문이 낡은 기준 버전의 것이 되는 판정과 지우기가 생긴다 — ADR-0062 가 초안 저장을 버린 이유와 같다 |
