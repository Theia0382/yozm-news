# ADR-0050: 이벤트를 읽을 수 없는 발행은 재제출 전에 거르고, 상한에 이른 · 읽을 수 없는 발행은 운영자가 즉시 1회 재제출하거나 기록 없이 폐기하며, 목록 · 폐기는 `platform` 이 레지스트리 테이블을 직접 다룬다

- 상태: 승인
- 날짜: 2026-11-01
- 근거: [이슈 #33](https://github.com/Theia0382/yozm-news/issues/33) — 기점 `2389701` 의 재처리 코드와 Spring Modulith 2.1.1(events-api · core · jdbc 소스 jar)을 읽어 확인. 구현 `82171b2`(`platform` 공개 운영 API) · `11f597d`(`admin` 엔드포인트) · `39bc04b`(운영자 화면) · `a81add1`(재제출 전 읽기 · 본문 판정) · `7ab0e7f`(화면 정정). 재제출 루프의 결함은 확인용 인스턴스의 실측 스택과 Spring Modulith 2.1.1 · 2.1.2 · 2.2.0-RC1 소스 비교로 확인
- 관련: [ADR-0023](0023-jobrunr-oss-framework-schema-and-event-resubmission.md)(재처리 상한 · 완료 발행 즉시 삭제 · 리스너 멱등 — 결과 절의 "수단이 아직 없다"를 이 ADR 이 해소한다), [ADR-0037](0037-domain-may-use-non-replaceable-framework-types.md)(정책이 Modulith 의 상태 타입을 받는다), [ADR-0044](0044-screen-api-results-as-flat-discriminated-200-and-rfc9457-problems.md)(발행마다 판별자 결과 — 그대로 적용), [ADR-0045](0045-admin-module-serves-operator-api-over-module-public-operation-apis.md)(공개 운영 API 형태 — 그대로 적용)

## 맥락

- 처리 시도가 상한(6회)에 이른 실패 발행은 `FAILED` 로 남고, 재처리 작업이 돌 때마다 경고 로그에 ID 만 남는다. 원인을 고친 뒤 다시 처리하거나 버리려면 DB 를 직접 다뤄야 했다.
- Spring Modulith 2.1.1 의 공개 API 는 미완료 발행을 재제출(`IncompleteEventPublications`)할 뿐, 미완료 발행을 목록으로 읽거나 지우지 못한다. 그런 기능은 저장소 SPI(`EventPublicationRepository`)에만 있다. 이 SPI 는 앱의 main 컴파일 경로에 없고, 삭제는 상태를 보지 않고 ID 로 지운다.
- 발행의 이벤트 종류는 이벤트를 역직렬화해야 얻는다. 그런데 이벤트 레코드의 필드 이름 · 형식을 바꾼 배포처럼, 클래스는 있어도 본문이 그 클래스로 읽히지 않는 발행이 생긴다.
- Spring Modulith 의 재제출 루프는 본문을 읽지 못하는 발행을 만나면, 조건부 갱신으로 처리 시도를 1 늘린 뒤 예외를 루프 밖으로 던진다. catch 블록의 진행 중 목록 해제가 이벤트를 다시 역직렬화하기 때문이다. 그래서 그 회차 · 요청에서 그 발행보다 뒤 순서의 발행은 재제출되지 않는다. 재처리 작업 회차는 실패하고, 상한 경고도 남지 않는다. 발행이 상한에 이를 때까지 이것이 되풀이된다. 2.1.2 · 2.2.0-RC1 도 같다.
- 이벤트 클래스를 로드하지 못하는 행은 Modulith 가 읽을 때 버린다. 그래서 그런 행은 재처리 작업에도, 멈춤 감시에도, 상한 경고 로그에도 나타나지 않고, Modulith 가 행을 읽을 때마다 남기는 "알 수 없는 종류" 경고에만 ID 와 클래스 이름이 보인다. 미완료 발행이 남은 채 이벤트 레코드의 이름을 바꾸거나 지운 배포에서 생긴다.
- 재제출의 조건부 갱신(`STATUS != 'RESUBMITTED'`)은 상한에 이른 발행에도 그대로 적용되고, 처리 시도를 1 늘린다. 처리 시도를 되돌리는 공개 API 는 없다.
- 멈춤 감시는 발행 시각으로 판정한다. 상한에 이른 발행은 대개 발행한 지 멈춤 기준(30분)이 지났다. 그래서 운영자가 재제출한 발행은 리스너가 아직 처리 중이어도 다음 감시 회차에 `FAILED` 로 바뀔 수 있다.

## 결정

- **재처리가 더 이상 다루지 않는 발행을 "남겨진 발행"으로 운영자에게 보인다.** 남겨진 발행은 두 가지다. 하나는 상한에 이른 실패 발행이고, 다른 하나는 완료되지 않았는데 이벤트를 읽을 수 없는 발행이다 — 이벤트 클래스를 로드할 수 없거나, 본문을 그 클래스로 읽을 수 없다(예외 또는 값 없음). 판정의 뜻은 재처리 정책(`EventResubmissionPolicy`), 읽기 결과를 "읽을 수 있음"으로 바꾸는 규칙은 `EventReading` 한 곳이다. 클래스를 로드할 수 있는지는 Modulith 와 같은 클래스 로더 · 같은 판정(`ClassUtils`)으로, 본문은 Modulith 와 같은 직렬화기(`EventSerializer`)로 본다.
- **이벤트를 읽을 수 없는 발행은 재제출 전에 거른다.** 재처리 작업과 운영자 다시 처리의 필터가 조건부 갱신 전에 실패 발행의 이벤트를 읽어 보고, 읽지 못하면 재제출하지 않는다. 재제출 루프가 끊기지 않고, 처리 시도도 소모하지 않는다. 재처리 작업은 상한에 이른 발행과 읽을 수 없는 발행을 따로 세어 경고 한 줄로 알린다. 원인 배포를 고쳐 다시 읽을 수 있게 되면 재처리 작업이 상한까지 그대로 이어 처리한다.
- **다시 처리는 지금 한 번 재제출한다.** 재처리 작업과 같은 공개 API 경로 · 같은 조건부 갱신을 거치고, 처리 시도는 누적한다. 앱은 처리 시도 열을 고치지 않는다. 다시 실패하면 곧바로 남겨진 발행으로 돌아오고, 재처리 작업은 그 발행을 다시 다루지 않는다. 읽을 수 없는 발행은 재제출할 수 없다.
- **재제출 직후의 다시 처리를 막지 않는다.** 화면에는 마지막 재제출 시각을 보인다. 같은 발행이 동시에 처리되면 리스너 멱등이 결과를 지킨다.
- **폐기는 기록 테이블 없이 지운다.** 지운 발행마다 `WARN` 로그 한 줄에 ID · 까닭 · 이벤트 종류 · 리스너 · 발행 시각 · 처리 시도를 남긴다. 이벤트 내용은 남기지 않는다.
- **목록과 폐기는 `platform` 이 레지스트리 테이블 `event_publication` 을 직접 읽고 지운다.**
  - 이벤트 내용은 읽을 수 있는지의 판정에만 Modulith 의 직렬화기(`EventSerializer` — `events-core` 를 main 컴파일 의존으로 들인다)로 읽고, 응답 · 로그에는 싣지 않는다. 처리 시도가 비어 있으면 Modulith 와 같게 0 으로 읽는다.
  - 폐기는 읽은 상태 · 처리 시도 · 이벤트 종류가 그대로일 때만 지운다.

## 결과

- ADR-0023 결과 절의 "상한에 이른 발행을 다시 처리하거나 지우는 수단은 아직 없다"가 해소된다. 운영자는 화면에서 남겨진 발행을 다시 처리하거나 폐기한다.
- 앱이 프레임워크 테이블의 열 이름과 상태 문자열에 묶인다. Modulith 를 올려 스키마가 바뀌면 라이브러리 원문 대조 시험이 먼저 실패하고, 실제 PostgreSQL 시험이 앱이 쓰는 열을 지킨다.
- 운영자가 재제출한 발행의 리스너는 화면 역할 프로세스에서 돈다.
- 앱이 Spring Modulith 의 공개 API 밖 인터페이스(`events-core` 의 `EventSerializer`)에 기댄다. 2.1.1 · 2.1.2 · 2.2.0-RC1 에서 같지만, 판을 올릴 때 확인할 대상이다. 재제출 전 읽기는 Modulith 가 읽기에 성공한 이벤트를 캐시하는 동작에 기대 같은 이벤트를 두 번 역직렬화하지 않는다 — 캐시가 없어져도 판정은 같고 비용만 는다.
- 목록과 폐기가 클래스가 있는 미완료 행의 본문을 모두 역직렬화한다.
- 폐기한 이벤트는 되살릴 수 없다. 예를 들어 `ArticleFetched` 발행을 폐기하면 그 기사는 저장되지 않는다. 수집은 이미 보낸 항목을 다시 보내지 않기 때문이다.
- 장애가 아직 이어지는 동안에는 재제출 한 번이 다시 실패한다. 운영자는 원인이 풀린 뒤 다시 처리를 한 번 더 누른다.
- `ClassUtils` 는 로드 중 생긴 모든 오류를 "로드할 수 없음"으로 본다. 반면 Modulith 는 클래스를 찾지 못한 경우만 버린다. 그래서 링크 오류가 나는 행은 화면에 "읽을 수 없음"으로 보이고, 폐기할 수 있다.
- 리스너가 길면 운영자가 재제출한 발행이 처리 중에 다시 목록에 보일 수 있다. 이것을 다시 처리하면 같은 발행이 동시에 처리된다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 다시 처리할 때 처리 시도를 처음으로 되돌리거나 N회를 더 허용하고, 재처리 작업이 상한까지 다시 처리한다 | Modulith 가 갱신하는 열을 앱이 고친다. 감시는 운영자가 되살린 발행을 처리 중에도 1분 안에 `FAILED` 로 돌리므로, 재처리 작업이 처리 중인 발행을 거듭 재제출할 수 있다. 결과도 재처리 주기만큼 늦게 보인다 |
| 폐기 기록 테이블을 둔다 | 운영자가 토큰 하나라 누가 지웠는지 남길 수 없어 감사 가치가 작다. 새 테이블과 보존 정책이 생기고, 이벤트 내용에 사용자 데이터가 들어가면 그 처리 대상도 늘어난다 |
| Modulith 저장소 SPI(`EventPublicationRepository`)로 읽고 지운다 | 이벤트 종류를 얻으려면 역직렬화해야 해 본문이 깨진 행에서 목록이 깨지고, 클래스 없는 행은 빠진다. 삭제가 상태를 보지 않는다 |
| 재제출 중 예외를 잡아 그 발행만 빼고 이어서 재제출한다 | 어느 발행이 던졌는지를 "마지막으로 필터를 통과한 발행"으로 추정한다 — Modulith 내부 순서에 기댄다. 그 발행은 매번 처리 시도를 소모해 상한에 이르면 "상한에 이름"으로 보여, 다시 처리해도 같은 실패가 되풀이된다 |
| 목록의 본문 판정을 공개 API 재제출(늘 거짓인 필터)로 읽어서 한다 | 재제출 메서드를 읽기로 쓰는 오용이다. 목록 요청마다 미완료 전체를 다시 읽는다 |
| 목록의 본문 판정을 앱의 `JsonMapper` 로 직접 한다 | Modulith 의 직렬화기 선택 규칙(컨텍스트의 `JsonMapper`, 없으면 기본 mapper, Jackson 2 대체 구성)의 사본이다 — 판을 올리거나 구성이 바뀌면 목록과 재제출의 판정이 조용히 어긋난다 |
| 상한에 이른 발행만 다룬다 | 이벤트 클래스가 없는 행은 여전히 DB 로만 지울 수 있다. 그 사이 매 회차 Modulith 경고가 반복된다 |
| 읽을 수 없는 발행을 "앱이 읽은 행 − Modulith 가 재제출 필터에 넘긴 행"으로 가른다 | 재제출 메서드를 목록용으로 부르는 오용이다. 두 읽기 사이에 경합이 생긴다 |
| 재제출 직후 정해진 시간 동안 다시 처리를 막는다 | 정책에 새 기준 시간이 생긴다. 실패가 확실한 발행도 그 시간 동안 다시 처리할 수 없다 |
