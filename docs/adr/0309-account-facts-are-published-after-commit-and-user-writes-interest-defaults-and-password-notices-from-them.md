# ADR-0309: 계정 생김 · 비밀번호 바뀜은 `account` 가 커밋 뒤 이벤트로 알리고, 관심 설정 기본값 · 비밀번호 알림은 받는 `user` 가 쓴다

- 상태: 승인
- 날짜: 2026-11-24
- 근거: [이슈 #250](https://github.com/Theia0382/yozm-news/issues/250) — 기점 `77769fb` 에서 설정 행이 없는 계정을 견디는 자리(조회의 기본값 대체 · 저장 유스케이스의 지연 생성 · 기동 채우기)와 기본값 쓰기의 한 번 보장(`insertIfAbsent`)을 확인
- 관련: [ADR-0308](0308-account-authentication-and-security-live-in-the-account-module-while-interests-and-notices-stay-in-user.md)(모듈 경계 · 의존 방향), [ADR-0182](0182-startup-work-reading-the-active-tag-set-runs-in-a-lifecycle-phase-after-first-start-seeding-and-before-the-web-server.md)(첫 운영자 생성이 활성 체계를 읽는 기동 작업이다 — 부분 대체), [ADR-0175](0175-tag-preferences-follow-tag-set-activation-events-and-are-rewritten-to-active-keys.md)(선호 버전 울타리 — 보충), [ADR-0145](0145-password-notices-are-left-for-password-changes-and-recovery-resets-but-not-for-the-forced-first-sign-in-change.md)(비밀번호 알림을 남길 계기), [ADR-0233](0233-digest-failure-notices-come-through-an-event-declared-by-the-receiving-user-module-for-every-failed-digest.md)(받는 쪽이 선언하는 이벤트 — 이 이벤트들은 받는 쪽이 내는 쪽에 의존해 내는 쪽이 선언한다)

## 맥락

- 계정을 만드는 정본은 계정 · 자격과 함께 관심 설정 기본값(설정 행 · 기본 제외 형식)을 한 트랜잭션에서 쓰고, 비밀번호 변경 · 복구 재설정은 자격과 함께 비밀번호 알림을 한 트랜잭션에서 쓴다. 계정 쪽을 `account` 로 떼면(ADR-0308) `account` 가 `user` 를 부르게 되어 두 모듈이 서로 의존한다.
- 관심 설정 기본값 쓰기는 활성 태그 체계를 읽고 선호 버전 울타리를 잡는다. 그래서 계정 생성이 태그 체계 쪽 실패로 함께 실패하고, 첫 운영자 생성이 태그 체계의 첫 적재 뒤에 돌아야 했다(ADR-0182).
- 설정 행이 없는 계정은 이미 견딘다 — 조회는 기본값으로 답하고, 저장 유스케이스는 잠그기 전에 행을 먼저 만들며, 기동 때 채우기가 행 없는 계정을 채운다. 기본값 쓰기는 행이 없을 때만 넣어 몇 번 불려도 한 번이다.
- 모듈 사이 이벤트는 모두 커밋 뒤 받는 `@ApplicationModuleListener` 이고, 발행 레지스트리가 실패한 처리를 다시 부른다.

## 결정

- **`account` 는 계정의 사실을 내는 쪽이 선언한 이벤트로 알린다** — 계정을 만드는 네 길 모두 계정을 쓴 트랜잭션에서 `AccountCreated(user, createdAt)` 를, 사용자가 고른 비밀번호로 바꾼 때(세션 사용자의 변경 · 복구 재설정) 자격을 바꾼 트랜잭션에서 `PasswordChanged(user, method, changedAt)` 를 낸다. 받는 쪽(`user`)이 내는 쪽에 의존하는 방향이라 받는 쪽이 이벤트를 선언하지 않는다.
- **`account` 의 트랜잭션은 다른 모듈의 표를 쓰지 않는다.** 관심 설정 기본값과 비밀번호 알림은 `user` 가 커밋 뒤 이벤트를 받아 새 트랜잭션에서 쓴다.
- **관심 설정 기본값의 이력 시각은 계정을 만든 시각이다.** 이벤트 전에 저장 유스케이스나 기동 채우기가 먼저 썼으면 리스너는 아무것도 쓰지 않는다.
- **비밀번호 알림은 같은 변경을 거듭 받아도 하나다** — 사용자 · 바꾼 시각의 부분 고유 인덱스로 막는다(키 무효 · 다이제스트 실패 알림과 같은 꼴).
- **첫 로그인의 강제 변경 · 운영자의 초기 비밀번호 다시 정하기 · 복구 코드 재발급에는 `PasswordChanged` 를 내지 않는다** — 지금 알림을 남기지 않는 계기(ADR-0145)와 같고, 받을 쪽이 없다.
- **첫 운영자 생성은 활성 태그 체계를 읽지 않는다.** 첫 운영자는 `account` 의 기동 단계(웹 서버 앞)에서 돌고, 기존 계정 채우기는 `user` 의 기동 단계(첫 적재 뒤 · 웹 서버 앞)에서 돈다 — 두 작업 사이에 순서가 없어 각 모듈이 자기 단계 상수를 갖는다.

## 결과

- 계정 생성 · 비밀번호 변경이 태그 체계 · 알림 쪽의 실패로 실패하지 않는다. 리스너가 실패하면 발행 레지스트리가 다시 부르고, 그사이 설정 행이 없는 계정은 기본값으로 다뤄진다.
- 가입 직후 · 비밀번호 변경 직후의 짧은 동안 설정 행 · 비밀번호 알림이 아직 없을 수 있다. 화면 · 조회의 결과는 기본값 대체로 같고, 비밀번호 알림은 리스너가 돈 뒤 알림함에 나타난다. 알림 행의 만든 시각은 리스너가 돈 시각이고, 화면이 보이는 바꾼 시각은 내용의 시각이다.
- 선호 버전 울타리(ADR-0175)는 그대로 기본값 쓰기를 활성 전환의 훑기와 줄 세운다 — 쓰는 자리가 계정 생성 트랜잭션에서 리스너의 트랜잭션으로 옮겨 갔을 뿐이다.
- 시험은 계정을 만든 뒤 설정 행을 읽을 때 리스너를 기다리거나 기본값 쓰기를 직접 부른다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| `account` 가 "계정과 함께 쓸 것" 공급 인터페이스를 선언하고 `user` 가 구현해 같은 트랜잭션에서 부른다 | 계정 모듈이 관심 쪽의 필요를 위한 구멍을 갖고, 관심 쪽의 실패가 계정 생성을 실패시킨다. 부르는 쪽 트랜잭션에 참여해 쓰는 첫 공급 인터페이스가 된다 |
| `account` 가 이벤트를 내고 `user` 가 같은 트랜잭션의 동기 리스너로 쓴다 | 빠지면 안 되는 단계를 이벤트로 감추고, 리스너가 빠져도 계정 생성이 조용히 성공한다. 실패는 여전히 함께 터지고, 모듈 사이 동기 리스너라는 새 꼴이 생긴다 |
| `PasswordChanged` 를 모든 자격 변경(강제 변경 · 운영자 다시 정하기 포함)에 내고 받는 쪽이 거른다 | 지금 받을 쪽이 없는 계기를 이벤트로 늘린다 |
| 비밀번호 알림의 중복 막기 키를 자격 버전으로 | 알림 내용에 이미 바꾼 시각이 있고, 키 무효 알림과 같은 꼴(내용의 시각)이 된다 |
