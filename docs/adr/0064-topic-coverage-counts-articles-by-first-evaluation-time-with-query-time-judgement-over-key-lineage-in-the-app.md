# ADR-0064: 주제별 보도량은 기사의 첫 평가 시각으로 기간에 넣고, 최신 평가의 조회 시점 판정을 계보로 활성 버전 키에 이어 앱에서 센다

- 상태: 승인
- 날짜: 2026-11-03
- 근거: [이슈 #72](https://github.com/Theia0382/yozm-news/issues/72) — 기점 `29bccac` 의 평가 결과 저장(기사 · 버전마다 넣기 한 번, 갱신 · 버전 단위 삭제 없음 — 지운 기사를 따라서만 지운다), 조회 시점 판정(`TagJudgement` — 태그 기준 · 저장 기준을 저장하지 않고 조회 때 적용), 최신 평가(버전 번호가 가장 큰 것), 태그 키 계보 해석(버전 → 활성 버전 키 집합의 표)을 확인. 구현 `55e832b`(집계 기간 · 평가 현황 · 커서 흘려 받기 · 읽기 전용 스냅숏) · `1c1976d`(주제별 보도량) · `4e4c3d2`(운영자 HTTP)
- 관련: [ADR-0062](0062-tag-set-versions-from-operator-text-activated-forward-with-key-lineage-and-recent-reevaluation.md)(버전은 앞으로만 켜고 키 계보로 옛 키를 잇는다 — 보도량이 그 해석을 쓴다), [ADR-0055](0055-tag-and-store-thresholds-change-with-history-and-warn-instead-of-blocking.md)(태그 기준 · 저장 기준은 조회 시점에 적용), [ADR-0045](0045-admin-module-serves-operator-api-over-module-public-operation-apis.md)(운영자 HTTP 는 `admin`), [ADR-0002](0002-shared-evaluation-with-jev.md)(공유 평가)

## 맥락

- 주제별 보도량은 운영자 화면이 먼저 쓰고, 변화 리포트 · 관심사 히스토리가 "기간마다 주제에 기사가 얼마나 있었나"로 뒤에 쓴다. 기간 축 · 세는 규칙이 소비자마다 달라지면 같은 기간의 수가 화면마다 다르다.
- 평가 행은 기사 · 버전마다 한 번 넣고 갱신하지 않는다. 버전 단위로 지우지 않고, 지운 기사를 따를 때만 지운다. 그래서 기사의 가장 이른 평가 시각은 기사가 남아 있는 한 바뀌지 않는다.
- 붙은 태그는 저장하지 않는다. 조회 때 그 평가 버전의 지금 태그 기준 · 저장 기준으로 판정한다(`low_confidence` 는 최고 확률 하나). 판정의 정본은 Java 의 `TagJudgement` 하나다.
- 옛 버전 평가의 키는 그 버전의 키다. 활성 버전의 키로는 계보 표로 푼다 — 분할된 키는 여러 키로, 계보 없이 지운 키는 빈 집합으로.
- 기사의 발행 시각 · 처음 본 시각은 `article` 이 갖는다. `evaluation` 의 SQL 은 `articles` 를 읽지 않는다.
- 재평가는 최근 기사를 한꺼번에 다시 평가한다. 평가 시각으로 기간을 나누면 재평가한 날에 기사가 몰린다.

## 결정

- **기간 축은 기사의 첫 평가 시각이다.** 기간 안에 첫 평가가 있는 기사를 센다 — 재평가는 기사를 옮기지 않는다. 기사는 그 기사의 최신 평가(버전 번호가 가장 큰 것)로 센다.
- **판정은 조회 시점에 Java 정본을 부른다.** SQL 은 평가 행과 태그 행을 가져오기만 하고, 판정 · 계보 풀기 · 세기는 `evaluation` 의 `domain` 이 한다 — SQL 에 판정의 두 번째 사본을 두지 않는다. `low_confidence` 로 붙은 주제도 센다.
- **계보로 활성 버전의 키에 이어 센다.** 분할된 키의 기사는 새 키마다 하나씩, 병합된 키들을 가진 기사는 한 번 센다. 계보 없이 지운 키만 가진 기사와 미분류 기사는 "활성 주제에 이어지지 않은 기사"로 따로 센다. 대분류의 수는 하위 중분류 수의 합이 아니라 하위 어느 것이든 붙은 기사 수다.
- **보도량은 공개 조회다.** 입력은 시간대 없는 `[from, to)` 시각 범위와 주제 집합(빈 집합이면 모든 주제, 대분류 키는 하위로 펼친다)이다. 활성 버전에 없는 키는 결과 종류 하나로 돌려준다. 사용자를 모른다.
- **기간은 시간대 없는 시각 범위이고, 상한은 날짜 31일이다.** 날짜 범위는 부르는 쪽이 정한 시간대의 자정으로 시각 범위를 만드는 보조 생성으로 둔다 — 1 ~ 31일. 시각 범위의 상한은 시간대 전환 여유로 하루를 더한 32일이다. 범위 판정은 공개 타입 하나가 하고, `admin` 은 그 결과를 400 으로 옮긴다.
- **집계는 읽기 전용 `REPEATABLE READ` 트랜잭션 하나에서 커서로 흘려 읽는다.** 활성 버전 · 체계 · 기준 · 계보 · 평가 행이 한 스냅숏이라 집계 중 활성 전환이 끼어도 계보 표의 기준 버전과 읽은 활성 버전이 같다 — 다르면 불변식이 깨진 것이라 실패한다. 행은 fetch size 커서로 나눠 받아 메모리가 기간의 행 수에 비례하지 않는다. 그래서 이 조회는 "트랜잭션을 열지 않는다"는 다른 공개 조회와 달리 트랜잭션을 연다.

## 결과

- 같은 기간을 다시 세면 같은 기사 집합이다 — 재평가 · 기준 변경 · 활성 전환은 기사의 주제(판정 · 계보)를 바꿀 수 있지만 기사를 다른 기간으로 옮기지 않는다. 기준을 바꾸면 지난 기간의 수도 지금 기준으로 다시 나온다.
- 첫 평가 시각은 기사를 처음 본 시각보다 늦다 — 정착 시간(30분)과 대기만큼이고, 평가가 멈췄던 동안의 기사는 평가가 재개된 날로 들어간다. 이 모듈을 들이기 전에 저장된 기사는 처음 평가한 날에 한꺼번에 들어간다(일회성).
- 이 계약은 평가 행이 갱신되지 않고 버전 단위로 지워지지 않는다는 데 기댄다. 평가 행을 고치거나 버전째 지우는 변경은 보도량의 기간 축을 함께 다시 정해야 한다.
- 처리 시간은 기간의 평가 행 수에 비례한다. 개발 기기의 합성 데이터(31일 · 평가 124,000건 · 평가마다 태그 행 10)에서 보도량은 1.20 ~ 1.47초, 같은 트랜잭션 모양의 평가 현황(버전 하나)은 1.74 ~ 2.28초(중앙값 약 1.96초)를 쟀다(준비 실행 뒤 — 첫 호출은 각각 1.42 ~ 1.53초 · 2.27 ~ 2.34초) — 목표 2초의 경계라 그대로 두고 기록했다. 힙 최고치는 31일과 7일이 같았다. 재평가가 많은 운영 데이터와 작은 셀프 호스팅 기기에서는 재지 않았다.
- 집계 트랜잭션이 열린 동안 그 스냅숏 뒤의 죽은 행을 정리(VACUUM)하지 못한다 — 운영자 화면 한 번의 조회라 짧고 드물다.
- 리포트 · 관심사 히스토리는 같은 공개 조회를 부르면 같은 수를 얻는다. 시간대는 부르는 쪽이 정한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 기사의 발행 시각으로 기간에 넣는다 | `evaluation` 이 `article` 의 시각을 사본으로 갖거나 모듈 경계를 넘어 읽어야 하고, 발행 시각이 없는 기사는 받은 시각으로 채운 값이라 피드마다 뜻이 다르다 |
| 기사를 처음 본 시각으로 기간에 넣는다 | 같은 사본 · 경계 문제가 있고, 첫 평가 시각과의 차이는 정착 시간과 대기뿐이다 |
| 그 평가의 평가 시각으로 기간에 넣는다 | 재평가한 날에 기사가 몰리고, 같은 기사가 버전마다 다른 기간에 나온다 |
| 판정을 SQL 로 한다(태그 기준 비교 + 창 함수로 `low_confidence`) | 판정의 두 번째 사본이 생겨 조회 시점 판정과 어긋날 수 있다 |
| 판정 결과를 평가 때 저장해 SQL 로 센다 | 태그 기준 · 저장 기준을 바꾸면 저장한 판정을 다시 써야 한다 — 조회 시점 판정(ADR-0055)과 맞지 않는다 |
| 활성 버전으로 평가된 기사만 센다 | 재평가 기간 밖의 기사가 활성 전환 뒤 보도량에서 사라진다 |
| 트랜잭션 없이 흘려 받는다 | PgJDBC 가 결과 전체를 메모리에 담고(31일 합성 기준 약 1,240,000행), 문장마다 스냅숏이 달라 집계 중 활성 전환을 다시 세야 한다 |
| 기사 ID 구간마다 한 문장씩 나눠 읽는다 | 메모리는 묶이지만 구간마다 스냅숏이 달라 첫 평가 · 최신 평가 판단과 활성 버전이 구간 사이에서 갈릴 수 있다 |
| 기간을 날짜 · 시간대로만 받는다 | 상한이 날짜 수 하나로 깔끔하지만, 자정에 맞지 않는 구간(조회 시각에서 거꾸로 7일)을 소비자가 낼 수 없다 |
| 기간 상한을 92일(분기)로 · 두지 않는다 | 가장 긴 v1 소비자는 월간 리포트다. 처리 시간이 기간에 비례해 92일이면 측정 목표가 세 배가 되고, 상한이 없으면 한 요청이 쌓인 평가 전부를 읽을 수 있다 |
