# ADR-0212: 마이그레이션은 사용자 데이터와 그것이 가리키는 공유 데이터의 행 · ID 를 지우지 않고, 데이터를 옮기면 데이터 시험으로 대조한다

- 상태: 승인. 부분 대체 — 사용자 데이터를 지우지 않는 범위([ADR-0315](0315-a-settings-column-of-a-removed-feature-may-be-dropped-by-a-migration-with-the-adr-that-removed-it.md))
- 날짜: 2026-11-17
- 근거: [이슈 #181](https://github.com/Theia0382/yozm-news/issues/181) — 마이그레이션 V1 ~ V51 전수 대조(사용자 행을 지운 마이그레이션 없음, 운영자 기준과 그 이력을 옮기지 않고 지운 것은 V29 · V40), 사용자 표의 다른 모듈 ID 참조(V44 · V46 · V47 · V50 — FK 없음), 구독 따라가기의 "없는 스토리라인은 뺀다"(`SubscriptionFollow`), 같은 꼴의 기존 마이그레이션 데이터 시험 7개. 공유 데이터를 포함하고 사용자 데이터가 아닌 데이터는 정하지 않는 범위로 정해 ADR 로 남김

## 맥락

- 마이그레이션은 앱이 기동할 때 모든 셀프 호스팅 인스턴스에서 실행된다. 사용자 데이터를 지우는 버전이 나가면 그 버전으로 올린 모든 운영자의 사용자 이력이 사라지고 되돌릴 길은 백업뿐이다.
- 다이제스트 · 노출 기록 · 관심 신호 이력 · 관심 설정 이력은 관심사 히스토리 · 변화 리포트의 근거라 오래 쌓여야 쓸모가 있다. 보존 기간은 [data-model.md 보존 정책](../data-model.md#보존-정책-초안)이 정하지만, 그 기간이 마이그레이션에도 걸린다는 규칙은 없었다.
- 사용자 데이터는 다른 모듈의 ID 를 FK 없이 가리킨다 — 다이제스트 인용 · 피드백은 기사 ID, 선호 이력은 태그 체계 버전과 태그 키, 스토리라인 구독은 스토리라인 ID. 가리키는 행이 사라지면 사용자 행이 남아도 뜻을 잃는다. 스토리라인 표를 다시 만들면 구독 따라가기가 찾지 못한 ID 를 사라진 것으로 보고 모든 구독을 빼고([user-R53](../specs/user.md#스토리라인-구독)), 시퀀스까지 처음으로 돌리면 옛 ID 가 무관한 새 스토리라인을 가리킨다.
- 데이터를 옮긴 마이그레이션(V6 · V10 · V19 · V26 · V27 · V49)은 직전 버전에 옛 행을 넣고 끝까지 올려 대조하는 시험을 이미 갖고 있다. 규약으로 적혀 있지는 않았다.

## 결정

> 부분 대체 — [ADR-0315](0315-a-settings-column-of-a-removed-feature-may-be-dropped-by-a-migration-with-the-adr-that-removed-it.md). 지금 상태: [CONTRIBUTING.md §7](../../CONTRIBUTING.md#7-코드)
- **사용자 데이터를 지우는 마이그레이션을 쓰지 않는다.** 대상과 기간의 정본은 보존 정책 표이고, 표의 기간은 마이그레이션에도 적용된다.
- **사용자 데이터가 가리키는 공유 데이터도 같다** — 기사 · 태그 · 태그 체계 · 사건 · 스토리라인의 행을 마이그레이션이 지우지 않고, ID 를 다시 매기지 않는다.
- **꼴을 바꿀 때는 새 자리로 옮긴 뒤 옛 자리를 지우고, 옮기거나 고쳐 쓰는 마이그레이션은 데이터 시험을 함께 둔다** — 실제 PostgreSQL 의 별도 스키마에 직전 버전까지 올려 옛 행을 넣고, 끝까지 올린 뒤 옮긴 값을 대조한다.
- 앱이 설계로 지우거나 바꾸는 경로(탈퇴, 지운 기사 따르기, 스토리라인 구독 따라가기, 태그 선호 따라가기, 보존 정리)는 이 결정의 대상이 아니다.
- 사용자 데이터도 그것이 가리키는 공유 데이터도 아닌 데이터(운영자 설정과 그 이력, 판정 원본, 대기열 등)는 이 결정이 정하지 않는다.

규칙은 [CONTRIBUTING.md §7](../../CONTRIBUTING.md#7-코드)에 있다.

## 결과

- 사건 · 스토리라인을 통째로 다시 만드는 일은 마이그레이션으로 하지 않는다 — 앱의 경로(합치기 · 풀기 · 다시 판정)가 알림으로 사용자 데이터를 따르게 하는 쪽으로 설계한다.
- 사용자 데이터의 꼴을 바꾸는 이슈는 옮기는 식과 데이터 시험만큼 일이 는다.
- 지키는 장치는 규칙과 리뷰다. 마이그레이션 원문을 훑어 막는 자동 검사는 없다 — 시험을 빠뜨린 마이그레이션은 리뷰가 잡는다.
- 보존 정책 표에 행이 없는 사용자 데이터는 표에 행을 두어야 대상이 분명하다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 사용자 표만 지킨다 | 가리키는 공유 데이터가 사라지면 사용자 행이 남아도 이력의 뜻이 사라진다 — 스토리라인을 다시 만드는 마이그레이션 하나로 모든 구독이 빠진다 |
| 인스턴스의 모든 기록 데이터를 지킨다 | 사용자 이력과 관계없는 운영자 설정 · 이력까지 묶어, 뜻이 바뀐 기준에도 옮기는 식을 억지로 만들게 한다 |
| 마이그레이션 원문에서 보호 표를 지우는 문장을 찾는 자동 검사를 더한다 | 보호 표 목록이 보존 정책 표의 사본이 되고, 옮긴 뒤 지우기 · 고쳐 쓰기 · 연쇄 삭제를 문면으로 가를 수 없어 허용 표시가 필요하다 |
| 보존 대상 목록을 CONTRIBUTING 에 나열한다 | 보존 정책 표와 같은 지식의 두 번째 사본이 된다 |
| 문서 규칙만 두고 데이터 시험은 요구하지 않는다 | "옮겼다"의 증거가 실행으로 남지 않는다. 시험 꼴은 이미 관행이라 요구해도 새 장치가 없다 |
