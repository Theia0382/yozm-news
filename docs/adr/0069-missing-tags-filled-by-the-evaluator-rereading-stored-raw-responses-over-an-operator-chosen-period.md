# ADR-0069: 저장 기준을 낮춘 뒤 빠진 태그는 운영자가 정한 기간의 평가를 저장된 원본 응답으로 평가기가 다시 읽어 채운다

- 상태: 승인
- 날짜: 2026-11-04
- 근거: [이슈 #76](https://github.com/Theia0382/yozm-news/issues/76) — 기점 `45b16f3` 의 평가 저장(기사 · 버전마다 평가 하나, 원본 응답을 함께 `jsonb` 로 저장 — Jev 응답은 체계의 모든 질문에 답해야 저장된다), 체계 변경 때의 재평가(새 버전으로만 다시 평가 — 같은 버전의 평가가 있으면 건너뜀)를 확인. 구현 `3b605b7`(평가기 포트의 다시 읽기) · `1119c5a`(요청 · 회차 · 작업) · `df72313`(운영자 HTTP). 합성 데이터 측정(30일 · 평가 120,000건 — 41.9 · 43.6초)
- 관련: [ADR-0055](0055-tag-and-store-thresholds-change-with-history-and-warn-instead-of-blocking.md)(부분 대체 — 결정 "빠진 태그를 채우는 재평가는 별도 기능이다"), [ADR-0062](0062-tag-set-versions-from-operator-text-activated-forward-with-key-lineage-and-recent-reevaluation.md)(체계 변경 때의 재평가 — 이 채움과 다르다), [ADR-0059](0059-evaluation-job-limits-concurrency-and-retries-with-db-leases-on-queue-rows.md)(대기 행의 DB 점유 — 같은 모양), [ADR-0070](0070-past-store-threshold-maximum-and-mixed-store-floors-computed-from-history-and-finished-backfills.md)(채움이 경고 · 평가 현황에 드는 방식)

## 맥락

- 주제 · 지역 태그는 평가 때의 저장 기준 이상인 확률만 태그 행으로 저장한다. 저장 기준을 낮추면 그 전 평가에는 낮춘 구간의 행이 없어, 태그 기준을 그 구간으로 내려도 옛 기사에는 붙지 않는다(ADR-0055).
- 평가 행에는 원본 응답이 함께 저장된다. Jev 응답은 체계의 모든 질문에 답해야 저장되므로 저장 기준 아래 확률도 원본 응답에 있다. 로컬 대체물의 원본 응답도 모든 확률을 담는다.
- 체계 변경 때의 재평가(ADR-0062)는 새 버전으로 Jev 를 다시 부르는 경로라, 같은 버전 안의 빈 구간을 채우지 못한다. 같은 버전으로 다시 평가하려면 평가 행을 덮어쓰거나(평가 행이 바뀌지 않는다는 주제별 보도량 · 평가 1회의 전제가 깨진다) 버전마다 평가를 여러 개 두어야 한다.
- 원본 응답 보존은 180일(초안)이고 아직 지우는 작업이 없다. 운영 평가기는 Jev 하나다.

## 결정

- **Jev 를 다시 부르지 않고 저장된 원본 응답을 다시 읽어 채운다.** 평가 행은 고치지 않는다 — 채울 저장 기준 이상인데 없는 태그 행만 더한다. 같은 원본에서 같은 확률이 나오므로 있는 행은 그대로이고, 다시 돌려도 결과가 같다. 운영자 비용이 없다.
- **원본 응답의 형식은 평가기 포트가 안다.** 포트에 다시 읽기 연산을 더하고 구현마다 자기 형식만 읽는다 — 다른 평가기가 남긴 원본 응답 · 읽을 수 없는 원본 응답 · 체계와 어긋나는 결과는 건너뛰고 센다.
- **대상은 평가 시각이 기간 안인 모든 버전의 평가다.** 빈 구간은 평가 시각에 따라 생긴다. 은퇴한 버전의 평가도 다시 평가되지 않은 기사에서는 최신 평가라 후보 선별에 쓰인다 — 각 평가를 그 버전의 저장 기준까지 채운다.
- **운영자가 일수를 정한다 — 1 ~ 180일.** 덮는 범위는 요청 시각에서 그 일수 × 24시간 전부터 요청 시각까지다. 상한은 원본 응답 보존 기간(초안)과 같다 — 상한이 막는 것은 비용이 아니라 실행 시간이다.
- **실행은 작업 역할의 반복 작업이 DB 점유로 한다.** 요청은 채움 행 하나와 그 순간 버전마다의 저장 기준(채울 기준)을 기록하고, 반복 작업이 그 행을 점유해 평가 ID 순 묶음마다 진행(커서 · 건수)을 쓴다. 끝나지 않은 채움은 하나뿐이다. 프로세스가 죽어도 점유가 만료되면 커서부터 잇는다.
- **실행 전 확인은 범위의 평가 수를 버전별로 보이고 아무것도 쓰지 않는다.**

## 결과

- 저장 기준을 낮춘 운영자는 비용 없이 지난 평가의 빠진 태그를 채운다. 개발 기기의 합성 데이터에서 30일치(120,000건)는 1분이 안 걸렸고, 180일은 선형으로 약 4.2 ~ 4.4분으로 추정한다(재지 않음).
- 원본 응답 보존을 구현하면 그보다 오래된 평가는 채울 수 없다 — 그 처분은 보존을 구현하는 작업이 정한다.
- 열린 채움이 이어 가지 못하는 드문 경우(요청 뒤에 생긴 버전의 평가가 범위에 있음 — 프로세스 사이 시계가 어긋날 때만, 계속되는 DB 오류) 새 요청도 그 채움을 돌려받는다. 취소 경로는 없다.
- 평가기를 바꾸면(예: 다른 모델 스키마) 옛 원본 응답을 읽을 구현이 있어야 채울 수 있다 — 못 읽으면 건너뛰고 센다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| Jev 를 다시 불러 평가한다 | 운영자 비용이 들고(30일 약 $15 ~ $21 — 평가 비용의 추정), 같은 버전의 평가가 있어 덮어쓰거나 버전마다 평가를 여럿 둬야 한다. 모델이 바뀌었으면 같은 기사의 확률이 달라져 있는 행과 섞인다 |
| 원본 응답을 먼저 읽고 못 읽는 평가만 Jev 로 | Jev 재호출의 비용 · 평가 1회 충돌을 그대로 떠안는다. 지금은 못 읽는 평가가 사실상 없다 |
| 활성 버전의 평가만 채운다 | 은퇴한 버전에서 생긴 빈 구간이 남는다. 처리량 말고는 이득이 없다 |
| 기간 안에 처음 본 기사로 고른다(체계 변경 재평가와 같은 축) | 빈 구간은 평가 시각에 따라 생겨 기간과 어긋난다 |
| 상한 30일 | 파일럿 때 저장 기준을 내린 뒤 오래 지나면 채울 수 없다. 비용이 없어 짧게 둘 까닭이 실행 시간뿐이다 |
| 화면 역할이 요청 때 JobRunr 한 번 작업을 등록한다 | 화면 역할의 작업 등록 선례가 없고, 진행 · 재개를 결국 DB 에 둬야 한다 |
| 채울 저장 기준을 실행 때 읽는다 | 요청과 실행 사이 기준이 바뀌면 운영자가 확인한 것과 다르게 채운다 |
