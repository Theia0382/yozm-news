# ADR-0065: 막힌 주소로 가는 피드 요청은 일시 실패로 센다

- 상태: 승인
- 날짜: 2026-11-04
- 근거: [이슈 #84](https://github.com/Theia0382/yozm-news/issues/84) — [이슈 #64](https://github.com/Theia0382/yozm-news/issues/64) 의 48시간 실측에서 관찰. 구현 `d823f66`
- 관련: [ADR-0031](0031-feed-request-blocks-internal-addresses-with-apache-httpclient-deadline.md)(내부 주소 기본 차단과 실패의 일시 · 영구 분류 — 이 ADR 이 막힌 주소의 분류를 대체한다), [ADR-0049](0049-feed-request-blocks-ipv6-reserved-space-and-local-nat64.md)(차단 대역), [ADR-0041](0041-activation-gate-previews-a-feed-on-enable-and-judges-by-code-constants.md)(활성화 관문)

## 맥락

- 수집은 연결 주소가 차단 대역이면 연결하지 않고 `BLOCKED_ADDRESS` 로 실패한다. ADR-0031 은 이 실패를 영구로 분류했다 — "사람이 무언가를 바꾸기 전에는 다시 보내도 같은 결과가 날 것으로 보는 실패"다.
- 이름이 차단 대역으로 풀린 실패는 설정 문제(내부 이름을 적은 피드)와 망의 일시 장애를 가르지 못한다. 수집 쪽에는 그 순간의 해석 결과만 보인다. 실측에서 라우터가 다시 시작하는 동안 그 라우터의 DNS 가 공개 이름 `www.khan.co.kr` 을 `10.0.0.1` 로 돌려줬고, 그 언론사 피드 둘이 영구 실패로 세어졌다. 다음 회차에 망이 돌아와 회복했다.
- 영구 실패는 연속 2회면 피드를 `DEGRADED` 로 만들고 백오프 상한이 24시간이다 — 주기 15분이면 30분 넘는 망 장애가 피드 이상으로 보이게 된다. 일시 실패는 연속 5회면 `DEGRADED` 이고 상한이 6시간이다. 백오프가 늘어나는 모양은 둘이 같고 일시 상한에 닿는 실패부터 갈린다(주기 15분이면 5번째 연속 실패).
- 꺼진 피드는 한 번 받아 미리보아야 켜지므로(ADR-0041), 켜기 전의 설정 문제는 분류와 무관하게 켜는 순간 거절된다. 켜진 피드의 정기 수집에서 막히는 것은 켠 뒤에 이름의 해석 결과 · 리다이렉트 대상 · 허용 목록이 바뀐 경우다.
- 이름 해석 결과에 기대어 원인을 가르지 못하는 실패를 일시로 둔 선례가 있다 — `NAME_NOT_RESOLVED` 는 "이름 없음"과 "해석기 장애"를 가르지 못해 일시다.

## 결정

- **`BLOCKED_ADDRESS` 는 일시 실패다.** IP 리터럴로 막힌 경우도 같다 — 이유는 하나로 두고, 분류는 지금처럼 이유가 정한다. 정본은 `FetchFailureReason.permanence()` 다.
- 차단 자체 · 차단 대역 · 허용 목록, `DEGRADED` 기준 · 백오프 상한 값은 그대로다. 막힌 대역으로는 연결하지 않는다.
- 피드 켜기 · 원문 미리보기 결과의 차단 안내 문구는 바꾸지 않는다.
- 이미 쌓인 연속 영구 실패 수는 옮기지 않는다 — 다음 성공 · 변경 없음이 0 으로 되돌린다.

## 결과

- 일시 장애로 공개 이름이 내부 주소로 풀려도, 연속 5회(주기 15분이면 첫 실패부터 7시간 30분) 전에는 피드가 `DEGRADED` 가 되지 않는다.
- 켠 뒤에 내부 주소로 가게 된 설정 문제도 `DEGRADED` 가 그만큼 늦어진다. 수집 현황의 마지막 실패(이유 · 분류 · 문구)와 로그로는 첫 실패부터 보인다 — 오타 난 호스트 이름(`NAME_NOT_RESOLVED`)이 드러나는 방식과 같다.
- 막힌 주소 실패의 백오프 상한이 6시간이 된다.
- 저장된 마지막 실패의 분류는 읽을 때 이유에서 계산하므로, 배포 직후부터 과거 실패도 "일시적"으로 보인다. 이미 막힌 주소로 `DEGRADED` 인 피드는 성공할 때까지 `DEGRADED` 에 머문다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 영구로 둔다 | 주기 15분이면 30분 넘는 망 장애마다 피드가 `DEGRADED` 가 되고 상한이 24시간이 된다. 원인을 가르지 못하는 실패를 "같은 결과가 날 것"으로 보는 셈이다 |
| 이유를 둘로 나눈다 — IP 리터럴은 영구, 이름이 막힌 주소로 풀리면 새 이유로 일시 | 앞당겨지는 것은 정기 수집의 리터럴 차단(리터럴 리다이렉트 · 리터럴 피드의 허용 대역 축소)의 `DEGRADED` 뿐이다. 내부 리터럴을 적은 설정은 켤 때 이미 거절되고, 내부 이름을 적은 설정은 이 안에서도 일시다. 그 대가로 공개 이유 목록 · 화면용 API · 화면이 넓어진다 |
| 같은 이유를 반복 횟수로 다르게 분류한다(처음 몇 번은 일시, 그 뒤 영구) | "분류는 이유가 정한다"와 저장된 이유에서 분류를 다시 계산하는 구조를 함께 깨고, 결국 이유별 `DEGRADED` 기준과 같아진다 |
| 이 이유만 `DEGRADED` 기준을 따로 둔다 | 피드 상태 판정 규칙이 이유를 알게 된다. 얻는 것이 위 결정보다 크지 않다 |
| 차단 안내에 DNS · 망 일시 장애 가능성을 더한다 | 안내는 켜기 · 미리보기 결과에만 있어 정기 수집의 일시 장애에는 닿지 않는다. 지금 안내는 열 수 있는 곳을 알릴 뿐 열라고 하지 않고, 판단 재료(호스트 → 주소 문구 · 분류)는 이미 화면에 있다 |
| 수집 현황의 마지막 실패에도 안내를 붙인다 | 켠 뒤 차단의 원인이 이름 변경 · 일시 장애 · 리다이렉트 · 허용 목록 축소로 갈려 안내 한 문장이 틀린 조치를 권할 수 있다 |
