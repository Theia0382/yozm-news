# ADR-0032: 같은 기사 판정은 기사를 잃지 않는 쪽으로 좁히고, 피드별 기록은 (기사, 피드)마다 한 행으로 소스 단위 잠금 안에서 쓴다

- 상태: 승인
- 날짜: 2026-10-28
- 근거: [이슈 #20](https://github.com/Theia0382/yozm-news/issues/20) — Spring Modulith 2.1.1 · Spring Boot 4.1.2 자동 구성을 확인하고, PostgreSQL 에서 btree 항목 크기 한계와 소스 잠금 대기를 실행으로 확인. 구현 `8b43269`(판정 규칙) · `a84e3fe`(스키마 · 저장소) · `ee7d895`(이벤트 처리)
- 관련: [ADR-0013](0013-architecture-patterns.md)(aggregate 사이 ID 참조 · 멱등 작업), [ADR-0014](0014-spring-data-jdbc.md)(upsert 는 JdbcClient), [ADR-0023](0023-jobrunr-oss-framework-schema-and-event-resubmission.md)(이벤트는 최소 한 번 처리된다), [ADR-0026](0026-event-clustering-with-local-embeddings-and-jev.md)(다른 기사를 같은 사건으로 묶는 일)

## 맥락

- 같은 기사가 여러 섹션 피드와 여러 번의 수집으로 들어온다. 문서의 규칙은 L1(정규 URL 해시, 또는 같은 피드 안의 guid)과 L2(같은 소스 + 제목 비교 키 + 발행 시각 48시간 이내)였다.
- 두 종류의 실수는 비용이 다르다.
  - **잘못 합침**: 서로 다른 기사를 하나로 합치면 뒤 기사는 저장되지 않아 평가 · 다이제스트에 들어가지 못하고, 되살릴 길이 없다. 수집은 성공이라 실패가 드러나지 않는다.
  - **잘못 가름**: 같은 기사를 두 건으로 남기면 평가 비용이 조금 늘 뿐이다. 사건 묶기가 같은 사건으로 묶고, 다이제스트는 사건 단위로 하나만 고른다.
- 문서 규칙을 그대로 따르면 잘못 합치는 입력이 있다.
  - guid 를 모든 항목에 같은 값으로 넣거나 날마다 번호를 다시 쓰는 피드에서는 첫 항목 외 전부가 합쳐진다. 활성화 관문은 guid 의 유일성을 보지 않는다.
  - 같은 소스가 날마다 같은 제목으로 내는 정형 기사(`[게시판]` · 시세표 · 날씨 등)는 발행 시각 차가 24시간이라 L2 에 걸린다.
  - 제목 비교 키가 말머리 · 구두점까지 지우면 `[속보] A` 와 뒤이어 나온 본 기사 `A` 가 합쳐진다.
- 이벤트 리스너는 Modulith 가 켠 비동기 실행기(기본 스레드 8개)에서 리스너마다 새 트랜잭션으로 동시에 돈다. 고유 제약으로 표현할 수 없는 판정(같은 피드의 guid, 시간 창이 있는 제목)은 "찾아보고 없으면 넣는다" 사이에 경합한다.
- 이벤트는 다시 처리될 수 있고, 완료된 발행 기록은 바로 지워진다. 같은 항목은 재처리뿐 아니라 다음 수집에서도 다시 온다. 결과가 같다는 것은 `article` 의 데이터가 스스로 지켜야 한다.

## 결정

### 판정

- **정규 URL 이 주 키이고 guid · 제목은 보조 키다.** 순서는 정규 URL → guid → 제목이다.
- **정규 URL 은 자원을 바꾸지 않는 변환만 한다.** 스킴 · 호스트 소문자, 기본 포트 · 프래그먼트 · 추적 파라미터 제거, 빈 경로와 빈 질의 정리다. http↔https · `www.` 통일, 파라미터 정렬은 하지 않는다.
- **guid 는 제목 비교 키도 같을 때만 같은 기사로 본다.** guid 가 같지만 제목이 다르면 새 기사로 저장하고 로그를 남긴다.
- **제목 비교 키는 보수적이다.** NFKC 정규화 · 소문자 · 공백 제거까지만 하고 말머리 · 구두점은 남긴다. 키가 비면 guid · 제목으로 판정하지 않는다.
- **L2 는 이 피드에서 이미 본 기사를 후보에서 뺀다.** 문서가 밝힌 L2 의 대상 — 여러 섹션 피드에 같은 기사가 실리는 경우 — 만 남는다. 후보가 여럿이면 발행 시각이 가장 가까운 기사, 같으면 먼저 저장된 기사다.

### 기록

- **`article_feed_entries` 는 (기사, 피드)마다 한 행이다.** 그 피드에서 처음 본 항목의 값(항목 URL 해시 · guid · 카테고리 · 발행 시각 추정 여부 · 판정 종류 · 받은 시각)을 남기고, 다시 보면 아무것도 바꾸지 않는다.
- **엔트리의 항목 URL 을 L1 이 대조한다.** 제목으로 붙은 항목은 자기 URL 이 기사의 URL 과 달라 다시 받으면 L2 를 다시 타는데, 그 사이에 이 피드의 엔트리가 생겼거나 더 가까운 기사가 저장됐을 수 있다. 엔트리의 항목 URL 이 처음 붙은 기사로 돌려보낸다.
- **판정 종류를 엔트리에 남긴다** — 새 기사 · URL · guid · 제목. 중복 제거의 근거이고 운영 지표(중복률)의 입력이다.
- **기사는 처음 저장한 값이 남는다.** 같은 기사의 다른 항목이 와도 고치지 않는다.

### 동시성 · 결과 불변

- **같은 소스의 판정은 소스 단위 트랜잭션 범위 advisory lock 안에서 한다.** guid 는 같은 피드, L2 는 같은 소스 안의 판정이라 소스 단위면 판정 대상 전체를 덮는다.
- **소스를 건너는 같은 정규 URL 은 고유키와 `INSERT … ON CONFLICT` 가 맡는다.** 늦은 쪽은 먼저 저장된 기사에 붙는다.
- **새 기사 행을 실제로 만든 트랜잭션에서만 `ArticleStored` 를 발행한다.** 같은 항목을 다시 처리하면 L1 이 처음 붙은 기사에 걸고, 엔트리 쓰기는 아무것도 바꾸지 않는다.

## 결과

- 깨진 guid · 정형 기사 · 말머리 때문에 기사를 잃지 않는다. 대신 아래 경우는 같은 기사가 두 건 저장된다. 평가 비용이 그만큼 늘고 사건 묶기가 받친다.
  - URL 과 제목이 함께 바뀐 같은 항목
  - 구두점 모양만 다른 같은 제목
  - 같은 피드에 URL 만 바꿔 다시 올라온 같은 기사(guid 가 없거나 함께 바뀐 경우)
- 날마다 다른 피드에 실리는 같은 제목의 정형 기사는 여전히 합쳐진다. 판정 종류 "제목" 의 비율로 드러난다.
- 같은 소스의 항목 처리가 줄을 선다. 잠금을 기다리는 동안 DB 연결을 붙잡으므로 처리는 짧아야 한다. 처리량은 실제 수집에서 잰다.
- 정규 URL · 제목 비교 키 · guid 는 길이 상한이 없어 SHA-256 해시에 인덱스를 건다. 원문에 btree 를 걸면 긴 값 하나가 INSERT 를 실패시킨다.
- 제목 비교 키 규칙을 바꾸면 저장된 키 해시와 어긋난다. 바뀐 직후 시간 창(48시간)의 L2 만 영향을 받고, 잘못 가름 쪽으로 어긋난다. 규칙을 바꿀 때는 새 ADR 로 기록한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| guid 일치만으로 같은 기사 (문서 규칙 그대로) | guid 가 깨진 피드는 첫 항목 외 전부를 조용히 잃는다 |
| guid 는 그대로 믿고 활성화 관문이 한 문서 안 guid 중복을 거부 | 시간에 걸친 재사용과, 켠 뒤에 깨진 피드는 막지 못한다 |
| 제목 비교 키에서 말머리 · 구두점까지 지움 | 속보와 본 기사처럼 별개 기사를 합쳐 본 기사를 잃는다 |
| L2 를 같은 소스 전체에 그대로 적용 | 같은 피드의 정형 기사가 다음 날부터 저장되지 않는다 |
| L2 시간 창을 줄임 | 하루 두 번 나오는 정형 기사는 그대로 합쳐지고, 섹션 피드에 늦게 실린 같은 기사를 놓친다 |
| 엔트리를 본 때마다 한 행 | 행 수가 수집 쪽의 새 항목 선별 정확도에 따라 늘고, 중복률이 다시 노출로 부푼다 |
| 판정을 SERIALIZABLE 격리로 직렬화 | 직렬화 실패가 리스너 실패 → 재처리로 흘러 재시도 횟수를 소모한다 |
| 처리한 이벤트를 따로 기록해 멱등을 지킴 | 엔트리의 고유키가 이미 같은 사실을 담는다 — 두 번째 정본이다 |
