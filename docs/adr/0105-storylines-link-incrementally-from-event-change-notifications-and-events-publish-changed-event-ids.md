# ADR-0105: 스토리라인은 사건 변화 알림으로 증분으로 잇고, `event` 는 바뀐 사건 ID 를 발행한다

- 상태: 승인
- 날짜: 2026-11-10
- 근거: [이슈 #127](https://github.com/Theia0382/yozm-news/issues/127) — 스토리라인 골격(모듈 · 소속 데이터 · 사건 변화 따르기 · 잇기 작업). `event` 의 사건 쓰기 경로 전수 조사와 리드 결정
- 관련: [ADR-0101](0101-shared-storylines-connect-events-and-the-personal-side-is-storyline-subscriptions-and-interests.md)(결정 "공유 스토리라인의 책임 · 계약은 구현할 때 정한다" — 보충), [ADR-0060](0060-article-deletion-announced-by-removed-article-ids-and-followed-by-referencing-modules.md)(지운 ID 를 이벤트로 알리고 가리키는 쪽이 따르는 꼴 — 같은 꼴), [ADR-0045](0045-admin-module-serves-operator-api-over-module-public-operation-apis.md)(운영 API 의 꼴), [ADR-0106](0106-provisional-storyline-linking-opens-only-with-a-partner-event-and-adds-the-single-best-storyline-without-removal.md)(이 틀 위에서 도는 임시 잇기 규칙)

## 맥락

- 스토리라인은 사건들을 잇는 공유 흐름이고, 구독 · 타임라인이 스토리라인 ID 를 가리킨다([ADR-0101](0101-shared-storylines-connect-events-and-the-personal-side-is-storyline-subscriptions-and-interests.md)). 기간을 통째로 다시 묶으면 ID 가 흔들린다.
- 사건은 계속 바뀐다 — `event` 는 사건을 일곱 갈래(열기 · 붙이기 · 재판정의 옮기기 · 떼어 내기 · 합치기 · 닫기 · 기사 삭제로 줄이거나 지우기)로 바꾸지만, 도메인 이벤트를 하나도 발행하지 않았다. 사건 행 쓰기는 `event` 저장소 구현 하나(`JdbcEventRepository`)를 지나간다.
- 지워진 사건은 행이 사라져 흔적이 없고, 사건의 `revision` 은 사건마다의 횟수라 "어디까지 봤는지"를 커서 하나로 둘 수 없다.
- 사건은 처리 중에도 바뀐다 — 대기에 "이미 있으면 그대로"를 쓰면 처리 중에 다시 온 알림이 사라져 마지막 변화가 반영되지 않는다.
- 이 기능이 켜지기 전에 있던 사건, 특히 닫힌 사건은 거의 다시 바뀌지 않아 알림이 오지 않는다. 잇는 방법을 견줄 평가 세트는 이미 수집된 지난 기사에서 뽑는다.

## 결정

- **잇기는 증분이다.** 사건이 생기거나 바뀌면 그 사건을 판정해 스토리라인에 붙이거나 새 스토리라인을 연다. 기간을 통째로 다시 묶지 않는다 — 스토리라인 ID 가 구독 · 타임라인의 기준이다.
- **`event` 는 바뀐 사건 ID 를 발행한다(`EventsChanged`).** 사건을 바꾸는 저장소 메서드 다섯(열기 · 고치기 · 지우기 · 합치기 · 닫기)이 같은 트랜잭션에서 발행한다 — 일곱 갈래가 모두 이 메서드를 지나가고, 앞으로 생길 갈래도 빠뜨릴 수 없다. 트랜잭션 밖에서 부르면 실패한다. 알림은 ID 만 싣고 무엇이 일어났는지는 싣지 않는다 — 받는 쪽이 지금 상태(`EventDirectory.find` — 지워짐 · 합쳐짐 · 그대로)를 읽어 가른다. 그래서 알림의 순서가 바뀌거나 두 번 와도 결과가 같다. 대표 기사 비우기는 소속의 재료를 바꾸지 않아 알리지 않는다.
- **`storyline` 은 알림을 잇기 대기로 받는다.** 사건마다 한 행이고, 이미 있으면 다시 알림 수를 올린다. 회차는 점유할 때의 다시 알림 수가 그대로일 때만 행을 지운다 — 처리 중에 다시 온 알림을 놓치지 않는다. 대기는 사건의 첫 기사 시각 순으로 점유한다(지워졌거나 합쳐진 사건이 먼저) — 한꺼번에 넣은 사건도 실시간과 같은 시간 순으로 판정한다. 판정은 모듈 잠금 하나로 직렬이다.
- **판정이 예외를 내면 그 사건만 건너뛴다.** 실패 수를 세어 상한(3)이면 대기에서 빼고 오류 로그를 남긴다 — 시각 순 점유에서 회차를 멈추면 같은 사건이 뒤 사건을 영영 막는다.
- **사건이 지워지면 소속을 지우고, 합쳐지면 남는 사건으로 옮긴다. 구성 사건이 없는 스토리라인은 지운다.** 사건이 비면 지우는 것과 같은 꼴이다. 스토리라인을 가리키는 쪽(앞으로의 구독)이 생기면 지운 스토리라인 ID 를 알린다.
- **스토리라인은 사건 ID 만 가리킨다.** 기사를 가리키지 않아 기사 삭제는 사건의 변화로 따른다. 스토리라인을 알아보게 하는 대표는 구성 사건 하나 — 기사 수가 가장 많은 사건(같으면 사건 ID 가 작은 것)이고, 대표 기사는 그 사건의 것을 조회할 때 읽는다. 소속마다 정한 것 · 점수 · 판정에 쓴 기준(기준 이력 ID)을 남긴다.
- **켜기 전의 사건은 운영자가 채운다.** 운영자가 일수(1 ~ 180)를 정하면 그 기간에 마지막 기사가 있는 사건을 잇기 대기에 넣는다 — 운영자 API 하나, 화면 없음. 사건 묶기 채우기와 같은 꼴이다.

## 결과

- `storyline` → `event` 의존이 생기고, `event` 는 `storyline` 을 모른다. 알림은 이벤트 발행 레지스트리에 남아 리스너가 실패하면 다시 처리된다.
- 사건 쓰기마다(기사 하나가 붙을 때마다) 발행이 하나 생긴다. 받는 쪽 대기는 사건마다 한 행이라 같은 사건의 잦은 변화는 한 행으로 모인다. 양 · 처리량은 재지 않았다.
- 저장소 구현이 이벤트를 발행한다 — 발행은 이벤트 버스로의 연결이고 계약은 포트의 Javadoc 과 event Spec 의 규칙이 갖는다. 사건 행을 쓰는 SQL 이 저장소 구현 밖에 생기지 않는지는 잔존 검사가 지킨다.
- 상한에 이르러 뺀 사건은 운영자가 채우기로 다시 넣어야 한다.
- 채우기로 만든 결과는 같은 기간을 실시간으로 이어 온 결과와 다를 수 있다 — 판정 때 그 사건보다 뒤의 사건도 창 안에 있다.
- 스토리라인 ID 가 사라질 수 있다 — 구독이 생길 때 지운 ID 알림을 더한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| `event` 가 사건 행에 전역 변경 순번과 지운 사건 기록을 두고, `storyline` 이 커서로 "이후 바뀐 사건"을 읽는다 | 늦게 커밋한 트랜잭션의 낮은 순번을 커서가 건너뛴다 — 막으려면 커밋 가시성을 다루는 장치가 더 든다. 지운 기록 테이블과 그 보존이 새로 생긴다 |
| `storyline` 이 주기적으로 최근 사건과 자기 소속의 사건을 훑는다 | 소속이 쌓일수록 훑는 양이 늘고, 창 밖의 변화(오래된 사건의 지워짐)를 놓치거나 전체를 훑어야 한다 |
| 회차마다 발행한다 | 호출 지점이 아홉이고, 갈래가 늘 때 빠뜨릴 수 있다 |
| 알림에 무엇이 일어났는지(열림 · 합쳐짐 · 지워짐)를 실어 받는 쪽이 차례로 적용한다 | 알림의 순서에 기대게 된다 — 비동기 리스너 · 재처리는 순서를 지키지 않는다 |
| 대기는 "이미 있으면 그대로" | 처리 중에 다시 온 알림이 사라져 마지막 변화가 반영되지 않는다 |
| 판정이 예외를 내면 회차를 멈춘다 | 시각 순 점유라 같은 사건이 매 회차 앞자리에서 실패해 뒤 사건이 영영 처리되지 않는다 |
| 실패한 사건을 빼지 않고 매 회차 다시 시도한다 | 고칠 때까지 같은 오류 로그가 1분마다 쌓이고 묶음 한 칸을 계속 쓴다. 다시 넣는 길(채우기)이 있다 |
| 빈 스토리라인을 소속 0 인 행으로 남긴다 | 표현을 정의할 수 없는 행을 모든 경로가 다뤄야 한다 |
| 대표를 스토리라인 중심에 가장 가까운 사건으로 한다 | 갈래가 여럿인 흐름에서는 중심이 갈래 사이에 놓여 가장 일반적인 사건이 뽑힌다 |
| 대표를 스토리라인을 연 사건으로 고정한다 | 처음 사건이 흐름의 곁가지일 수 있고, 그 사건이 합쳐지거나 지워지면 다시 골라야 한다 |
| 스토리라인이 대표 기사 ID 를 저장한다 | 기사 삭제를 따로 받아야 하고, `event` 의 리스너와 같은 이벤트를 순서 없이 받아 둘 사이의 순서를 기댈 수 없다 |
| 켜기 전 사건을 기동 때 자동으로 채운다 | "판정한 적 있는 사건" 기록이 새로 들고, 운영자가 고르지 않은 양을 배포하자마자 처리한다. 마이그레이션으로 한 번 넣으면 `event` 의 테이블을 직접 읽어 모듈 경계를 넘고 다시 채울 수 없다 |
| 채우지 않는다 | 켜기 전에 닫힌 사건이 영영 스토리라인에 들지 않고, 평가 세트 기간이 비어 잇는 방법을 견줄 수 없다 |
