# ADR-0230: 일정 다이제스트는 생성 시각이 지난 뒤 만들고, 기간은 직전 READY · EMPTY 의 끝부터 생성 시각까지다

## 맥락

- 후보는 첫 평가 시각으로 기간에 든다. 선별은 부른 시각까지 커밋된 평가를 읽으므로, 기간 끝이 선별 시각보다 뒤면 그 사이에 첫 평가된 기사는 이번에도 다음에도 들지 않는다.
- 사용자가 정하는 시각은 화면에서 "다이제스트를 만드는 시각"이다. 생성은 공급자 호출이라 그 시각 뒤에 끝난다.
- 작업 서버가 멈췄다 돌아오거나, 생성 시각이 지난 뒤 키를 등록하거나, 시간대를 바꾸면 그날의 생성 시각이 이미 지나 있다.
- 시간대 · 생성 시각을 바꾸면 날짜 d 의 기간 끝이 d − 1 일 10:00 UTC(UTC+14 의 0시)에서 d + 1 일 11:59 UTC(UTC−12 의 23:59) 까지 걸쳐, 다음 날짜의 끝이 직전 끝보다 앞설 수 있다.

## 결정

- **정한 시각은 생성 시각이다** — 일정은 그 시각이 지난 뒤 행을 만들고, 기간 끝은 생성 시각이다. 선별은 언제나 그 뒤라 틈이 없다.
- **생성 시각 뒤 2시간 안에서만 따라잡는다** — 지나면 그 날짜는 만들지 않는다. 바로 받고 싶으면 수동 생성을 쓴다.
- **기간 시작은 끝난 다이제스트 가운데 READY · EMPTY 의 가장 늦은 기간 끝이다(계기 무관)** — 실패한 기간은 다음 다이제스트가 이어서 덮는다. 처음이면 끝에서 24시간, 길이는 72시간까지.
- **일정은 그 사용자의 가장 늦은 다이제스트 날짜보다 뒤의 날짜만 만들고, 기간이 비면 그 날짜를 건너뛴다** — 날짜가 거꾸로 생기지 않는다.
- **쓸 모델이 없는 사용자 · 쓰는 계정이 아닌 사용자는 일정에서 뺀다** — 쓸 모델은 `user` 가 따로 낸 조회(`DigestModelDirectory` — `ModelChoice`)로 생성 직전에도 다시 정한다. 다이제스트가 읽는 관심 설정 조회에 더하지 않는다.
- **같은 사용자 · 날짜의 일정 다이제스트는 하나다** — 사용자 잠금 안에서 날짜를 다시 확인하고, 저장소의 부분 유일 제약이 한 번 더 막는다. 생성 작업은 행을 만든 트랜잭션이 커밋된 뒤 등록하고, 작업 ID 는 행에 적은 등록 토큰이다.

## 결과

- 다이제스트는 생성 시각에 시작해 생성 시간만큼 뒤에 보인다.
- 평가 커밋의 짧은 틈(평가 시각은 커밋 직전에 찍힌다)은 남는다 — 작업 대기만큼 줄고 측정 대상이다.
- 키 없는 사용자도 생성 시각 뒤 2시간 동안은 매분 쓸 모델을 확인한다.
- 시간대를 크게 바꾼 날은 하루를 건너뛸 수 있고, 다음 날짜가 이어서 덮는다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 생성 시각 15분 전에 만들고 기간 끝은 생성 시각 | 선별이 기간 끝보다 앞서 날마다 틈이 생긴다 |
| 15분 앞에 만들고 기간 끝은 그 시각(받을 시각으로 읽기) | 화면의 "만드는 시각"과 다르다 — 리드가 생성 시각으로 정했다 |
| 그날 안이면 언제든 따라잡는다 | 생성 시각에서 많이 벗어난 시각에 일정 다이제스트가 생긴다 — 수동 생성이 그 몫이다 |
| 직전 다이제스트(상태 무관)의 끝부터 | 실패 하나로 그 기간의 소식을 잃는다 |
| 기간 상한 없음 · 24시간 | 오래 쉰 뒤 묵은 기사가 채운다 · 실패 하루를 덮지 못한다 |
| 기간이 비면 시작을 당긴다 | 앞 다이제스트와 기간이 겹쳐 같은 기사가 두 번 든다 |
