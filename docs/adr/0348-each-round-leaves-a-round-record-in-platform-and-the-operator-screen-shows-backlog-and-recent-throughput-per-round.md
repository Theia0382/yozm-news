# ADR-0348: 회차마다 시작 · 끝 · 처리 수를 platform 의 회차 기록에 남기고, 운영자 화면 처리 현황이 회차마다 밀린 수와 최근 1시간 처리량을 보인다

- 상태: 승인
- 날짜: 2026-11-26
- 근거: [이슈 #204](https://github.com/Theia0382/yozm-news/issues/204) — 운영자가 볼 수 있는 대기 건수는 태그 평가 대기뿐이었고, 처리량은 어디에도 남지 않았다(대기 행은 마치면 지워진다). 실측 인스턴스의 관계 대기 823건은 관계 판정 71건으로 비었다 — 판정 기록으로는 처리 수를 셀 수 없다. 구현 커밋 `9a0f9e0` · `1e35185` · `cdcb189` · `05e80c7` · `cdf7149` · `5a2d94a`
- 관련: [ADR-0347](0347-a-recurring-round-takes-another-batch-of-the-same-size-within-a-time-budget-while-its-queue-has-more.md)(반복 회차의 실행 모델 — 같은 이슈의 짝), [ADR-0045](0045-admin-module-serves-operator-api-over-module-public-operation-apis.md)(운영자 API 는 `admin` 이 모듈 공개 API 위에 낸다 — 그 꼴을 따른다), [ADR-0254](0254-evaluation-queue-defers-transient-failures-without-an-attempt-limit-and-counts-retrying-rows-for-the-operator.md)(평가 대기의 건수 — 평가 현황의 표시는 그대로)

## 맥락

- 다시 잇기 · 다시 묶기 · 태그 재평가 뒤 운영자는 대기가 얼마나 남았고 얼마나 빨리 줄고 있는지 알 수 없었다.
- 회차가 처리한 항목 가운데 판정 기록 · 결과 행을 남기지 않고 끝나는 것이 많다 — 잇기의 띠 밖 사건, 쌍 없는 관계 스토리라인.
- 회차 반복은 `platform` 의 회차 실행기 하나가 한다(ADR-0347). 대기 표는 각 모듈의 것이다.

## 결정

- **회차가 끝날 때마다 회차 기록 한 행을 `platform` 의 표 `round_runs` 에 남긴다** — 회차 이름 · 시작 · 끝 · 부른 뭉치 수 · 처리 수 · 끝난 까닭. 처리할 것이 없던 회차와 뭉치가 예외를 던진 회차(`FAILED`)도 남긴다. 기록 쓰기가 실패하면 오류 로그를 남기고 삼킨다 — 뭉치의 쓰기는 이미 커밋됐다.
- **회차 이름은 각 모듈이 정해 넘기는 문자열이다** — 소문자 낱말을 `-` 로 잇는다. `platform` 은 이름의 뜻을 모른다.
- **처리량은 최근 1시간 안에 끝난 회차의 처리 수 합과 회차 수다.** 기록은 2일 보존하고 하루 한 번 지운다(값은 측정 전 목표).
- **밀린 수는 각 모듈이 센다.** 모듈마다 공개 조회(`EventProcessing` · `StorylineProcessing` · `TagProcessing`)가 회차마다 남은 수 · 미룬 수(다시 볼 시각이 아직 오지 않은 것)를 한 문장으로 세고, 처리량은 회차 기록에서 붙인다. `admin` 이 셋을 이어 붙여 `GET /api/admin/processing` 으로 낸다.
- **운영자 화면 "처리 현황"(`/admin/processing`)이 회차 일곱을 한 표로 보인다** — 대기 · 미룸 · 최근 1시간 처리 · 최근 1시간 회차 · 마지막 회차(끝난 시각 · 까닭). 화면을 연 동안 30초마다 다시 읽고, 같은 일의 비용은 같고 시간당 지출이 커진다는 안내를 단다.

## 결과

- 다시 묶기 하나가 사건 회차 넷과 흐름 회차 둘을 차례로 밀어내는 진행을 한 화면에서 따라간다.
- 회차 기록은 하루 약 1만 행(회차 일곱 × 1분 실행)이고 2일치를 둔다.
- 비울 때까지 걸릴 시간은 보이지 않는다 — 운영자가 밀린 수와 처리량으로 가늠한다.
- 평가 현황 화면의 평가 대기 건수(거부 · 일시 실패 칸)는 그대로이고, 남은 수는 처리 현황과 같은 질의에서 나온다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 결과 기록(판정 원본 · 배정 행)에서 처리 수를 센다 | 판정 없이 끝난 항목을 셀 출처가 대기마다 없거나 다르다 |
| 모듈마다 회차 기록 표를 둔다 | 같은 구조 · 지우기가 셋이 된다 |
| 운영자 API 만 둔다 | 평가 대기 건수는 이미 화면에 있어, 같은 성격의 다른 대기만 API 에 두면 운영자가 볼 곳이 갈린다 |
| 수집 현황 화면에 절을 더하거나 평가 현황 · 사건 · 사건 흐름 화면에 나눠 넣는다 | 이어지는 회차의 진행을 보려면 화면을 옮겨 다닌다. 수집 현황은 피드 상태 표라 성격이 다르다 |
| 비울 때까지 걸릴 시간을 계산해 보인다 | 처리 속도가 대기의 성격(띠 안 비율 등)마다 달라 틀리기 쉽다 |
| 처리할 것이 없던 회차는 기록하지 않는다 | 반복 작업이 살아 있는지(마지막 회차 시각)를 볼 수 없다 |
