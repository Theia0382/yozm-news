# ADR-0224: 로그인은 세션을 저장한 뒤 자격 행을 잠가 대조한 자격의 버전을 다시 확인하고, 세션 저장소는 세션 변경을 곧바로 저장한다

- 상태: 제안
- 날짜: 2026-11-18
- 근거: [이슈 #195](https://github.com/Theia0382/yozm-news/issues/195) — 로그인의 대조를 붙잡아 복구 재설정 · 초기 비밀번호 다시 정하기와 겹친 시험으로 옛 비밀번호의 세션이 남는 것을 재현하고, Spring Session 의 저장 시점(기본은 요청 끝)을 라이브러리 원문으로 확인해 구현
- 관련: [ADR-0126](0126-user-paths-authenticate-with-a-jdbc-session-holding-only-the-user-id-and-cookie-csrf-reading-the-account-per-request.md)(세션에는 사용자 ID 만 담는다 — 그대로), [ADR-0143](0143-operators-reset-the-initial-password-only-of-accounts-before-their-first-sign-in-and-end-their-sessions.md)(초기 비밀번호 다시 정하기가 세션을 지운다 — 그대로), [ADR-0144](0144-recovery-code-failures-are-delayed-on-the-sign-in-schedule-in-a-separate-record-and-current-password-checks-share-the-sign-in-record.md)(현재 비밀번호 확인이 로그인 실패 기록을 쓴다 — 그대로)

## 맥락

- 로그인은 제출된 이메일의 로그인 실패 기록을 잠그고, 자격 행은 잠그지 않고 읽은 해시와 대조한다. 대조(Argon2id)는 수백 ms 가 걸린다.
- 비밀번호를 바꾸는 길(비밀번호 변경 · 복구 재설정 · 초기 비밀번호 다시 정하기)은 자격 행을 잠가 새 해시로 바꾸고, 커밋 직전 마지막 단계로 그 사용자의 세션을 지운다. 세션 저장소는 부르는 쪽의 트랜잭션에 들지 않고 곧바로 커밋한다.
- 로그인의 세션은 처리기가 연 뒤 요청이 끝날 때 Spring Session 이 저장한다(기본 저장 시점). 로그인 트랜잭션이 무엇을 잠그든, 그 트랜잭션이 끝난 뒤 세션이 저장소에 들어가기까지 틈이 있다.
- 옛 해시로 대조하는 동안 복구 재설정이 커밋되면, 재설정의 세션 지우기 뒤에 로그인 세션이 저장돼 남는다. 복구 재설정은 비밀번호가 새어 나갔을 때 쓰는 길이라, 옛 비밀번호를 아는 쪽이 그 순간 로그인 중이면 재설정 뒤에도 세션을 쥔다. 초기 비밀번호 다시 정하기도 같은 순서다. 비밀번호 변경은 현재 비밀번호 확인이 같은 로그인 실패 기록을 잡아 대조와 줄을 서지만, 로그인 트랜잭션이 커밋된 뒤 세션이 저장되기까지의 틈은 같다.

## 결정

- **로그인은 대조한 자격의 버전을 결과에 싣고, 세션을 연 뒤 자격 행을 잠가 그 버전이 그대로인지 다시 확인한다.** 바뀌었거나 자격이 없으면 연 세션을 거두고(로그아웃과 같다) `REJECTED` 다. 실패 기록은 성공 때 지운 그대로다.
- **세션 저장소는 세션 변경을 요청 끝이 아니라 바뀔 때 곧바로 저장한다**(Spring Session JDBC 의 저장 시점 `immediate`). 그래서 다시 확인은 로그인 세션이 저장소에 들어간 뒤다.
- 비밀번호를 바꾸는 길은 지금처럼 자격 행을 잠근 뒤 바꾸고 마지막으로 세션을 지운다.

## 결과

- 다시 확인이 자격을 바꾸는 쪽의 잠금보다 먼저면 그쪽의 세션 지우기가 이미 저장된 로그인 세션을 지우고, 나중이면 다시 확인이 그 커밋을 기다려 바뀐 버전을 보고 세션을 거둔다. 어느 순서에서도 비밀번호가 바뀐 뒤에 옛 비밀번호의 세션이 남지 않는다 — 복구 재설정 · 초기 비밀번호 다시 정하기 · 비밀번호 변경이 모두 같다.
- 응답은 그대로 셋(`SIGNED_IN` · `REJECTED` · `WAIT`)이다. 다시 확인은 대조에 성공한 시도에만 돌아, 계정 유무와 무관한 같은 응답 · 같은 계산을 바꾸지 않는다. 겹친 로그인의 `REJECTED` 본문은 틀린 비밀번호와 같다.
- 로그인 성공 한 번에 짧은 트랜잭션 하나(자격 행 잠금 · 읽기)가 는다.
- 세션 쓰기가 요청 안의 바뀌는 자리마다 일어난다 — 로그인은 세션을 만들 때 · 보안 문맥을 넣을 때 · 수명을 정할 때 따로 쓰고, 그 밖의 요청은 마지막 접근 시각을 요청 끝이 아니라 세션을 읽을 때 쓴다. 로그인 밖의 요청은 쓰기 수가 같다.
- 요청이 세션을 처음 읽을 때 곧바로 저장하면서 사용자 이름 색인을 다시 계산한다. 보안 문맥을 읽지 못하는 세션(배포로 직렬화 형식이 바뀐 세션)은 그 계산이 실패하므로, 색인 해석기가 빈 색인으로 저장하고 같은 요청이 그 세션을 지운다.
- 세션 저장 시점을 요청 끝으로 되돌리면 다시 확인이 저장 전 세션을 보고 틈이 돌아온다 — 다시 확인 직후 재설정을 끝내는 시험이 그 순서를 지킨다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 비밀번호를 바꾸는 모든 길이 그 계정 이메일의 로그인 실패 기록을 함께 잡는다 | 로그인의 잠금은 로그인 트랜잭션이 커밋되면 풀리고 세션은 그 뒤 요청 끝에 저장된다 — 줄을 서도 세션 지우기가 아직 저장되지 않은 세션을 놓친다 |
| 로그인이 자격 행을 공유 잠금으로 읽고, 세션을 저장할 때까지 그 트랜잭션을 늘인다 | 세션 저장소는 자기 트랜잭션(다른 연결)으로 쓰므로 로그인 하나가 연결 둘을 쥔다 — 동시 로그인이 많으면 연결 풀이 바닥나 서로 기다린다. 세션도 곧바로 저장해야 하는 것은 같다 |
| 세션에 자격 버전을 담고 요청마다 계정 조회에서 대조한다 | 세션에 담는 앱 값이 사용자 ID 하나라는 결정([ADR-0126](0126-user-paths-authenticate-with-a-jdbc-session-holding-only-the-user-id-and-cookie-csrf-reading-the-account-per-request.md))을 바꾸고, 직렬화 형식이 바뀌어 배포 때 모든 세션이 끊긴다. 비밀번호 변경이 남기는 지금 세션의 값도 고쳐야 하고, 옛 세션 행은 다음 요청까지 남는다 |
| 세션의 만든 시각과 자격의 바꾼 시각을 비교한다 | 겹친 로그인의 세션은 재설정이 커밋된 뒤에 만들어져 바꾼 시각보다 늦다 — 가르지 못한다 |
| 로그인 요청의 세션만 처리기 안에서 저장한다 | Spring Session 이 요청의 세션 객체와 저장을 감싸 두어 처리기에서 부를 공개 수단이 없다. 응답을 먼저 내보내면 저장되지만, 그때는 응답 본문 · 머리를 아직 정하지 않았다 |
