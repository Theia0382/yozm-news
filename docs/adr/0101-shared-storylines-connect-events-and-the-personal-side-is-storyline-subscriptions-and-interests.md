# ADR-0101: 사건을 잇는 흐름은 모든 사용자가 공유하는 스토리라인이 맡고, 개인 쪽은 스토리라인 구독과 관심사로 나눈다

- 상태: 승인
- 날짜: 2026-11-09
- 근거: [이슈 #116](https://github.com/Theia0382/yozm-news/issues/116) — 라벨 기준 2판 검토(#100)에서 리드가 정한 층과 이름을 바탕으로, 스토리라인의 소속 · 관계 · 행사 · 개인 쪽 모듈 배치를 리드와 정함
- 관련: [ADR-0025](0025-long-term-personal-news-history-in-v1.md)(세 층 가운데 이슈 항목 · 다이제스트 입출력의 이슈 문장 · 모듈 항목, 변화 리포트 입력의 이슈 변화, 결과의 이슈 세 항목, 검토한 대안의 이름 행 — 부분 대체), [ADR-0026](0026-event-clustering-with-local-embeddings-and-jev.md)(결정 "그보다 긴 전개는 사용자별 이슈가 잇는다" — 부분 대체), [ADR-0028](0028-explicit-signals-and-interest-weighted-candidates.md)(관심 신호의 이슈 추적 · 해제와 그 기록 모듈 — 부분 대체), [ADR-0029](0029-indefinite-summary-retention-with-optional-deletion.md)(다이제스트 호출에 넘기는 이슈 상태 요약 — 부분 대체), [ADR-0086](0086-events-close-after-an-idle-period-since-the-last-join-or-a-maximum-period-since-opening.md)(긴 전개를 잇는 단위 — 부분 대체), [ADR-0102](0102-an-event-is-the-reports-of-one-happening-narrowed-by-the-event-membership-question-wording.md)(사건의 범위), [ADR-0103](0103-big-judgement-on-storylines-and-the-storyline-milestone-right-after-event-clustering-takes-over-big-events.md)(큰 판정의 단위와 마일스톤)

## 맥락

- [ADR-0025](0025-long-term-personal-news-history-in-v1.md)는 공유 사건 위에 사용자별 이슈(`storyline`)를 두었다. 이슈는 다이제스트를 만드는 사용자 LLM 호출이 그 사용자의 진행 중 이슈 목록을 받아 열거나 잇는다(BYOK).
- 라벨 기준 2판은 정답 사건을 한 번 일어난 일로 좁혔고([ADR-0097](0097-event-clustering-evaluation-labels-reports-of-one-happening-narrower-than-the-system-event.md)), 시스템의 사건도 같은 범위로 좁힌다([ADR-0102](0102-an-event-is-the-reports-of-one-happening-narrowed-by-the-event-membership-question-wording.md)). 그러면 선거 하나 · 법안 하나처럼 갈래가 많은 일은 사건 여럿이 되고, 그 갈래를 잇는 일은 사건보다 큰 단위가 맡아야 한다.
- 사용자별 이슈는 그 사용자의 다이제스트에 들어온 기사로만 이어지고, 사용자마다 다르다. 갈래 전체의 보도량이나 "구독과 무관하게 알릴 만한 흐름"을 사용자 사이에 공유해 판정할 수 없다. 한 사용자의 LLM 출력으로 공유 단위를 만들면 다른 사람의 키로 만든 결과를 공유하는 문제([ADR-0003](0003-byok-personalized-digest.md))가 생긴다.
- "이슈"는 GitHub 이슈와 이름이 겹쳐 개발 대화와 문서에서 헷갈린다.
- `storyline` · `digest` · `user` · `report` 모듈은 아직 코드가 없다.

## 결정

- **층은 기사 → 사건 → 스토리라인이다.** 사건(`event`)은 한 번 일어난 일을 다룬 보도들이다([ADR-0102](0102-an-event-is-the-reports-of-one-happening-narrowed-by-the-event-membership-question-wording.md)). 스토리라인(`storyline`)은 사건들이 이어진 흐름이다 — 같은 큰 일의 여러 갈래와, 시간이 지나 생긴 후속을 함께 담는다.
- **스토리라인은 모든 사용자가 공유한다.** 사용자를 모르고, 생성형 LLM 없이 잇고, 비용은 운영자가 낸다. 다이제스트를 만드는 사용자 LLM 은 스토리라인을 열거나 잇지 않는다.
- **사건은 스토리라인 여럿에 들 수 있다(0개 이상).** 주 소속을 둘지, 여러 스토리라인의 합계에서 같은 사건을 어떻게 한 번만 셀지, 겹치는 묶음의 평가 지표, 소속을 정하는 방법은 스토리라인을 구현할 때 정한다.
- **스토리라인 사이에는 관계가 있다.** 종류는 둘이다 — 포함(큰 흐름과 그 갈래)과 이어짐 · 인과(앞 흐름이 뒤 흐름을 낳음). 관계를 소속에서 끌어낼지 명시 고리로 둘지, 판정 방법, 데이터는 스토리라인을 구현할 때 정한다.
- **행사(포럼 · 박람회)는 스토리라인이다.** 강연 · 발표 · 행사 자체를 다룬 보도는 각각 사건이고 그 행사의 스토리라인에 든다. 발표 사건은 그 내용의 흐름에도 들 수 있다.
- **주제는 스토리라인 층 밖이다.** 주제(태그)는 기사의 분류이고, 흐름이 아니다.
- **개인 쪽은 스토리라인 구독과 관심사 둘이다.** 스토리라인 구독(사용자와 스토리라인의 관계와 그 변경 이력)은 주제 구독과 같은 자리인 `user` 에 둔다. 사용자마다 달라지는 스토리라인 정보(그 사용자가 받은 소식 등 — 둘지는 다이제스트 설계)와 관심사(관심도 · 관심사 히스토리)는 `digest` 에 둔다. 관심사를 개체로 세울지는 관심도를 설계할 때 정한다.
- **이름은 개발 이름과 코드가 같다** — 사건은 `event`, 스토리라인은 `storyline`. "이슈"는 개발 이름으로 쓰지 않는다. 화면 문구는 화면을 만들 때 따로 정한다. 사건 단위의 구독은 두지 않는다 — 개인이 따라가는 단위는 스토리라인이다.
- **모듈 `storyline` 은 공유 스토리라인이 이어받는다.** 지금 설계의 사용자별 일(추적 · 해제 · 상태 전이)은 스토리라인 구독(`user`)과 `digest` 로 옮긴다. 공유 스토리라인의 책임 · 계약은 구현할 때 정한다.

## 결과

- [ADR-0025](0025-long-term-personal-news-history-in-v1.md)가 사건만 두는 대안을 기각한 이유("임베딩 기반 묶음은 몇 주에 걸쳐 내용이 바뀌어 가는 전개를 잘 잇지 못한다")는 스토리라인을 잇는 방법이 풀어야 할 요구다. 그 방법은 아직 설계되지 않았다.
- 다이제스트 호출의 입력에 사용자별 이슈 목록이, 출력에 이슈 연결이 들지 않는다. 다이제스트가 스토리라인을 어떻게 쓰는지는 다이제스트를 설계할 때 정한다.
- 스토리라인이 사건을 한 번만 센다는 보장이 소속 하나에서 오지 않는다. 보도량 · 큰 판정 · 리포트의 합계 규칙을 따로 정해야 한다.
- 관심 신호의 스토리라인 쪽 신호는 구독 변경이고, `user` 가 기록한다.
- 스토리라인의 코드가 생길 때까지 개요 · 설계 문서의 `storyline` 계약은 미설계로 표시된다.
- 큰 판정의 단위와 마일스톤 순서는 [ADR-0103](0103-big-judgement-on-storylines-and-the-storyline-milestone-right-after-event-clustering-takes-over-big-events.md)이 정한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 사용자별 이슈(다이제스트 LLM 이 열고 잇는다)를 유지한다 | 갈래 전체의 보도량과 큰 판정을 사용자 사이에 공유할 수 없고, 그 사용자의 다이제스트에 들어온 기사로만 이어진다 |
| 사건은 스토리라인 하나에만 든다 | 여러 흐름에 걸친 사건(예: 공장 방문에서 낸 지원책 발표 — 산업 정책 · 순방)을 하나만 골라야 하고, 다른 흐름을 구독한 사람이 그 사건을 놓친다 |
| 주 스토리라인 하나와 보조 소속을 둔다 | 주 · 보조를 가르는 기준이 하나 더 생긴다. 구현할 때 소속 여럿 위에서 고를 수 있다 |
| 스토리라인 사이에 관계를 두지 않는다(평평한 한 층) | 큰 흐름과 그 갈래, 앞뒤로 이어진 흐름의 방향을 담을 자리가 없다 |
| 포함을 상위 스토리라인(깊이 2)으로 지금 정한다 | 관계를 나타내는 방법과 판정 근거가 아직 없다 — 스토리라인을 구현할 때 정한다 |
| 행사는 스토리라인으로 묶지 않고 주제로만 모은다 | 행사 자체 보도(개막 · 현장)가 갈 곳이 애매하고, 같은 행사 소식이 흩어진다 |
| `storyline` 이 공유 층과 사용자별 구독까지 갖는다 | 공유 층이 사용자를 알게 된다 — 사건(`event`)과 같은 "사용자를 모른다" 경계를 잃는다 |
| 새 모듈(예: `subscription`)이 스토리라인 구독과 사용자별 정보를 갖는다 | 주제 구독은 `user` 에 남아 구독이 두 모듈로 갈리고, 모듈이 늘어난다 |
| 공유 층의 이름을 "이슈"(`issue`)로 둔다 | GitHub 이슈와 겹친다 |
