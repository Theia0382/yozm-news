# ADR-0196: 피드백은 그 사용자의 다이제스트가 인용한 기사에만 받고, 그 확인은 `feedback` 이 선언한 인터페이스를 `digest` 가 구현해 답한다

- 상태: 승인
- 날짜: 2026-11-17
- 근거: [이슈 #183](https://github.com/Theia0382/yozm-news/issues/183) — 기점 `156d2a5` 의 모듈 의존 선언(`digest` 의 허용 의존 · 개요 문서의 의존 문단)과 `digest` 의 인용 저장 꼴을 대조하고, 피드백을 받을 범위를 리드와 정함
- 관련: [ADR-0157](0157-credential-depends-on-llm-and-stored-keys-reach-llm-through-a-supply-interface-that-llm-declares-and-credential-implements.md)(같은 꼴 — 필요한 쪽이 선언하고 지식을 가진 쪽이 구현하는 공급 인터페이스), [ADR-0013](0013-architecture-patterns.md)(포트는 외부 의존성에만 — 이 인터페이스는 포트가 아니다), [ADR-0028](0028-explicit-signals-and-interest-weighted-candidates.md)(`digest` 가 `feedback` 을 읽는 방향), [ADR-0193](0193-the-per-user-storyline-information-is-the-received-news-counted-from-the-digest-shown-for-each-date.md)(받은 소식 — 날짜별로 보이는 다이제스트로 세는 다른 정의)

## 맥락

- 관심도는 좋아요 · 싫어요를 노출 수(다이제스트가 인용한 기사)로 나눈 값이다. 노출되지 않은 기사의 신호를 받으면 나눌 노출이 없는 신호가 섞인다.
- 피드백에는 어느 다이제스트에서 눌렀는지를 남긴다. 그 다이제스트 ID 는 화면이 요청에 실어 보내는 값이라, 확인하지 않으면 다른 사용자의 다이제스트나 없는 ID 가 저장된다. 선정 이유는 인용 행에만 있어, 맞지 않는 (다이제스트, 기사) 쌍은 선정 이유별 반응을 잴 때 빠지거나 틀린 이유에 붙는다.
- 어떤 다이제스트가 어떤 기사를 인용했는지는 `digest` 만 안다. 그런데 `digest` 는 후보에서 싫어요 기사를 빼고 관심도를 계산하려고 `feedback` 을 읽는다. `feedback` 이 `digest` 의 공개 조회를 부르면 두 모듈이 서로 의존하고, 모듈 검증이 순환을 실패로 판정한다.

## 결정

- **피드백은 그 사용자의 다이제스트가 인용한 기사에만 받는다.** 요청은 누른 다이제스트의 ID 를 싣고, 그 다이제스트가 요청한 사용자의 것이며 그 기사를 인용할 때만 기록한다. 받을 수 없는 요청은 아무것도 쓰지 않는다.
- **그 다이제스트가 날짜별로 보이는 다이제스트인지는 묻지 않는다.** 화면을 열어 둔 사이 같은 날짜의 다이제스트가 다시 만들어져도, 열어 둔 화면에서 누른 것을 받는다.
- **없음으로 되돌리는 요청도 같은 확인을 지나고, 되돌리기를 누른 다이제스트를 이력에 남긴다.**
- **인용했는지는 `feedback` 이 선언한 인터페이스(`DigestCitations`)로 묻고 `digest` 가 구현한다.** `feedback` 은 `digest` 의 타입을 쓰지 않고 다이제스트를 ID 로만 든다. 의존은 `digest` → `feedback` 하나다.
- **그 인터페이스는 좁히지 않은 공개 타입이다.** 답이 참 · 거짓 하나라 명명 인터페이스와 경계 시험으로 지킬 것이 없다.

## 결과

- 노출과 반응이 같은 기사 집합에 놓인다.
- 받을 수 있는 기사의 판정이 `feedback` 한 곳에 있다 — 기록을 부르는 길이 늘어도 판정을 지난다.
- 다이제스트 밖의 화면(스토리라인 타임라인 등)에서는 피드백을 남길 수 없다. 그 기능을 넣으려면 인용 확인의 질문을 넓히는 결정이 필요하다.
- 화면의 현재 상태 조회는 다이제스트 ID 가 아니라 기사 ID 묶음으로 받는다 — 다이제스트의 기사 목록은 `digest` 의 지식이다.
- 덮인 다이제스트에서 온 신호를 관심도가 셀지는 노출 수의 정의와 함께 관심도를 구현하는 작업이 정한다.
- 한 다이제스트가 같은 기사를 여러 번 인용할 수 있어 (다이제스트, 기사)가 인용 행 하나로 정해지지 않는 경우가 있다 — 그때 선정 이유를 세는 방법은 측정하는 쪽이 정한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 제한하지 않는다 — 있는 기사면 받는다 | 노출되지 않은 기사의 신호가 섞이고, 다이제스트 ID 를 믿을 수 없다 |
| `feedback` 이 `digest` 의 공개 조회를 부른다 | `digest` 가 `feedback` 을 읽으므로 순환이다 |
| 쓰기 처리기를 `reader` 에 두고 처리기가 확인한 뒤 `feedback` 의 쓰기 API 를 부른다 | 받을 수 있는 기사의 규칙이 `adapter` 에 놓이고, `reader` 가 판정 · 저장을 하지 않는다는 경계에서 벗어난다. 쓰기 API 를 다른 길이 부르면 제한이 빠진다 |
| 의존을 `feedback` → `digest` 로 뒤집고, `digest` 가 읽을 신호를 `digest` 가 선언한 인터페이스로 받는다 | 관심 신호의 소비자가 읽는 공개 조회를 `feedback` 이 낸다는 방향을 함께 뒤집어야 한다 |
| 날짜별로 보이는 다이제스트의 인용에만 받는다 | 열어 둔 화면에서 누른 것이 그 사이의 재생성 때문에 거부된다 |
