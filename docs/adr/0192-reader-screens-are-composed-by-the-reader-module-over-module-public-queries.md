# ADR-0192: 독자 화면의 응답은 `reader` 모듈이 각 모듈의 공개 조회를 엮어 내고, 뉴스 내용을 보이는 사용자 화면은 모두 `reader` 가 맡는다

- 상태: 승인
- 날짜: 2026-11-16
- 근거: [이슈 #180](https://github.com/Theia0382/yozm-news/issues/180) — 기점 `0a8b984` 의 모듈 경계(`storyline` · `digest` · `user` 의 Spec 과 의존 선언, `admin` 의 엮기)를 대조하고, 화면용 API 를 맡을 모듈을 정함
- 관련: [ADR-0013](0013-architecture-patterns.md)(부분 대체 — 결정 "별도 `web` 모듈은 두지 않는다"), [ADR-0045](0045-admin-module-serves-operator-api-over-module-public-operation-apis.md)(보충 — 같은 꼴을 사용자 화면에 둔다), [ADR-0101](0101-shared-storylines-connect-events-and-the-personal-side-is-storyline-subscriptions-and-interests.md)(검토한 대안의 새 모듈 기각과의 관계), [ADR-0068](0068-rss-summaries-shown-only-on-operator-screens-and-users-get-processed-information.md)(사용자 화면의 노출 범위)

## 맥락

- 사용자 스토리라인 화면은 `storyline` 의 공개 조회(목록 · 타임라인 · 관계)에 대표 기사(`event`)와 기사 정보(`article` · `source`)를 엮고, 그 사용자가 받은 소식(`digest`)을 더해야 한다.
- 스토리라인에는 제목이 없다 — 대표 사건의 대표 기사 제목으로 알아본다. `storyline` 은 사건 ID 만 저장하고, 기사는 ID 를 받아 넘기기만 한다(storyline Spec §1 · §4).
- 받은 소식은 `digest` 의 노출 기록이 재료다. `digest` 는 다이제스트를 만들고 저장하는 모듈이고 공유 스토리라인 목록의 지식이 없다.
- `user` 는 이미 `storyline` · `event` · `article` · `source` 에 의존하지만, 계획된 의존이 `digest` → `user` 라 `user` 가 `digest` 를 읽으면 순환이다. `user` Spec 은 스토리라인의 표시 정보를 내지 않는다고 적었다.
- 뉴스 내용을 보이는 사용자 화면(스토리라인 · 다이제스트 · 관심사 히스토리 · 변화 리포트)은 거의 모두 기사 정보(제목 · 출처 · 발행 시각 · 원문 링크)를 엮는다. 운영자 화면은 같은 문제를 `admin`(ADR-0045)으로 풀었다 — 모듈은 공개 API 만 내고 응답 모양과 기사 엮기는 `admin` 한 곳이 정한다.
- ADR-0013 은 "컨트롤러는 각 모듈 안에 둔다. 별도 `web` 모듈은 두지 않는다"로 정하고, "컨트롤러를 별도 `web` 모듈에 모음"을 "`web` 이 모든 모듈을 알아야 하고, 각 모듈이 내부 서비스를 공개해야 해서 경계가 약해진다"로 기각했다. ADR-0045 의 `admin` 은 운영자 화면에서 이미 이 꼴의 예외였지만 ADR-0013 에 그렇게 적지 않았다.

## 결정

- **새 모듈 `reader` 가 독자 화면의 HTTP API 를 낸다.** `reader` 는 공개 타입 · 데이터 · 테이블 · 판정이 없고, 각 모듈의 공개 조회를 엮어 응답 모양을 정한다. 코드는 `adapter/in/web` 하나이고 처리기는 트랜잭션을 열지 않는다 — `admin`(ADR-0045)과 같은 꼴이다. `admin` 과 다른 점은 처리기가 세션 사용자를 받고 키 관문 뒤에 있으며 사용자 격리 시험에 등록된다는 것이다.
- **경계: 뉴스 내용(기사 · 사건 · 스토리라인 · 다이제스트 · 변화 리포트 · 관심사 히스토리)을 보이는 사용자 화면의 응답은 `reader` 가 각 모듈의 공개 조회를 엮어 정한다. 사용자가 정해 두는 것(계정 · 키 · 관심 설정 · 구독 · 알림)의 화면은 그 데이터를 가진 모듈이 연다.**
- **각 모듈은 자기 지식만 공개 조회로 낸다.** 판단(예: 받은 소식의 뜻)은 그 모듈의 `domain` 에 남고, `reader` 는 맞붙이기만 한다. 어느 모듈도 `reader` 를 모른다.
- **사용자 화면의 기사 정보는 제목 · 출처 · 발행 시각 · 원문 링크다** — RSS 요약문 · 섹션 · 카테고리를 싣지 않는다(ADR-0068).

## 결과

- ADR-0013 이 기각한 이유 둘에 이렇게 답한다 — ① 여러 모듈을 아는 것은 엮는 모듈 `reader` 하나이고, 그 범위를 위 경계 문장이 정한다 ② 각 모듈은 내부 서비스가 아니라 Spec 이 선언한 공개 조회만 연다(Spring Modulith 가 하위 패키지 접근을 막는다).
- 다이제스트 화면 · 관심사 히스토리 · 변화 리포트 열람의 처리기도 `reader` 가 내고, `digest` · `report` 는 화면이 쓸 공개 조회를 연다. 다이제스트 화면의 기사 엮기가 `reader` 한 곳에 있다.
- 공유 내용만 내는 처리기(사용자 데이터 없음)도 세션 · 키가 필요해 사용자 격리 시험에 등록한다 — 두 사용자가 같은 응답을 받고 세션 없이 401 인지를 본다.
- 운영자 화면(`admin`)과 독자 화면(`reader`)이 같은 재료를 따로 엮는다 — 보이는 칸이 다르다(ADR-0068). 같은 규칙이 생기면 그 지식을 가진 모듈의 공개 조회로 올린다.
- ADR-0101 이 기각한 "새 모듈(예: `subscription`)이 스토리라인 구독과 사용자별 정보를 갖는다"는 구독 · 사용자별 정보를 소유하는 모듈이다. `reader` 는 아무것도 소유하지 않아 그 기각과 다른 대안이다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| `digest` 가 스토리라인 화면 처리기를 연다 | 기간의 스토리라인 목록 · 표시 정보 처리기에 `digest` 의 지식(다이제스트 · 노출 기록)이 없다 — 엉뚱한 모듈의 책임이 된다 |
| `storyline` 이 공유 처리기를, `digest` 가 받은 소식 처리기를 연다 | `storyline` 이 기사를 읽게 되어 "`article` 은 기사 ID 타입(`ArticleId`)만 쓴다 — 받아서 넘긴다"(storyline Spec §4 나가는 쪽) 경계가 바뀐다. 기사 엮기가 `storyline` 과 `digest`(다이제스트 화면) 두 곳에 생기고, 화면이 두 응답을 맞붙인다 |
| `user` 가 공유 처리기를 연다 | 받은 소식을 읽으면 `digest` → `user` 계획 의존과 순환이다 — 결국 공유와 개인이 두 모듈로 갈린다. `user` 의 "표시 정보를 내지 않는다" 경계도 바뀐다 |
| 이 이슈의 스토리라인 화면만 `reader` 에 두고 다른 뉴스 화면의 소속은 그때 정한다 | 다이제스트 화면을 `digest` 에 두면 기사 엮기가 한 벌 더 생긴다(`digest` 는 `reader` 를 쓸 수 없다) — `reader` 를 둔 이유가 성립하지 않는다 |
