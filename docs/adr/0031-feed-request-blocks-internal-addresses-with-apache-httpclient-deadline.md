# ADR-0031: 피드 요청은 내부 주소를 기본으로 막고, Apache HttpClient 로 한 번의 수집 전체에 마감 · 크기 상한을 건다

- 상태: 승인
- 날짜: 2026-10-28
- 근거: [이슈 #19](https://github.com/Theia0382/yozm-news/issues/19) — JDK 25 `HttpClient` · Apache HttpClient 5.6.5 · Jetty client 12.1.14 를 실행해 확인. 구현 `f94c1c8`(판단 규칙) · `f0006ad`(수집 구현) · `9d53e21`(설정 · 배포)
- 관련: [ADR-0001](0001-news-source-rss.md)(공급원은 `ArticleSource` 뒤 — 이 ADR 이 이행한다), [ADR-0004](0004-tech-stack.md)(스택에 HTTP 클라이언트를 더한다), [ADR-0012](0012-swappable-external-dependencies.md)(외부 의존성 · 로컬 대체물), [ADR-0021](0021-separate-deploy-compose-with-single-app-service.md)(배포 필수 값은 `${VAR:?}`), [ADR-0030](0030-feed-xml-own-parser-and-rome-for-format-title-link.md)(받은 문서의 해석)

## 맥락

- 피드 URL 은 운영자 프로필(운영자 권한)이나 프리셋(저장소)에 있고, 피드 서버는 리다이렉트로 요청을 아무 곳으로나 보낼 수 있다. 운영자 계정을 빼앗기거나 피드가 리다이렉트하면 서버가 자기 내부(클라우드 메타데이터 `169.254.169.254`, 같은 호스트 · Compose 망의 서비스)를 향해 요청하게 된다. 한편 셀프 호스팅 운영자는 같은 망에 둔 RSS 생성기를 피드로 받을 수 있다.
- 이름을 검사한 뒤 다시 해석해 연결하면, 그 사이에 이름이 내부 주소로 바뀔 수 있다(DNS rebinding). 막으려면 **실제로 연결하는 주소**를 검사해야 한다.
- 측정한 클라이언트별 성질:
  - JDK `HttpClient`: 요청 타임아웃이 응답 헤더까지만 걸린다 — 본문을 0.5초 간격으로 흘리는 5초 응답이 `timeout(2s)` 에서 끝까지 받아진다. 이름 해석 지점을 클라이언트 단위로 바꿀 수 없다(JVM 전역 SPI 만 있다). IP 로 접속하며 `Host` 를 붙이는 우회는 제한 헤더라 막힌다.
  - Apache HttpClient 5.6.5: 연결 관리자의 이름 해석기를 IP 리터럴까지 거친다. 타임아웃은 본문을 묶지 못하지만, 요청을 `cancel()` 하면 본문을 읽는 중에도 바로 끊긴다. 기본값은 압축 요청 · 리다이렉트 50회 · 풀 대기 3분 · 경로당 연결 5 · 재시도(429 · 503 은 `Retry-After` 를 따른다)이고, 처리기가 끝나면 남은 본문을 끝까지 읽는다.
  - Jetty client 12.1.14: 이름 해석기를 클라이언트 단위로 꽂고, 요청 타임아웃이 본문 · 리다이렉트 체인 · 풀 대기를 묶으며, 푼 바이트 기준 크기 상한을 내장한다. 그러나 자동 리다이렉트 중의 301 은 요청 리스너에 보이지 않는다.
- 피드 운영자(언론사)가 요청 주체를 알아보고 연락할 수 있어야 한다. 셀프 호스팅마다 운영 주체가 다르다.

## 결정

### 내부 주소

- **기본으로 막는다.** 루프백 · 사설 · 링크 로컬 · 공유(CGNAT) · 문서용 · 벤치마크 · 멀티캐스트 · 예약 대역과 IPv6 의 같은 종류(고유 로컬 · 링크 로컬 · Teredo 등)다. IPv4 를 품은 IPv6(IPv4 호환 · NAT64 · 6to4)는 품은 IPv4 도 본다. 대역 표의 정본은 `source` 모듈의 `AddressPolicy.BLOCKED` 다.
- **운영 설정의 허용 목록(CIDR)만 연다.** 허용 목록은 서버 설정(`YOZMNEWS_COLLECTION_ALLOWED_NETWORKS`)이다 — 화면의 운영자 권한으로는 열 수 없다.
- **연결하는 주소를 검사한다.** 연결 관리자의 이름 해석기가 해석 결과를 걸러, 하나라도 막힌 주소가 있으면 그 이름 전체를 거부한다. 처음 URL 과 모든 리다이렉트 홉이 같은 검사를 지난다.
- 시스템 프록시 설정을 읽지 않는다 — 프록시를 거치면 연결 주소 검사가 무의미하다. 쿠키 · 인증 정보를 보내지 않고, userinfo 가 있는 URL 은 요청하지 않는다.

### 클라이언트

- **Apache HttpClient 5(classic)를 쓴다.** 버전은 Spring Boot 가 관리한다.
- 리다이렉트는 자동으로 따르지 않고 수집이 직접 따라가며 홉마다 판정한다. 한 번의 수집 안에서는 재시도하지 않는다 — 다음 수집은 일정이 정한다.
- 연결 풀은 전체 · 호스트당 256 의 안전 상한 하나다. 호스트별 동시 연결을 클라이언트가 제한하지 않는다 — 우리 쪽 대기가 마감을 먹어 언론사 탓이 아닌 실패가 피드에 쌓이지 않게 한다. 같은 언론사 피드의 동시 수집은 수집 일정이 피한다.

### 한 번의 수집에 거는 제한

- **마감 10초** — 풀 대기 · 연결 · 응답 · 리다이렉트 홉 · 본문을 합친 한 번의 수집 전체에 하나다. 홉마다 남은 시간으로 타임아웃을 두고, 남은 시간 뒤에 그 홉의 요청을 취소한다. 이름 해석은 취소로 끊기지 않아 OS 해석기의 시간 상한을 따른다.
- **본문 5 MiB** — 압축을 푼 바이트로 센다. 같으면 통과, 넘는 순간 멈춘다. 압축되지 않은 응답은 밝힌 길이로 먼저 거른다.
- **gzip · deflate 를 요청한다** — 피드 서버의 부담을 줄인다. 상한을 푼 바이트로 세므로 압축 폭탄도 5 MiB 에서 멈춘다.
- **리다이렉트 5회** — 홉마다 대상을 현재 주소 기준으로 풀고(RFC 3986), 요청할 수 있는 주소(http · https · 호스트 · 유효한 포트 · userinfo 없음)인지 보고, 연결 주소를 검사한다. https → http 로 내려가는 홉도 따라간다 — 보내는 비밀 값이 없고 본문은 원래 신뢰하지 않는 입력이다.
- 본문을 끝까지 읽지 않는 응답(리다이렉트 · 실패 상태 · 상한 초과)은 연결을 버린다 — 그대로 두면 클라이언트가 남은 본문을 끝까지 읽어 긴 본문이 마감까지 붙잡는다. 본문이 없는 304 의 연결은 풀로 돌아간다.

### 연락처

- `User-Agent` 는 `YozmNews (+https://github.com/Theia0382/yozm-news; {연락처})` 다. 연락처(`YOZMNEWS_COLLECTION_CONTACT`)는 이메일 주소나 http · https URL 이고, **없거나 형식이 틀리면 앱이 뜨지 않는다.**

### 결과의 모양

- 결과는 성공(정규화 결과) · 변경 없음(304) · 실패 셋이다. 입출력 실패는 예외가 아니라 결과다.
- 영구 이동(301 · 308)을 처음 URL 에서 끊기지 않고 거쳤으면 마지막 주소를 성공 · 변경 없음 결과에 싣는다 — 프리셋 · 운영자 프로필을 고칠 단서다. 대부분의 수집은 304 라서 변경 없음에도 싣는다.
- 실패는 일시 · 영구로 나눈다. 영구는 "사람(언론사 · 운영자 · 개발팀)이 무언가를 바꾸기 전에는 다시 보내도 같은 결과가 날 것으로 보는 실패"다. 401 · 403 · 404 · 410 · 그 밖의 4xx · 예상 밖 상태 · 리다이렉트 오류 · 요청할 수 없는 주소 · 막힌 주소 · TLS 오류 · 크기 초과 · 정규화 불가는 영구, 마감 초과 · 연결 실패 · 이름 해석 실패 · 408 · 429 · 5xx 는 일시다. 표의 정본은 `FetchFailureReason.permanence()` 다.
- 실패 문구는 응답 본문을 옮기지 않는다. URL 을 인용할 때 userinfo 를 지운다.

### 로컬 대체물

- 피드는 계정 · 비밀 값이 없는 공개 HTTP 라 로컬 대체물을 두지 않는다([ADR-0012](0012-swappable-external-dependencies.md) 의 의존성 표에 피드 행이 없는 이유). 개발 중에도 실제 피드를 받고, 테스트는 WireMock 으로 대체한다.

## 결과

- 셀프 호스팅에서 같은 망의 피드를 받으려면 서버 설정에 대역을 연다. 연 대역만큼 보호가 준다.
- 바깥 연결이 프록시를 거쳐야만 하는 망에 둔 셀프 호스팅은 피드를 받지 못한다.
- 배포에 필수 값(`YOZMNEWS_COLLECTION_CONTACT`)이 하나 는다. 연락처는 `User-Agent` 로 모든 피드 서버에 나가므로 비밀 값을 넣지 않는다.
- 마감은 수집 코드가 직접 강제한다 — 취소 예약이 실제로 끊는지는 본문을 흘리는 응답 · 긴 실패 본문 테스트로 지킨다. Apache 판을 올릴 때 이름 해석기 · 취소 · 남은 본문 처리의 동작을 같은 테스트로 다시 확인한다.
- 한 번의 수집 안에서 재시도하지 않으므로, 서버가 이미 닫은 재사용 연결이 드물게 일시 실패 하나가 될 수 있다.
- `Retry-After` 는 결과에 싣지 않는다. 일정이 필요로 하면 실패 결과에 더한다.
- Spring Boot 의 `RestClient` 자동 구성은 classpath 에서 Apache HttpClient 를 가장 먼저 고른다. 나중에 `RestClient` 를 쓰는 모듈(예: Spring AI 로 LLM 을 부르는 `llm`)은 그 영향을 받으므로, 그 모듈을 만들 때 `spring.http.clients.imperative.factory` 로 고를지 정한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 내부 주소를 막지 않는다(운영자를 믿는다) | 운영자 계정 탈취나 피드의 리다이렉트가 곧 내부망 요청이 된다 |
| 예외 없이 항상 막는다 | 같은 망의 RSS 생성기를 쓰는 셀프 호스팅이 막힌다 |
| 요청 전에 이름을 해석해 검사한다(JDK `HttpClient`) | 연결 때 다시 해석하므로, 그 사이의 변경을 막는 근거가 JVM 이름 캐시뿐이다 |
| Jetty client | 마감 · 크기 상한이 내장이지만, 자동 리다이렉트 중의 301 이 보이지 않아 영구 이동을 기록하려면 리다이렉트 루프와 상한 리스너를 직접 써야 한다. 그러면 직접 만드는 양이 Apache 와 비슷하고 의존성은 더 많다(7개 대 3개) |
| Reactor Netty | 블로킹 작업 안에서 리액티브 스택을 `block()` 으로 쓰게 되고, Jetty 보다 얻는 것이 없다 |
| 연락처가 없으면 연락처 없이 수집한다 | 피드 운영자가 요청 주체에 닿을 수 없다 |
| 연락처가 없으면 기동하되 수집을 실패로 둔다 | 설정 문제가 피드 문제로 보이고, 피드마다 같은 실패가 쌓인다 |
| 리다이렉트를 따르지 않는다(3xx 는 영구 실패) | http → https 같은 흔한 이전에도 수집이 멈춘다 |
| 리다이렉트를 따르기만 한다 | 영구 이동이 묻혀 프리셋이 낡아도 알 수 없다 |
| 압축을 요청하지 않는다 | 피드 서버와 우리 쪽 전송량이 크다. 상한을 푼 바이트로 세면 안전성은 같다 |
| 클라이언트가 호스트당 연결을 2개로 제한한다 | 몰리면 우리 쪽 대기가 마감을 먹어 언론사 탓이 아닌 일시 실패가 피드에 쌓인다 |
