# ADR-0023: 백그라운드 작업은 JobRunr OSS 로 돌리고, 프레임워크 스키마는 라이브러리 원문을 Flyway 에 담으며, 실패한 이벤트는 반복 작업이 상한까지 다시 처리한다

- 상태: 승인
- 날짜: 2026-10-27
- 근거: [이슈 #16](https://github.com/Theia0382/yozm-news/issues/16) — 기점 `ca8479f` 의 저장소와 JobRunr 9.0.2(바이너리 · 소스 jar, Maven Central SHA-1 대조) · Spring Modulith 2.1.1(events-api · core · jdbc 소스 jar)을 읽어 확인
- 관련: [ADR-0004](0004-tech-stack.md)(백그라운드 작업 = JobRunr), [ADR-0013](0013-architecture-patterns.md)(도메인 이벤트 · 멱등 작업), [ADR-0014](0014-spring-data-jdbc.md)(스키마 정본 = Flyway)

## 맥락

- [ADR-0004](0004-tech-stack.md)는 백그라운드 작업에 JobRunr(PostgreSQL 저장소)를 고르면서 라이선스와 OSS 판의 기능 범위를 착수 때 다시 확인하기로 했다. 다시 확인한 결과는 다음과 같다(JobRunr 9.0.2 기준).
  - 라이선스는 LGPL-3.0-or-later 와 상용 라이선스의 이중 라이선스다. 이 서비스는 jar 를 수정하지 않고 의존성으로 쓰며, 배포 이미지에는 Boot 실행 jar 안의 별도 jar 로 그대로 담긴다.
  - 반복 작업과 재시도(기본 10회, 지연 `3^실패횟수` 초)는 OSS 에 있다. 같은 반복 작업의 이전 실행이 대기 · 처리 중이면 그 회차는 건너뛴다.
  - 작업 종류별 동시성 제한(뮤텍스 · rate limit)은 OSS 에 없다. OSS 에서 조절할 수 있는 것은 서버당 worker 수뿐이다.
  - 대시보드는 Spring MVC 밖의 별도 HTTP 서버(기본 포트 8000, 평문 basic 인증)이고 기본으로 꺼져 있다.
- JobRunr 는 기동 때 스스로 테이블을 만든다. 스키마 생성을 끄면(`skip-create`) 테이블 4개가 있는지만 확인하고, 적용된 마이그레이션 목록은 보지 않는다. 그래서 JobRunr 를 올릴 때 새 스크립트를 옮기지 않아도 기동은 성공한다.
- Spring Modulith 의 이벤트 발행 레지스트리 스키마 자동 생성은, 설정 키가 없으면 켜진다.
- [ADR-0013](0013-architecture-patterns.md)은 "이벤트는 레지스트리에 기록되어 재시작 후에도 처리된다"고 했다. 기본 설정의 Modulith 에는 실패하거나 멈춘 발행을 다시 처리하는 경로가 하나도 켜져 있지 않다. 재시작 때 다시 보내는 설정은 다른 인스턴스가 처리 중인 발행까지 다시 보낸다.
- Modulith 의 멈춤 감시(staleness)는 기간 하나라도 설정하면 `PUBLISHED` · `PROCESSING` · `RESUBMITTED` 세 상태를 모두 판정한다. 기간을 비운 상태는 그 상태의 발행 전부를 멈춤으로 본다. 경과는 상태가 바뀐 시각이 아니라 발행 시각으로 잰다.

## 결정

- **JobRunr OSS 를 쓴다.** `org.jobrunr:jobrunr-spring-boot-4-starter` 를 수정 없이 의존성으로 넣는다. LGPL 고지를 어디에 둘지는 이미지를 외부에 게시할 때 정한다.
- **두 라이브러리의 스키마 자동 생성을 끈다.** `jobrunr.database.skip-create: true`, `spring.modulith.events.jdbc.schema-initialization.enabled: false` 다. 스키마의 정본은 Flyway 마이그레이션이다.
- **첫 마이그레이션 `V1` 에 라이브러리 원문을 그대로 담는다.**
  - JobRunr 가 PostgreSQL 에 적용하는 스크립트 전부를 파일 이름순으로, 구획 표시 줄과 함께 손대지 않고 담는다.
  - JobRunr 가 스스로 적용했을 때와 같게 `jobrunr_migrations` 기록 행을 남긴다.
  - Modulith 레지스트리 V2 스키마 원문을 같은 파일에 담는다. 완료 기록 보관 테이블은 만들지 않는다.
- **원문 대조 테스트가 업그레이드를 지킨다.**
  - 마이그레이션 파일의 구획이 라이브러리가 지금 내놓는 스크립트 목록 · 본문과 같은지 비교한다.
  - `jobrunr_migrations` 의 기록이 그 목록과 같은지 비교한다.
  - 라이브러리를 올려 새 스크립트가 생기면 이 테스트가 실패한다. 그 원문을 Flyway 새 버전 파일에 같은 구획 규칙으로 옮긴다.
- **대시보드는 기본으로 끈다.** 익명 사용 통계도 끈다. 대시보드는 운영자 접근 통제가 생긴 뒤에 연다.
- **작업 서버는 기본 설정에서 켠다.** 기본 배포 구성은 두 역할을 함께 하는 프로세스 하나다. 역할별로 나누는 일은 역할 profile 이 맡는다. 작업 서버를 켠 프로세스는 서버가 멈추면 `/actuator/health` 가 DOWN 이다.
- **실패한 이벤트 발행은 JobRunr 반복 작업이 주기적으로 다시 처리한다.**
  - 반복 작업은 미완료 발행 전체를 읽는 공개 API(`IncompleteEventPublications`)로 `FAILED` 발행만 골라 재제출한다. 재제출은 조건부 UPDATE 를 거치므로 인스턴스가 여럿이어도 한 발행은 한 곳에서만 재제출된다.
  - 재시작 때 미완료 발행을 다시 보내는 설정은 켜지 않는다.
  - 반복 작업 자체는 재시도하지 않는다. 실패하면 다음 주기가 재시도다.
- **멈춘 발행은 Modulith 감시가 세 상태 모두 같은 기간으로 `FAILED` 로 바꾼다.**
  - 세 기간은 설정 값 하나(`yozmnews.events.stale-after`)를 가리킨다.
  - "(시도 상한 − 1) × 재제출 주기 < 멈춤 기간"을 기동 때 확인하고, 어기면 기동이 실패한다. 정상 운영에서 재처리 중인 발행이 발행 시각 기준 감시에 걸리지 않게 하는 조건이다.
- **재처리에는 상한이 있다.** 한 발행의 총 처리 시도는 최초 1회와 재제출 5회를 합해 6회다. 상한에 이른 발행은 `FAILED` 로 남고, 남아 있는 동안 반복 작업이 실행될 때마다 경고 로그 한 줄에 그 ID 들을 남긴다.
- **완료된 발행 기록은 즉시 지운다.** 결과는 각 모듈의 데이터에 남고, 조사할 실패 발행은 상한 규칙에 따라 남는다.
- **이벤트 리스너도 다시 실행해도 결과가 같아야 한다.** 재제출은 리스너를 다시 부르므로 이벤트 처리는 최소 한 번이다. [ADR-0013](0013-architecture-patterns.md)의 멱등 작업 규칙을 이벤트 리스너에도 적용한다.

## 결과

- [ADR-0013](0013-architecture-patterns.md)의 "재시작 후에도 처리된다"는 "반복 작업이 주기적으로 다시 처리하고, 상한을 넘으면 실패로 남긴다"로 바뀐다. 이벤트가 레지스트리에 기록된다는 결정은 그대로다.
- `V1` 에는 JobRunr 가 이미 지운 테이블을 만들었다 지우는 문장과 뷰를 여러 번 다시 만드는 이력이 그대로 남는다. 빈 DB 에서 한 번 실행되므로 동작 비용은 없다.
- 실패한 발행이 다시 처리되기까지 재제출 주기만큼, 멈춘 발행은 멈춤 기간 + 감시 주기 + 재제출 주기만큼 늦어진다.
- 감시는 발행 시각으로 판정하므로, 재제출이 멈춤 기간보다 늦어지는 이상 상황(작업 서버가 오래 멈췄다 돌아온 경우 등)에서는 처리 중인 발행을 멈춤으로 오판해 한 번 더 처리할 수 있다. 결과는 리스너 멱등이 지키고, 반복은 상한이 묶는다. 기동 때 확인하는 조건은 재제출 시각만 묶는다. 한 시도의 처리 시간은 담지 않으므로 리스너는 짧은 처리여야 한다.
- 상한에 이른 발행을 다시 처리하거나 지우는 수단은 아직 없다. 운영자 기능이 생길 때까지는 DB 에서 직접 다룬다.
- 작업 종류별 동시성 제한이 필요한 작업(평가 등)은 작업 설계와 worker 수로 제한한다. 방식은 그 기능을 구현할 때 정한다.
- 멈춤 감시는 Spring 스케줄링으로 모든 인스턴스에서 돈다. 역할별로 끌지는 역할 profile 을 나눌 때 정한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| JobRunr 스키마를 최종 상태 DDL 한 벌로 직접 쓴다 | 손으로 합친 결과라 JobRunr 실제 스키마와 어긋날 수 있다. 믿으려면 카탈로그 비교 가드를 새로 만들어야 한다 |
| Flyway Java 마이그레이션이 JobRunr 의 마이그레이션 실행기를 부른다 | 저장소에 SQL 이 남지 않아 스키마 변경을 리뷰에서 볼 수 없다. 스키마 정본이 Flyway 마이그레이션 SQL 이라는 [ADR-0014](0014-spring-data-jdbc.md)에서 벗어난다 |
| 재시작 때 미완료 발행을 다시 보낸다(단독 또는 반복 작업과 함께) | 처리 중 실패한 발행이 재시작 때까지 방치된다. 인스턴스가 여럿이면 기동하는 쪽이 다른 인스턴스가 처리 중인 발행까지 다시 보내 중복 처리가 생긴다 |
| `FailedEventPublications.resubmit` 의 필터로 상한을 건다 | 실패 발행을 정해진 개수만 읽은 뒤 필터를 적용한다. 상한을 넘긴 행이 그 개수 이상 쌓이면 매 주기 같은 행만 읽혀 새 실패가 재제출되지 않는다 |
| 상한 없이 성공할 때까지 다시 처리한다 | 영구 실패(직렬화 깨짐 · 코드 결함)를 끝없이 반복해 비용과 로그 잡음이 계속 생긴다 |
| 처리 대기 · 처리 중 발행은 반복 작업이 마지막 활동 시각으로 판정하고, 감시는 재제출 중 상태만 맡긴다 | 감시는 세 상태를 함께 판정하므로 나머지 두 상태에 "사실상 판정 안 함"을 뜻하는 긴 기간을 따로 둬야 한다. 그 값이 발행의 정상 수명보다 짧아지면 조용히 중복 처리된다. 재제출 중 상태의 오판은 같은 이상 상황에서 남아, 얻는 차이가 작다 |
| 완료 기록을 남기고(`UPDATE`) 또는 보관 테이블로 옮기고(`ARCHIVE`) 주기적으로 정리한다 | 정리 작업과 보존 기간이라는 새 정책이 더해진다. 완료 기록을 볼 일은 실패를 조사할 때뿐이고 실패 기록은 남는다 |
| 작업 서버를 테스트에서만 켠다 | 기본 구성이 재처리를 하지 않는 상태가 역할 분리 때까지 이어진다. 기본 구성은 두 역할을 함께 하는 프로세스 하나다 |
