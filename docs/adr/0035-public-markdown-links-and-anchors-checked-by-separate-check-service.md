# ADR-0035: 공개 마크다운의 상대 링크와 앵커는 별도 검사 서비스가 확인한다

- 상태: 승인
- 날짜: 2026-10-29
- 근거: [이슈 #41](https://github.com/Theia0382/yozm-news/issues/41) — 기점 `cfd13e3` 의 공개 마크다운 53개 · 링크 474개(상대 455 · 앵커 15)를 집계하고, 구현 `02bec79` 의 검사기로 같은 수와 깨진 링크 0 을 확인. 무시 대상을 심은 작업 트리에서 빌드한 검사 이미지의 파일 목록을 추적 파일 목록과 대조
- 관련: [ADR-0016](0016-containerized-checks.md)(컨테이너 검사 · 허용 목록 `.dockerignore` · 메이저 태그 베이스 이미지 — 검사 서비스 목록을 이 ADR 이 대체), [ADR-0022](0022-image-targets-per-side-dockerfile-without-run-in-runtime-stage.md)(측별 Dockerfile — 문서 검사는 검사 전용 Dockerfile 하나), [ADR-0034](0034-module-spec-as-public-interface-specification-and-docs-by-kind.md)(문서 체계)

## 맥락

- CI 에는 코드 · 배포 검사만 있고 문서 검사가 없었다. 문서의 상대 링크는 개인 도구로만 확인했고, 그 도구는 `#앵커` 를 떼고 파일 존재만 보았다.
- 모듈 Spec 을 만들며 여러 문서의 절을 옮긴다. GitHub 은 사라진 앵커를 다른 곳으로 이어 주지 않는다 — 절을 옮기면 그 절을 가리키던 링크가 조용히 깨진다. 팀원 PR 의 문서 변경도 같은 위험이 있다.
- 공개 마크다운의 링크 가운데 문서 밖을 가리키는 것이 있다(`backend/` · `frontend/` · `api/` · `deploy/` · `.editorconfig`). 링크 대상이 있는지 보려면 검사가 도는 이미지에 그 경로가 있어야 한다.
- 백엔드 검사 이미지는 백엔드 빌드 파일과 테스트가 읽는 저장소 파일만, 프론트엔드 검사 이미지는 `.editorconfig` · `frontend/` · `api/openapi.json` 만 받는다(허용 목록 `.dockerignore`).

## 결정

- **검사 서비스 `docs` 를 따로 둔다.** `compose.check.yaml` 의 서비스는 `backend` · `frontend` · `docs` · `docker`(DinD)다. CI 는 같은 정의로 job `docs` 를 돌리고, 로컬은 같은 명령(`docker compose -f compose.check.yaml run --rm --build docs`)을 쓴다. 이 서비스 목록이 ADR-0016 의 서비스 목록을 대체한다 — 나머지 ADR-0016 결정(이미지 복사 · 허용 목록 · 메이저 태그 · 호스트 도구는 Docker 뿐)은 그대로 따른다.
- **검사기는 표준 라이브러리만 쓰는 Python 이다**(`tools/docs-check/check_links.py`, 단위 테스트 `test_check_links.py`). 이미지는 `python:3-slim` 이고 설치 단계가 없다. 컨테이너는 단위 테스트와 저장소 검사를 모두 돌리고, 하나라도 실패하면 실패한다.
- **대상과 판정**
  - 대상은 저장소 루트의 `*.md` 와 `docs/` · `.github/` 아래의 `*.md` 다. 코드 블록 · 인라인 코드 안의 링크는 링크가 아니다.
  - 스킴이 있는 링크(`https:` · `mailto:` 등)는 보지 않는다. 상대 링크는 경로가 있는지, `#앵커` 가 있고 대상이 마크다운이면 그 파일의 제목 앵커에 있는지 본다.
  - 앵커는 GitHub 의 규칙을 따른다 — 제목 글자를 소문자로 바꾸고 글자 · 결합 부호 · 십진 숫자 · 연결 구두점 · 공백 · `-` 만 남긴 뒤 공백을 `-` 로, 같은 앵커가 다시 나오면 `-1` · `-2` 를 붙인다.
  - 지원하지 않는 링크 형식(참조형 정의 · HTML `href` · 저장소 루트 기준 경로)은 건너뛰지 않고 실패한다.
  - 검사한 파일이 없거나 `docs/README.md` 가 대상에 없으면 실패한다 — 허용 목록이 문서를 빠뜨린 이미지가 링크 0개로 통과하지 않게 한다.
- **이미지에는 문서와 문서가 가리키는 경로만 넣는다.** 허용 목록(`tools/docs-check/Dockerfile.dockerignore`)은 검사기 · 대상 문서 · 문서 밖 링크 대상 경로를 넣고, 저장소가 추적하지 않는 것(`.gitignore` 의 대상)은 다시 뺀다. 문서가 허용 목록에 없는 경로를 가리키면 검사가 "경로 없음"으로 실패하고, 링크를 더한 변경이 허용 목록에 그 경로를 더한다.

## 결과

- 문서 검사 결과가 백엔드 · 프론트엔드 검사와 따로, 빠르게 나온다. 링크만 확인할 때 다른 검사를 돌리지 않는다.
- 검사 이미지 · 서비스 · CI job 이 하나씩 늘고, 최상위 디렉터리 `tools/` 와 검사기 언어(Python)가 저장소에 더해진다. 필수 체크 목록에 `docs` 를 더하는 일은 저장소 설정이다.
- 허용 목록이 문서 밖 경로를 디렉터리 단위로 넣으므로, 그 디렉터리의 파일만 바뀌어도 검사 이미지의 복사 계층이 다시 만들어진다.
- 저장소의 무시 규칙(`.gitignore`)이 바뀌면 이 허용 목록도 함께 맞춘다(ADR-0016 과 같다).
- 앵커 규칙은 GitHub 규칙의 사본이다. 갈리는 제목이 생기면 링크를 검사기의 앵커에 맞춰 쓴 경우 검사는 통과하고 GitHub 에서만 깨진다 — 갈림이 드러나면 규칙과 단위 테스트를 함께 고친다. setext 제목(밑줄 제목)은 앵커를 만들지 않아, 그런 제목을 가리키는 링크는 실패로 드러난다.
- 검사는 컨테이너에서만 돈다. 호스트에서 직접 돌리면 무시 대상 마크다운이 있는 작업 트리에서 대상이 달라진다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 백엔드 테스트(JUnit)로 둔다 | 새 job · 이미지 · 언어는 없지만, 백엔드 검사 이미지가 프론트엔드 · 배포 파일까지 품어 검사 입력이 저장소 전체로 번진다. 링크만 확인하려 해도 백엔드 검사 전체(Testcontainers 포함)를 돌려야 하고, CI 의 링크 결과도 백엔드 검사가 끝나야 나온다 |
| 프론트엔드 검사(Vitest)에 넣는다 | 프론트엔드 검사 이미지에 문서와 링크 대상을 넣어야 해 같은 번짐이 프론트엔드 쪽에 생기고, 문서 검사가 화면 코드의 테스트 묶음에 섞인다 |
| 개인 도구로 둔다 | 팀원 PR 의 깨진 링크를 잡지 못하고, 그 도구는 앵커를 보지 않는다 |
| 개발 인프라 문서를 정리할 때로 미룬다 | 문서를 가장 많이 옮기는 동안 공개 장치가 없다 |
