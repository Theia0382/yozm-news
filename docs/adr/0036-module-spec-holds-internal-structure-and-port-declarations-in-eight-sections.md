# ADR-0036: 모듈 Spec 은 책임 단위의 내부 구조와 포트 선언까지 갖고, 절을 바깥에서 안쪽 순서의 여덟 절로 둔다

- 상태: 승인
- 날짜: 2026-10-29
- 근거: [이슈 #48](https://github.com/Theia0382/yozm-news/issues/48) — 기점 `7c15503` 에서 세 Spec(`source` · `article` · `platform`)과 세 모듈의 코드 구성(파일 141개), Spec 절을 인용하는 코드 · 문서를 대조
- 관련: [ADR-0034](0034-module-spec-as-public-interface-specification-and-docs-by-kind.md)(모듈 Spec 의 자리 · 공통 구조 — 이 ADR 이 일부를 대체), [ADR-0013](0013-architecture-patterns.md)(모듈 내부 패키지 구조 · 포트는 외부 의존에만), [ADR-0035](0035-public-markdown-links-and-anchors-checked-by-separate-check-service.md)(문서 검사)

## 맥락

- ADR-0034 는 Spec 을 모듈 공개 인터페이스의 명세로 정하고, 내부 상세(클래스 구조 · 알고리즘 · 비공개 시그니처)는 Javadoc 이 정본이라 했다. 그래서 모듈 내부 구조의 개관이 들어갈 자리가 없었다. Javadoc 은 클래스 하나씩의 정본이라 개관을 주지 못하고, 코드가 생기기 전에는 아예 없다.
- 그 결과 Spec 만으로는 코드를 고칠 자리나 새 기능을 둘 자리를 정할 수 없었다. `source` Spec 만 읽어서는 수집 한 회차가 거치는 구성 요소(반복 작업 → 점유 → 수집 → 피드 요청 관문 → 정규화)도, 판단(백오프 · 점유 · 새 항목)이 `domain` 의 어디에 있는지도, 무엇이 aggregate 인지도 알 수 없었다. 새 모듈을 Spec 으로 먼저 설계할 때도 내부 구조가 공개 문서에 남지 않는다.
- 아홉 절 가운데 "작업과 리스너"(§5)는 들어오는 쪽 어댑터, "외부 의존"(§8)은 포트와 나가는 쪽 어댑터였다. 둘 다 내부 구조의 일부라, 내부 구조 절을 따로 더하면 같은 구성 요소가 두 절에 나온다.
- 포트 선언(`source` 의 `ArticleSource`)이 Spec 에 코드 블록으로 있었지만, 정본 규칙은 공개 인터페이스만 Spec 정본으로 정했다. 포트는 모듈 안의 타입이라, 그 선언은 감수하기로 정한 적 없는 사본이었다.
- 모듈마다 저장 방식이 달랐다. `source` 에는 Spring Data JDBC aggregate 둘(`Source` · `Feed`)과 aggregate 가 아닌 상태 객체(`FeedPollState` — `domain` 이 전이를 계산하고 저장은 점유 토큰 조건의 SQL)가 함께 있고, `article` 에는 aggregate 가 없다(삽입 전용 저장소). `platform` 은 자기 테이블이 없다.
- 기점에서 Spec 의 절 번호를 가리키는 코드 주석은 0건이었다. 절 번호를 바꿔도 고칠 인용은 문서 쪽(링크 둘 · 텍스트 인용 몇)뿐이었다. 코드 주석이 절을 인용하기 시작하면 이 비용이 커진다.

## 결정

- **Spec 은 모듈의 내부 구조를 갖는다.** 구성 요소와 그 책임 · 협력, 저장 단위(aggregate · 상태 객체 · 저장소와 쓰기 경로), 판단의 자리(상태 전이 · 일정 · 판정 · 검증 · 정규화의 정본), 트랜잭션 경계를 담는다. 클래스 내부 상세(필드 · 메서드 · 알고리즘 · 비공개 시그니처)만 Javadoc 이 정본이다.
  - 구성 요소는 책임 단위로 고른다 — 패키지마다 그 책임을 쓰고, 들어오는 쪽(작업 · 리스너 · 컨트롤러 · 기동 시 동작) · 유스케이스 · aggregate 와 상태 객체 · 저장소 · 판단의 정본 · 포트와 그 구현 · 로컬 대체물만 이름과 책임 한 줄로 쓴다. 값 · 결과 · 예외 · 보조 타입은 패키지 줄에 묶는다.
  - aggregate 가 없는 모듈 · aggregate 가 아닌 상태 객체도 같은 틀(저장 단위와 쓰기 경로)로 쓴다.
  - 내부 구조 절에 있는 구성 요소를 새로 만들거나 지우거나 이름 · 책임을 바꾸는 변경은 Spec 을 고친다.
- **포트 선언은 Spec 이 정본이다.** 공개 인터페이스와 같다 — 코드의 선언은 사본이고 감수한다. 포트 선언을 바꾸는 변경은 Spec 과 코드를 함께 고친다. 포트 구현 · 어댑터는 이름과 책임만 쓴다.
- **공통 구조는 바깥에서 안쪽 순서의 여덟 절이다** — 1 책임과 범위 · 2 용어 · 3 공개 인터페이스 · 4 내부 구조 · 5 규칙과 불변식 · 6 데이터 · 7 설정 · 8 결정.
  - 내부 구조(§4)는 하위 절 다섯으로 나눈다 — 개관 · 들어오는 쪽 · `application` · `domain` · 나가는 쪽. 옛 "작업과 리스너"는 들어오는 쪽, 옛 "외부 의존"은 나가는 쪽이 된다.
  - 공개 인터페이스(§3)는 공개 타입 · 이벤트마다 하위 절(제목 = 타입 이름, 번호 없음)을 두고 선언 · 필드 표(필드 · 뜻 · 제약) · 계약 · 관련 규칙 식별자를 담는다.
  - 이번 재배치는 한 번의 예외다. 새 번호는 고정하고, 이후 개정은 절 번호를 유지한다.
- **Spec 은 시퀀스 · 상태 다이어그램(Mermaid)을 쓸 수 있다.** 그림은 설명이고 규범은 규칙 절이다 — 둘이 다르면 규칙이 맞고 그림을 고친다. 그림의 단계 · 전이에는 규칙 식별자를 단다. 클래스 다이어그램은 쓰지 않는다.
- **폐지한 규칙은 지우지 않는다.** 식별자를 남긴 채 내용을 `(폐지 — 대체 식별자 또는 사유)` 로 바꾼다.
- **공개 인터페이스 · 내부 구조 절의 하위 제목은 규칙 절의 하위 제목과 이름이 겹치지 않는다.** 겹치면 앞 절이 앵커를 가져, 규칙 하위 절을 가리키던 링크가 깨지지 않은 채 다른 절을 가리킨다.
- **Spec 은 코드 이름을 인라인 코드로만 쓰고, 코드 파일 · 디렉터리로 링크하지 않는다.** Spec 의 코드 이름이 코드와 맞는지는 공개 인터페이스 · 포트 선언의 사본처럼 리뷰가 본다. 기계 검사는 두지 않는다.

## 결과

- Spec 하나로 코드를 고칠 자리 · 새 기능을 둘 자리 · 판단의 정본을 찾는다. 새 모듈의 설계 이슈는 Spec 에 내부 구조까지 먼저 쓴다.
- Spec 이 커진다. 구성 요소가 많은 모듈(`source`)은 내부 구조 절에 수십 개의 이름이 나온다.
- 클래스 이름을 바꾸는 리팩토링이 Spec 을 고치지 않아도 검사는 통과한다 — 리뷰가 잡아야 한다.
- 구성 요소의 책임 한 줄(Spec)과 그 클래스 Javadoc 의 첫 문장이 같은 내용을 두 번 적을 수 있다. 정리는 Javadoc 이 Spec 을 가리키는 표기를 정할 때 한다.
- 사본이 포트 선언만큼 늘어난다. 포트는 외부 의존에만 있으므로(ADR-0013) 수가 적다.
- 절 번호가 바뀌어, 옛 번호를 가리키던 문서 인용을 함께 고쳤다. 이후 코드 주석이 절을 인용하면 번호 변경 비용이 커지므로 번호를 고정한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 내부 구조 절에 모든 클래스를 나열한다 | `source` 만 118줄이 되어 개관이 묻히고, 보조 클래스를 더할 때마다 Spec 을 고친다. 클래스 목록은 Javadoc · IDE 가 이미 준다 |
| 패키지 단위만 쓴다 | 판단이 놓인 구성 요소를 가리키지 못한다 |
| 포트는 이름 · 책임 · 계약 문장만 쓰고 선언은 Javadoc 이 갖는다 | 새 포트를 Spec 으로 먼저 설계할 때 시그니처가 없다 — ADR-0034 가 공개 인터페이스에서 기각한 "의미만 쓴다"와 같은 약점이다 |
| 절 번호를 유지하고 내부 구조를 끝 절로 붙인다 | 작업 · 리스너와 외부 의존이 내부 구조와 따로 남아 같은 구성 요소가 두 절에 나온다 |
| 클래스 다이어그램도 쓴다 | 공개 인터페이스 절의 선언과 겹치고, 내부 타입의 상세는 Javadoc 이 정본이다 |
| Spec 이 코드 타입을 링크로 가리키고 문서 검사가 그 파일의 타입 선언을 확인한다 | ADR-0034 가 "리뷰가 본다"고 정한 Spec ↔ 코드 정합성을 이름 수준에서 기계 검사로 바꾼다. 표준 라이브러리 정규식으로 Java 선언을 판정하는 코드를 유지해야 하고, 모든 공개 마크다운에 새 작성 제약이 걸리며, 코드만 바꾼 PR 도 문서 검사로 실패한다 — 테스트 클래스 이름을 Spec 에 적는 안을 기각한 이유(이름을 바꿀 때마다 Spec 을 고친다)와 같은 비용이다 |
| Spec 이 코드 파일을 보통 상대 링크로 가리킨다(지금 경로 검사가 파일 이름 변경 · 삭제를 잡는다) | 코드 링크도 Spec ↔ 코드의 어긋남을 기계가 일부 잡는 장치가 되어, 위 대안과 같은 종류의 제약이 문서 검사에 걸린다 |
