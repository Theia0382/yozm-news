# ADR-0034: 모듈 Spec 은 모듈 공개 인터페이스의 명세로 코드보다 먼저 쓰고, 설계 문서는 종류 · 독자별 갈래로 나눈다

- 상태: 승인 (Spec 이 담는 것 · 클래스 구조의 자리 · 절 목록과 번호 고정은 [ADR-0036](0036-module-spec-holds-internal-structure-and-port-declarations-in-eight-sections.md)이 대체)
- 날짜: 2026-10-29
- 근거: [이슈 #41](https://github.com/Theia0382/yozm-news/issues/41) — 기점 `cfd13e3` 에서 코드가 있는 세 모듈(`source` · `article` · `platform`)의 지식이 놓인 문서 · 코드 · ADR 을 대조
- 관련: [ADR-0013](0013-architecture-patterns.md)(모듈 구조 · 모듈 문서 자동 생성 — 손으로 쓰는 Spec 은 그 생성물을 대체하지 않는다), [ADR-0020](0020-screen-api-contract-from-committed-openapi-spec.md)(화면용 API 형식의 정본은 `api/openapi.json` — Spec 은 엔드포인트만 적는다)

## 맥락

- 문서 위계에는 2층 모듈 Spec 의 자리가 있었지만 Spec 은 하나도 없었다. 작성 시점 규칙이 "모듈을 구현하는 이슈에서 작성한다", 갱신 트리거가 "Spec 이 있으면 — 없으면 작성 여부를 그 작업의 설계 단계에서 정한다", "Spec 이 없는 동안은 `architecture.md`"였다. 코드가 있는 세 모듈(`source` · `article` · `platform`)은 모두 Spec 없이 구현됐고, 이 예외를 들어 Spec 을 미루거나 쓰지 않기로 한 구현 이슈도 있었다.
- 그 결과 코드가 있는 모듈의 지식이 `pipeline` · `architecture` · `data-model` · `security` 와 ADR 에 흩어졌고, 일부는 코드와 어긋났다 — 데이터 모델 문서가 마이그레이션에 없는 컬럼을 적었고, 모듈 지도가 어디에도 정의되지 않은 이벤트를 가리켰다.
- 이전 위계는 "1 · 2층은 실제 시그니처를 다시 적지 않는다"였다. 그러면 Spec 만으로 모듈의 계약을 알 수 없어, Spec 을 토대로 코드를 쓰는 흐름이 성립하지 않는다.
- Spec 이 공개 인터페이스를 시그니처까지 가지면 코드의 선언과 사본이 생긴다. Spec 을 토대로 코드를 쓰는 흐름에서는 피할 수 없는 사본이다.
- `docs/` 루트에 설계 초안 · 개발 인프라 · 운영 · 계획 문서가 섞여 있었다. `infrastructure.md` 한 파일이 개발 · 검사 환경과 셀프 호스팅 운영을 함께 담았다.

## 결정

- **모듈 Spec(`docs/specs/{모듈}.md`)은 모듈 공개 인터페이스의 명세다.** 공개 타입 · 이벤트의 선언(시그니처)과 그 의미 · 제약, 규칙 · 불변식, 작업 · 리스너, 데이터, 설정, 외부 의존, 모듈 용어를 담는다.
  - 공개 인터페이스의 정본은 Spec 이고 코드는 Spec 을 따른다. 코드의 선언은 사본이고, 이 사본은 감수한다 — 공개 인터페이스를 바꾸는 변경은 Spec 과 코드를 함께 고친다.
  - 내부 상세(클래스 구조 · 알고리즘 · 비공개 시그니처)는 Javadoc 이 정본이다. 판단의 이유는 ADR 이 갖고 Spec 은 번호로 가리킨다.
- **새 모듈은 Spec 을 먼저 쓴다.** 그 모듈의 Spec 을 만드는 설계 이슈가 먼저이고, 구현 이슈는 그 Spec 을 토대로 한다. 공개 인터페이스 · 이벤트 · 작업 · 규칙 · 불변식을 바꾸는 변경은 Spec 을 고친다. 모듈마다 Spec 이 있는지 확인하는 자동 검사는 두지 않는다.
- **공통 구조는 `docs/specs/README.md` 하나가 정본이다.** 모든 Spec 이 같은 번호의 아홉 절(책임과 범위 · 용어 · 공개 인터페이스 · 규칙과 불변식 · 작업과 리스너 · 데이터 · 설정 · 외부 의존 · 결정)을 갖고, 빈 절은 "해당 없음"으로 남긴다. 절 번호는 바꾸지 않는다 — 코드 주석이 `docs/specs/{모듈}.md §n` 으로 가리킨다.
- **규칙 · 불변식에는 식별자 `{모듈}-R{번호}` 를 단다.** 테스트가 자기가 지키는 규칙을 이 식별자로 가리킨다. 지운 규칙의 번호는 다시 쓰지 않는다.
- **아직 구현되지 않은 설계도 Spec 에 담고 `(미구현)` 으로 표시한다.** 구현하는 변경이 표시를 지운다.
- **1층 `overview` 는 v1 전체의 시스템 지도다.** 아직 코드가 없는 모듈 · 의존 · 이벤트도 담고, 설계되지 않은 부분은 `(미설계)` 로 표시한다. **모듈 사이 의존의 정본은 `overview` §5** 이고, Spec 은 그 모듈이 내놓는 것(공개 인터페이스 · 발행 이벤트)만 정본으로 갖는다.
- **모듈 테이블은 그 모듈 Spec 의 데이터 절이 서술한다.** 주요 컬럼 · 의미 · 제약의 뜻을 적고, 컬럼 타입 · 인덱스 · 제약 문면의 정본은 Flyway 마이그레이션이다(주요 컬럼은 사본). 모듈 사이 관계 · 보존 정책 · 프레임워크 테이블은 `data-model.md` 가 갖는다.
- **용어는 쓰는 범위가 자리를 정한다.** 한 모듈 안에서만 쓰는 용어는 그 Spec 의 용어 절, 여러 모듈 · 화면이 쓰는 용어는 `overview` §8 이다.
- **`docs/` 는 종류 · 독자별 갈래로 나눈다** — 1층 `overview`, 2층 `specs/`, 개발 인프라 `development/`, 운영 `operations/`, 결정 `adr/`, QA `qa/`, 자료 `research/` · `archives/`, 계획 문서 `roadmap` · `open-questions`. 새 갈래(`specs/` · `development/` · `operations/`)마다 `README.md` 가 담는 것 · 담지 않는 것 · 문서 목록을 갖는다.
- **전환 중인 설계 초안은 루트에 둔 채 옮긴다.** `docs/README.md` §1 의 행선지 표가 문서마다 남은 내용이 갈 곳을 정한다. 모듈에 속한 내용은 그 모듈의 Spec 으로 가고, `data-model` 의 모듈 사이 관계 · 보존 정책과 `security` 의 횡단 정책은 그 문서에 남는다.

## 결과

- 모듈 하나를 이해하려면 그 Spec 과 `overview` §5 를 읽는다. 새 모듈의 설계 이슈는 Spec 을 쓰는 것으로 계약 · 스키마를 먼저 정한다.
- 공개 인터페이스와 주요 컬럼이 Spec 과 코드 두 곳에 있다. 어긋남을 잡는 자동 검사는 없고 리뷰가 본다.
- 새 모듈마다 설계 이슈가 하나 더 생긴다.
- Spec 에 구현된 것과 아직 구현되지 않은 것이 섞인다 — 표시를 지켜야 읽힌다. 구현하는 변경이 표시를 지우지 않으면 미구현이 남은 것처럼 보인다.
- 규칙 식별자를 붙이고 유지해야 한다. 식별자 없는 테스트 · 테스트 없는 식별자를 잡는 검사는 없다.
- 모듈 Spec 이 생기면 `data-model` · `security` 의 모듈 부분과 `pipeline` 의 단계 절은 그 Spec 을 가리키는 제목과 링크만 남는다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| Spec 은 의미 · 보장만 쓰고 타입 · 상수는 이름으로 가리킨다 | 사본은 없지만 Spec 만으로 계약을 알 수 없어 Spec 을 토대로 코드를 쓸 수 없다 |
| 공통 구조를 `docs/README.md` 작성 규칙에 둔다 | 모든 문서의 작성 규칙에 Spec 전용 구조가 섞이고, Spec 을 쓰는 사람이 `specs/` 에서 구조를 찾지 못한다 |
| 복사해 쓰는 템플릿 파일을 공통 구조의 정본으로 | 절마다 무엇을 담고 무엇을 담지 않는지 설명하기에 좁다 |
| 미구현 설계는 전환 중인 문서에 남기고 구현 때 옮긴다 | Spec 은 늘 현재 상태지만, 옮기는 일을 잊으면 모듈 지식이 다시 흩어진다 — 이 결정이 고치려는 실패 방식이다 |
| Spec 의 규칙마다 지키는 테스트 클래스 이름을 적는다 | 테스트를 나누거나 이름을 바꿀 때마다 Spec 을 고쳐야 한다 |
| 어느 테스트가 지키는지는 테스트 코드만 소유한다(식별자 없음) | Spec 에서 테스트로, 테스트에서 Spec 의 규칙으로 가는 경로가 없다 |
| 모듈 목록과 `docs/specs/` 를 대조하는 자동 검사 | 모듈 없는 Spec 을 잡는 방향은 Spec 을 먼저 쓰는 흐름과 부딪힌다. Spec 없는 모듈을 잡는 방향만 남기면, 모듈 신설은 드물고 설계 이슈가 먼저라 오래 놓치기 어렵다 |
| `overview` 는 확정된 것만 담는다 | 코드가 없는 모듈이 지도에서 빠져 모듈 이름 · 책임 경계의 정본이 사라진다 |
| 전환 중인 문서의 행선지를 정하지 않고 모듈을 만드는 이슈에 맡긴다 | 모듈에 속하지 않는 부분(ER 개요 · 보존 정책 · 횡단 보안 정책 · 외부 API)은 옮길 이슈가 없어 계속 남는다 |
| 모듈 테이블은 `data-model` 에 남긴다 / Spec 에는 의미만 쓴다 | 앞은 모듈 지식이 두 문서로 나뉘고, 뒤는 Spec 을 토대로 스키마를 설계할 수 없다 |
| 새 갈래는 디렉터리 없이 `docs/README.md` 에 자리만 / 빈 표시 파일만 | 갈래의 경계가 한 파일에 몰리거나 어디에도 없어, 그 갈래를 채우는 작업이 경계를 다시 정하게 된다 |
| 모듈 의존을 각 Spec 의 절로 옮긴다 / 두 곳에 다 둔다 | 앞은 코드가 없는 모듈의 의존이 자리를 잃고, 뒤는 같은 의존이 두 곳에서 어긋난다 |
