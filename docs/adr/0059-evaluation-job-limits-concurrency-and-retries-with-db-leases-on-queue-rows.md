# ADR-0059: 평가 작업은 대기 행의 DB 점유와 상태로 동시성 · 재시도를 제한하고, 정착 시간 뒤 평가하며, 결과가 체계와 어긋나거나 평가기가 예상 못한 예외를 던지면 회차를 멈춘다

- 상태: 승인
- 날짜: 2026-11-02
- 근거: [이슈 #69](https://github.com/Theia0382/yozm-news/issues/69) — 평가 대기 · 평가 작업을 만들며 JobRunr OSS 의 재시도 · 반복 작업 규칙과 수집 작업의 점유(ADR-0033)를 대조하고, 프리셋의 피드 구성 · 기본 수집 주기를 확인. 구현 `320f143`(일정 · 판정 규칙) · `90aa870`(대기 · 결과 저장소) · `a62ae65`(회차 · 작업)
- 관련: [ADR-0023](0023-jobrunr-oss-framework-schema-and-event-resubmission.md)(작업 종류별 동시성 제한은 기능을 구현할 때 정한다 — 이 ADR 이 정한다), [ADR-0033](0033-feed-polling-db-lease-per-feed-new-items-and-per-source-request-spacing.md)(수집의 DB 점유), [ADR-0058](0058-evaluator-failures-in-three-kinds-and-unavailable-evaluator-skips-article-retries.md)(실패 세 갈래)

## 맥락

- 공유 평가는 기사마다 평가기 요청 하나를 보낸다. 유입은 하루 수천 건으로 추정되고, 첫 수집 · 오래 쌓인 대기는 한꺼번에 들어온다.
- JobRunr OSS 의 재시도는 작업 단위이고, 작업 종류별 동시성 제한이 없다. 서버당 worker 수만 조절된다(ADR-0023).
- 평가기 실패는 세 갈래다. 평가기 사용 불가면 기사 재시도를 쓰지 않고 회차를 멈춘다(ADR-0058). 이 "회차"는 작업 사이에 표현할 길이 있어야 한다.
- 같은 기사가 "전체기사" 피드와 섹션 피드에 함께 실리면, 먼저 수집된 피드의 엔트리로 저장되고 다른 엔트리는 그 피드의 다음 수집(기본 15분)에서 붙는다. 첫 엔트리의 섹션이 "전체기사"면 주제 단서가 되지 않는다. 같은 체계 버전으로는 기사를 한 번만 평가한다.
- 포트 결과는 값 하나하나만 검사되고, 체계와 맞는지는 부르는 쪽이 본다. 체계 · 구현 불일치나 예상 못한 예외는 모든 기사에 같게 날 수도, 특정 기사에서만 날 수도 있다.

## 결정

- **평가는 대기 행 하나가 기사 하나인 DB 대기열로 한다.** 반복 작업(1분, JobRunr 재시도 없음)의 회차가 평가할 수 있는 행을 `FOR UPDATE SKIP LOCKED` 로 묶음(50건)만큼 잠그고 점유(토큰 · 만료)를 써 커밋한 뒤, 트랜잭션 밖에서 기사마다 차례로 평가기를 부르고, 결과는 기사마다 새 트랜잭션에서 토큰이 맞을 때만 반영한다. 회차 비중첩은 반복 작업의 규칙이, 인스턴스 사이 · 점유 만료 뒤 겹침은 토큰이 막는다. 평가는 작업 서버 worker 가운데 많아야 하나를 쓴다.
- **재시도는 대기 행의 상태로 한다.** 일시 실패는 시도 수를 늘리고 간격(1분부터 두 배, 상한 1시간)만큼 평가 가능 시각을 미루며 다섯 번째에 실패로 남긴다. 기사 거부는 바로 실패로 남긴다. 실패로 남은 행은 운영자가 셀 수 있다.
- **새 기사는 정착 시간(30분) 뒤에 평가한다.** 다른 피드 엔트리가 붙은 입력으로 한 번뿐인 평가를 한다.
- **결과가 체계와 어긋나거나 평가기가 예상 못한 예외를 던지면 평가기 사용 불가와 같이 회차를 멈춘다.** 그 기사부터 남은 점유를 풀고(시도 수 그대로) 오류 로그에 기사 ID 를 남긴다. 체계와 맞는다는 것은 태그 종류마다 키 집합이 같고 원본 응답을 저장할 수 있다는 것이다.
- 값(정착 시간 · 점유 기간 · 묶음 · 시도 상한 · 간격)은 측정 전 목표이고 코드의 상수 하나씩이다.

## 결과

- 평가기 결함 · 키 무효가 고쳐질 때까지 기사를 잃지 않는다. 결함을 고쳐 배포하면 대기가 그대로 이어진다.
- 특정 기사만의 결함이면 그 기사가 매 회차 맨 앞에서 평가 전체를 막는다 — 오류 로그가 회차마다 기사 ID 와 함께 남아 드러난다.
- 처리량은 한 회차에 50건, 회차는 겹치지 않는다. 점유 기간(30분)은 묶음 × 요청 마감보다 길어야 하고, 넘으면 다른 회차가 같은 기사를 다시 평가할 수 있다(저장은 한 번).
- 결과가 정착 시간만큼 늦다. 다이제스트는 하루 단위라 생성 직전 기사 일부가 다음 날로 밀린다.
- 저장 단계의 DB 오류가 그 기사에서 계속 나면 점유 만료마다 다시 평가해 비용이 든다. 알려진 저장 거부(원본 응답의 문자)는 평가 결과 검사가 먼저 막는다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 기사마다 JobRunr 작업을 만들고 작업 재시도를 쓴다 | 작업 종류별 동시성 제한이 없어 worker 전부가 평가에 쓰일 수 있다. 평가기 사용 불가의 "회차 멈춤"을 작업 사이에 표현할 수 없다 |
| 대기에 들어간 뒤 첫 회차에 평가한다 | 다른 섹션 피드 엔트리가 붙기 전의 입력으로 한 번뿐인 평가를 한다 |
| 결과 어긋남 · 예상 못한 예외를 그 기사의 일시 실패로 센다 | 결함이 모든 기사에 같으면 대기의 기사가 모두 상한을 소진해 실패로 남는다 — 평가기 사용 불가를 일시 실패로 셀 때와 같은 결과다 |
| 성공한 대기 행을 상태만 바꿔 남긴다 | 대기 테이블이 기사 수만큼 무기한 커진다. 평가 행이 성공의 기록이다 |

## 후속 기록

- 2026-11-02: 체계를 활성으로 바꾸면 재평가 기간 안의 기사를 대기에 넣거나 되돌린다(평가 가능 시각은 그 시각, 순서는 같다). 회차는 결과를 쓰는 트랜잭션에서 `tag_sets` 표를 `SHARE` 로 잠그고 자기가 읽은 버전이 아직 활성인지 본 뒤 쓴다 — 아니면 점유를 풀고 회차를 멈춘다([ADR-0062](0062-tag-set-versions-from-operator-text-activated-forward-with-key-lineage-and-recent-reevaluation.md))
