# ADR-0135: 피드 상태 변화는 검사 회차마다 전이를 실은 이벤트로 알리고, 그때의 운영자 계정마다 안 읽은 알림 하나에 모으며, 읽음은 화면이 받은 판까지다

- 상태: 승인
- 날짜: 2026-11-13
- 근거: [이슈 #146](https://github.com/Theia0382/yozm-news/issues/146) — 구현 `cc0656c`(발행) · `83eb094`(모으기 · 반영 기준) · `d17b8d0`(읽음)
- 관련: [ADR-0040](0040-feed-status-stored-in-poll-state-and-rejudged-hourly-by-health-check.md)(직전 상태를 저장하는 이유로 "화면 내 알림에 넘기기"를 들었다 — 이 ADR 이 그 연결을 정한다), [ADR-0105](0105-storylines-link-incrementally-from-event-change-notifications-and-events-publish-changed-event-ids.md)(`EventsChanged` 는 무엇이 일어났는지 싣지 않는다 — 이 이벤트가 다른 꼴인 이유를 아래에 적는다), [ADR-0134](0134-in-app-notices-are-one-row-per-recipient-with-a-closed-kind-and-per-kind-jsonb-content-and-read-notices-are-deleted-after-ninety-days.md)(알림의 저장 꼴)

## 맥락

- 피드 건강 검사는 1시간마다 켜진 피드를 다시 판정하고, 바뀐 피드의 상태를 쓴 뒤 전이를 로그로 남긴다. 운영자 계정에 화면 안에서도 알려야 한다.
- 알림이 쏟아지는 원천은 두 가지다.
  - 앱 서버의 바깥 연결이 끊기면 켜진 피드 N 개가 함께 실패해 함께 바뀌고, 복구되면 함께 돌아온다 — 전이마다 알림이면 장애 한 번에 2N 개다.
  - 깜빡이는 피드 하나는 하루 최대 24번(명목) 바뀐다. 운영자가 일주일 뒤에 들어오면 168건이다.
- 이벤트는 최소 한 번 처리된다 — 리스너가 실패하거나 처리 중에 멈춘 발행은 나중에 다시 처리되고, 운영자가 다시 처리할 수도 있다. 같은 회차가 두 번 오거나 앞선 회차가 늦게 올 수 있다.
- 알림 내용은 "무엇에서 무엇으로 바뀌었나"다. 받는 쪽이 지금 상태를 다시 읽어서는 이전 상태를 알 수 없다.

## 결정

- **`source` 는 검사 회차에 바뀐 피드가 있을 때만, 상태를 쓴 트랜잭션에서 `FeedStatusesChanged` 를 한 번 발행한다.** 판정 시각과 바뀐 피드마다 이전 · 새 상태를 싣는다. 복귀(`ACTIVE`)도 전이다.
- **`user` 는 그때 쓰는(`ACTIVE`) 운영자(`ADMIN`) 계정마다 안 읽은 피드 상태 알림 하나에 모은다.** 피드마다 처음 이전 상태 · 마지막 새 상태 · 바뀐 횟수 · 처음 · 마지막 판정 시각을 둔다. 안 읽은 알림이 없으면 새로 만든다. 사용자마다 안 읽은 피드 상태 알림은 많아야 하나다(부분 고유 인덱스).
- **사용자마다 반영 기준(반영한 마지막 회차의 판정 시각)을 읽은 알림과 따로 둔다.** 기준보다 늦은 회차만 반영한다. 반영 기준 행의 잠금이 같은 사용자에 대한 리스너들을 줄 세운다.
- **피드 이름은 남길 때 함께 적는다.** 뒤에 피드를 지워도 알림의 이름은 남는다.
- **읽음은 화면이 받은 `{알림 ID, 판}` 이 그대로인 알림만 바꾼다.** 화면이 받은 뒤 리스너가 전이를 더했으면 판이 달라 안 읽음으로 남는다.

## 결과

- 운영자가 얼마나 오래 들어오지 않든 안 읽은 피드 상태 알림은 하나이고, 깜빡임은 바뀐 횟수로 드러난다. 장애 한 번은 피드 N 줄짜리 알림 하나다.
- 늦게 온 앞선 회차는 버린다 — 바뀐 횟수 · 처음 이전 상태가 빠질 수 있지만 마지막 새 상태는 맞다.
- 검사 둘이 겹치면(판정 시각을 트랜잭션 전에 읽는다) 판정 시각 순서와 커밋 순서가 어긋나 알림이 한 회차 앞의 상태로 남을 수 있다. 다음 회차가 상태를 다시 판정한다.
- 나중에 운영자가 된 계정은 반영 기준이 없어, 운영자가 옛 발행을 다시 처리하면 그 옛 회차를 받는다. 알림에 판정 시각이 보인다.
- `user` → `source` 의존이 생긴다. `source` 는 `user` 의 타입을 쓸 수 없다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 전이마다 알림 하나 | 장애 한 번에 피드 수의 두 배, 깜빡이는 피드 하나에 하루 24건이 쌓인다 |
| 검사 회차마다 알림 하나 | 동시 전이는 묶이지만 깜빡이는 피드 하나로 하루 24건이 쌓인다. 알림이 바뀌지 않아 재처리는 쉽다 |
| `EventsChanged` 처럼 피드 ID 만 싣고 받는 쪽이 지금 상태를 읽는다 | 이전 상태를 알 수 없다 |
| 반영 기준을 안 읽은 알림 안에만 둔다 | 읽은 뒤 같은 회차가 다시 처리되거나 앞선 회차가 늦게 오면 이미 본 전이가 새 알림이 된다 |
| 반영한 회차의 판정 시각을 모두 남긴다(늦은 회차도 끼워 넣기) | 집합이 계속 커지고, 늦게 오는 것은 실패 · 재처리 때뿐이다 |
| 만들기를 고유 인덱스 위반 뒤 다시 시도로 줄 세운다 | PostgreSQL 에서 위반은 트랜잭션을 깬다. 반영 기준 잠금이 이미 줄을 세운다 |
| 읽음을 "목록을 받은 서버 시각까지"로 받는다 | 알림을 고치는 프로세스(작업 역할)와 읽음을 받는 프로세스(화면 역할)의 시계가 다르다 |
