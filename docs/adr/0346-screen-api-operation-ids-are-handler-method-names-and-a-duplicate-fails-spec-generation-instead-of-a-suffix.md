# ADR-0346: 화면용 API 명세의 연산 ID 는 처리기 메서드 이름이고, 겹치면 접미사를 붙이지 않고 명세 생성이 실패한다

- 상태: 승인
- 날짜: 2026-11-26
- 근거: [이슈 #174](https://github.com/Theia0382/yozm-news/issues/174) — 기점 `00fa7ff` 의 명세에서 연산 116개 가운데 10개(이름 9개)에 접미사가 붙어 있었고, 연산 ID 를 읽는 곳(프론트엔드 · 저장소 도구 · 배포 구성)은 없었다. 구현 커밋 `5498edb`
- 관련: [ADR-0020](0020-screen-api-contract-from-committed-openapi-spec.md)(화면 계약의 정본은 커밋된 명세 — 보충), [ADR-0345](0345-screen-api-schema-names-stay-simple-and-a-name-shared-by-two-types-fails-spec-generation.md)(스키마 이름 겹침 — 같은 자리의 다른 이름 규칙)

## 맥락

- 명세 생성기는 처리기 메서드 이름을 연산 ID(`operationId`)로 쓰고, 겹치면 생성 끝에서 `_1` · `_2` 접미사를 붙인다. 번호는 경로를 훑는 순서로 매기므로, 같은 이름의 처리기가 더 앞서 훑이게 생기면 기존 연산의 번호가 경고 없이 바뀐다.
- 운영자 API 의 소스 · 피드 처리기가 같은 동작 이름(`enable` · `delete` 등)을 써서 접미사가 붙어 있었다.
- 프론트엔드는 연산 ID 가 아니라 경로로 API 를 부른다. 연산 ID 로 클라이언트를 만드는 소비자(외부 공개 API · MCP 어댑터)는 로드맵에 있다.

## 결정

- **연산 ID 는 처리기 메서드 이름이고, 화면용 API 전체에서 겹치지 않는다.** 겹치면 접미사를 붙이지 않고 명세 생성이 실패한다. 메시지에 그 ID 와 겹친 연산들의 HTTP 메서드 · 경로를 낸다.
- **생성기의 접미사 장치를 같은 bean 이름의 검사로 바꾼다.** 접미사 처리와 검사가 두 벌로 돌지 않고, 장치 사이의 순서에 기대지 않는다.
- **겹치던 처리기는 동작 이름에 대상 명사를 붙인다.** 소스 · 피드처럼 같은 동작을 가진 짝은 양쪽 모두 바꾼다(`enableSource` · `enableFeed`).
- 한 처리기를 경로나 HTTP 메서드 둘 이상에 매핑하면 연산 둘이 같은 ID 를 받는다 — 그런 처리기는 매핑마다 메서드를 나눈다. 연산 ID 를 직접 주는 애너테이션(`@Operation(operationId)`)도 메서드 하나에 하나라 매핑마다 다른 ID 를 주지 못한다.
- 규칙 본문은 [platform Spec](../specs/platform.md) platform-R129 다.

## 결과

- 처리기를 더해도 기존 연산 ID 가 밀리지 않는다. 새 처리기가 다른 처리기와 같은 메서드 이름을 쓰면 명세 갱신과 대조 시험이 실패한다.
- 이 결정으로 기존 명세의 연산 ID 18개가 바뀌었다. 스키마 · 경로 · 응답은 바뀌지 않았다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 접미사를 그대로 두고 연산 ID 를 계약 밖으로 적기 | 처리기 순서에 따라 번호가 경고 없이 바뀌는 것이 남는다. 연산 ID 를 읽는 소비자가 생기는 순간 조용히 깨진다 |
| 연산 ID 를 클래스 이름 등으로 늘 유일하게 만들기 | 모든 연산 ID 가 바뀌고 이름 규칙을 생성기 밖에서 다시 정한다 — 스키마 이름의 정규화된 이름을 기각한 근거([ADR-0345](0345-screen-api-schema-names-stay-simple-and-a-name-shared-by-two-types-fails-spec-generation.md))와 같다 |
| 겹친 쪽만 이름 바꾸기(10개) | 소스 · 피드의 같은 동작이 `enable` · `enableFeed` 처럼 짝이 어긋난다 |
| 생성기 장치는 두고 그보다 먼저 도는 검사 추가 | 접미사 장치가 죽은 코드로 남고, 검사가 장치 순서에 기댄다 |
