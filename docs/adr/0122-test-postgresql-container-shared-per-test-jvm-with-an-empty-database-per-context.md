# ADR-0122: 테스트의 PostgreSQL 컨테이너는 테스트 JVM 이 함께 쓰고, 컨텍스트마다 빈 데이터베이스를 만든다

- 상태: 승인
- 날짜: 2026-11-12
- 근거: [이슈 #139](https://github.com/Theia0382/yozm-news/issues/139) — 로컬 컨테이너 검사로 테스트 시간의 구성을 재고, 바꾼 구성으로 전체 테스트를 돌려 확인함(`73c97db`)
- 관련: [ADR-0004](0004-tech-stack.md)(테스트 DB 는 Testcontainers 의 PostgreSQL — 그대로), [ADR-0019](0019-dev-compose-per-checkout-and-test-image-source.md)(테스트의 PostgreSQL 이미지 정본 — 그대로), [ADR-0016](0016-containerized-checks.md)(검사는 컨테이너에서, CI 와 로컬이 같은 정의), [ADR-0018](0018-local-profile-compose-connection.md)(맥락의 "테스트가 Testcontainers 의 `@ServiceConnection` 으로 접속 정보를 받는다"는 문장이 구현과 어긋난다 — 보충. 결정은 그대로)

## 맥락

- 백엔드 테스트는 실제 PostgreSQL 에서 돈다([ADR-0004](0004-tech-stack.md) · [테스트 전략 §5](../qa/test-strategy.md#5-오라클-규약)). 테스트 구성은 PostgreSQL 컨테이너를 스프링 빈으로 두고 `@ServiceConnection` 으로 접속 정보를 받았다. 빈이므로 스프링 컨텍스트 하나가 컨테이너 하나를 가졌다.
- 스프링은 구성이 같은 테스트 클래스끼리 컨텍스트를 함께 쓰고, 구성이 다르면 새로 만든다. 슬라이스 테스트와 속성이 다른 통합 테스트가 많아 한 번의 전체 실행에 DB 를 쓰는 컨텍스트가 수십 개 만들어진다.
- 로컬 컨테이너 검사 두 번에서 컨테이너 기동은 48회였고 그 시간이 테스트 시간의 약 40% 였다. 마이그레이션을 처음부터 적용하는 시간은 컨텍스트마다 0.3초 이하였다.
- 컨텍스트마다 빈 DB 에서 시작하는 것에 기대는 테스트가 있다 — 마이그레이션 테스트, 기동 때 적재되는 것을 보는 테스트, 작업 서버를 켠 통합 테스트.

## 결정

- **PostgreSQL 컨테이너는 테스트 JVM 하나에 하나다.** 처음 쓸 때 한 번 띄우고, JVM 이 끝날 때 Testcontainers 가 치운다. 스프링은 컨테이너의 수명을 맡지 않는다.
- **격리 단위는 데이터베이스다.** 컨텍스트가 만들어질 때마다 그 컨테이너 안에 빈 데이터베이스를 새로 만들고, 컨텍스트는 그 데이터베이스에 마이그레이션을 처음부터 적용한다. 데이터베이스는 지우지 않는다.
- **접속 정보는 테스트 구성의 `JdbcConnectionDetails` 빈이 준다.** `@ServiceConnection` 은 쓰지 않는다.
- **서버의 연결 수 한도를 올린다.** 컨텍스트 캐시에 남는 컨텍스트마다 연결 풀이 하나씩 붙으므로, 한도를 캐시 크기와 풀 크기에서 계산해 컨테이너 명령으로 준다. 테스트의 연결 풀 설정은 바꾸지 않는다.
- 구성의 현재 상태는 [개발 인프라 — 테스트 DB](../development/infrastructure.md#테스트-db)가 갖는다.

## 결과

- 한 번의 전체 실행에서 컨테이너 기동이 한 번이 됐다. 로컬 컨테이너 검사에서 검사 단계가 약 600초(두 번)에서 약 256초(두 번)로 줄었다. CI 에서의 시간은 따로 잰다.
- 컨텍스트마다 빈 DB 에서 시작하는 것은 그대로다. 컨텍스트 구성 · 컨텍스트 캐시 크기 · 테스트의 단언은 바뀌지 않았다.
- 한 서버를 여러 데이터베이스가 함께 쓴다. 서버 전체에 걸친 것(역할 · 서버 설정 · 다른 데이터베이스의 연결)을 만들거나 읽는 테스트는 다른 컨텍스트에 영향을 주거나 받는다 — 그런 테스트를 더할 때는 자기 데이터베이스 · 자기 연결로 좁혀 읽는다.
- 컨텍스트 캐시 크기나 연결 풀 크기를 바꾸면 연결 수 한도가 함께 맞아야 한다. 한도의 산식은 테스트 구성 한 곳에 있고, 서버에 적용된 값은 테스트가 지킨다.
- 컨테이너가 뜨지 못하면 그 JVM 의 DB 를 쓰는 테스트가 모두 실패한다.
- 테스트 JVM 을 여럿으로 나누면 JVM 마다 컨테이너가 하나씩 뜬다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 컨텍스트마다 컨테이너(앞선 구성) | 컨테이너 기동이 테스트 시간에서 가장 큰 덩어리였다 |
| 컨테이너 하나에 데이터베이스도 하나를 함께 쓴다 | 캐시에 남은 컨텍스트의 작업 서버가 다른 테스트의 작업을 집어 가고, 테이블을 비우는 테스트와 빈 DB 를 전제한 테스트가 서로를 깬다. 테스트 간 데이터 격리([테스트 전략 §5](../qa/test-strategy.md#5-오라클-규약))를 깬다 |
| `@ServiceConnection` 을 유지하고 컨테이너 빈을 정적 필드로 함께 쓴다 | `@ServiceConnection` 이 내는 접속 정보는 컨테이너의 기본 데이터베이스라 위와 같아진다. 스프링이 컨텍스트를 닫을 때 컨테이너를 멈추는 수명 관리와도 부딪힌다 |
| 접속 정보를 `spring.datasource.*` 속성으로 등록한다 | 성립하지만 접속 정보를 속성 이름 문자열로 넘긴다. `JdbcConnectionDetails` 는 접속 정보를 바꿔 끼우는 타입이고 `@ServiceConnection` 이 만들던 것과 같은 타입이다 |
| 마이그레이션을 적용한 템플릿 데이터베이스에서 복제한다 | 마이그레이션 적용 시간이 작아 얻는 것이 없고, 마이그레이션 테스트는 빈 DB 에서 시작해야 한다 |
| 테스트의 연결 풀 유휴 연결을 줄인다 | 기본 연결 풀의 수요를 재는 테스트의 전제를 바꾼다 |
| 컨텍스트 구성을 합쳐 컨텍스트 수를 줄인다 | 구성 대부분이 클래스 하나짜리 슬라이스라, 합치려면 슬라이스가 띄우는 범위를 넓혀야 한다. 컨테이너를 뺀 컨텍스트 기동 시간은 작다 |
