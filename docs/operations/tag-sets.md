# 태그 체계 바꾸기

평가가 기사에 붙이는 태그 체계(주제 · 지역 · 형식 · 중요도의 키와 질문)를 바꾸는 방법이다. 태그 체계는 운영자 API 로 바꾼다 — **(미구현)** 운영자 화면의 태그 체계 편집. 운영자 API 는 [운영자 토큰](configuration.md#운영자)으로 연다.

이 문서는 작업 순서와 결과를 다룬다. 원문의 키 · 값 규칙은 [체계 파일 형식과 검증](../specs/evaluation.md#체계-파일-형식과-검증), 버전 · 계보 · 재평가의 규칙은 [체계 변경](../specs/evaluation.md#체계-변경)에 있다.

## 바꾸기 전에

- **바꾸면 새 버전이 생긴다.** 원문을 내면 지금 활성 버전(기준 버전)과 대조한 뒤 다음 번호의 버전으로 저장하고 곧바로 활성으로 바꾼다. 이전 버전은 지워지지 않고 목록에 남는다
- **되돌리기도 새 버전이다.** 이전 버전으로 돌아가려면 그 버전의 원문을 받아 다시 낸다 — 번호가 하나 더 생긴다
- **이전 기사는 이전 버전의 결과를 유지한다.** 새 버전은 그 뒤에 평가하는 기사부터 쓴다. 최근 기사를 새 버전으로 다시 평가하려면 [재평가 기간](#재평가-기간)을 정한다
- **키를 바꾸거나 나누거나 합칠 때는 계보를 적는다.** 사용자의 태그 선호와 주제별 기록이 계보를 따라 새 키로 이어진다. 계보 없이 지운 키의 선호는 이어지지 않는다 — [계보](#계보)
- **태그 기준 · 저장 기준만 바꾸려면 원문을 내지 않는다.** 원문의 `thresholds` 만 다른 원문은 "바뀐 것 없음"(`UNCHANGED`)으로 끝나고 아무것도 쓰지 않는다. 원문의 `thresholds` 는 새 버전의 처음 값이다
  - **(미구현)** 태그 기준 · 저장 기준을 바꾸는 운영자 화면 · API

## 평가 현황으로 근거를 본다

운영자 화면의 **평가 현황**(`/admin/evaluation`)에서 기간(시작일 · 종료일, 1 ~ 31일)을 고른다. 날짜는 브라우저 시간대의 자정 기준이다.

- **품질 지표** — 고른 버전(기본 활성 버전)의 평가 가운데 평가 시각이 기간 안인 것을 그 버전의 지금 태그 기준 · 저장 기준으로 판정해 센다
  - 태그 분포 · 기사당 붙은 태그 수 — 거의 붙지 않는 태그와 너무 자주 붙는 태그
  - `low_confidence` · 미분류 비율 — 태그 기준이 높거나 체계가 기사를 덮지 못하는 정도
  - 확률 분포 — 태그 기준 근처에 확률이 몰리는지. 지금 저장 기준 아래 칸은 "저장하지 않음"(0 이 아니라 저장하지 않은 것), 걸친 칸은 "일부 저장"이다. 기간 안 평가의 저장 기준이 섞였으면(기간 안에서 저장 기준을 바꿨고 [빠진 태그를 채워](#저장-기준을-낮춘-뒤-빠진-태그-채우기) 고르게 하지 않았으면) 화면이 알린다 — 그 근처 칸은 평가마다 다른 기준으로 저장됐다
  - 중요도 기대값 분포, 요청당 입력 토큰(평균 · 최소 · 최대 · 칸) — 질문을 늘리면 입력 토큰이 는다
- **주제별 보도량** — 첫 평가 시각이 기간 안인 기사를 활성 버전의 주제마다 센다. 옛 버전으로 평가된 기사도 계보를 따라 활성 키로 센다. 대분류의 수는 하위 중분류의 합이 아니라 그 대분류의 주제가 하나라도 붙은 기사 수다
- **평가 대기** — 지금의 대기 · 실패 건수(기간과 무관)

태그 기준 · 저장 기준을 바꾸면 지난 기간의 지표 · 보도량도 지금 기준으로 다시 나온다. 규칙은 [평가 현황 · 주제별 보도량](../specs/evaluation.md#평가-현황--주제별-보도량)에 있다.

## 순서

아래 예시는 이 호스트에서 기본 공개 주소(루프백 `127.0.0.1:8000` — [공개](configuration.md#공개))로 부른다. `curl` 과 `jq` 가 필요하다.

1. **지금 원문을 받는다** — 버전 목록에서 활성 버전(`"active": true`)의 `id` 를 찾아 그 원문을 받는다. 원문에는 그 버전의 내용과 지금 태그 기준 · 저장 기준이 들어 있고, 계보 절과 주석은 없다

   ```sh
   export YOZMNEWS_ADMIN_TOKEN='운영자 토큰'
   curl -s -H "Authorization: Bearer $YOZMNEWS_ADMIN_TOKEN" http://127.0.0.1:8000/api/admin/tag-sets | jq
   curl -s -H "Authorization: Bearer $YOZMNEWS_ADMIN_TOKEN" http://127.0.0.1:8000/api/admin/tag-sets/1/text | jq -r .text > tag-set.yaml
   ```

2. **원문을 고친다** — 키를 바꾸거나 나누거나 합쳤으면 끝에 계보 절을 적는다([예시](#예시))
3. **확인한다** — 아무것도 쓰지 않고 대조 결과를 본다. `recentDays` 는 활성화 때 쓸 재평가 기간이고, 그 기간에 처음 본 기사 수가 `recentArticles` 로 온다

   ```sh
   jq -Rs '{text: ., recentDays: 7}' tag-set.yaml \
     | curl -s -H "Authorization: Bearer $YOZMNEWS_ADMIN_TOKEN" -H 'Content-Type: application/json' \
         --data-binary @- http://127.0.0.1:8000/api/admin/tag-set-reviews | jq
   ```

   | `result` | 뜻 |
   |---|---|
   | `READY` | 활성화할 수 있다. `changes` 에 더한 · 지운 · 고친 키, 계보, 질문 · 중요도 문구가 바뀌었는지, 지금 값과 다른 태그 기준 · 저장 기준이 있다 |
   | `UNCHANGED` | 기준 버전과 내용이 같다 — 활성화해도 아무것도 하지 않는다 |
   | `INVALID_TAG_SET` | 원문이 형식 검증이나 기준 버전과의 대조에 걸렸다. `problems` 에 문제마다 경로 · 코드 · 문구 · 줄:열이 있다 |

4. **활성화한다** — 같은 본문을 `/api/admin/tag-sets` 로 보낸다. 확인과 같은 판정을 그 순간의 활성 버전과 다시 하고, 통과하면 새 버전의 `id` · `number`, 변경 목록, 재평가 대기에 넣거나 실패에서 되돌린 기사 수 `requeued`(이미 대기 중인 기사는 세지 않는다)가 `ACTIVATED` 로 온다

   ```sh
   jq -Rs '{text: ., recentDays: 7}' tag-set.yaml \
     | curl -s -H "Authorization: Bearer $YOZMNEWS_ADMIN_TOKEN" -H 'Content-Type: application/json' \
         --data-binary @- http://127.0.0.1:8000/api/admin/tag-sets | jq
   ```

`recentDays` 를 빼거나 `null` 로 보내면 0 이다 — 재평가하지 않는다. 0 ~ 30 밖이면 400 이고 아무것도 하지 않는다.

## 계보

계보 절(`lineage`)은 이전 버전의 키가 새 버전의 어느 키로 이어지는지 적는다. 항목마다 태그 종류 `kind`(`topic` · `region` · `format`), 변경 `change`, 이전 키 `from` · 새 키 `to` 의 목록을 적는다.

| `change` | `from` → `to` | 쓰는 때 |
|---|---|---|
| `rename` | 1 → 1 | 키 이름만 바꾼다. 새 키는 기준 버전에 없다 |
| `split` | 1 → 2 이상 | 키 하나를 여럿으로 나눈다. 이전 키를 남기면 `to` 에도 적고, 그 밖의 새 키는 기준 버전에 없다 |
| `merge` | 2 이상 → 1 | 여러 키를 하나로 합친다. 새 키는 기준 버전에 없거나 `from` 가운데 하나다 |

- 주제의 중분류는 전체 키(`politics.executive`)로 적는다. 대분류는 대분류끼리, 중분류는 중분류끼리 잇는다
- 대분류 키를 바꾸면 그 아래 중분류의 전체 키도 바뀐다 — 바뀐 전체 키마다 따로 적는다. 앱은 계보를 추론하지 않는다
- 계보는 그 원문을 낸 버전에만 속한다. 다음 원문을 낼 때는 지운다 — 받은 원문에는 계보 절이 없다

## 예시

기본 체계의 지역 "기타 해외"(`other-foreign`)에서 중동을 따로 떼어 내는 변경이다. 받은 원문의 `regions` 절을 아래로 바꾸고, 원문 끝에 계보 절을 더한다.

```yaml
regions:
  - key: domestic
    name: "국내"
    description: "대한민국(북한 제외)"
  - key: korean-peninsula
    name: "북한·한반도"
    description: "북한과 남북 관계 · 한반도 정세"
  - key: us
    name: "미국"
    description: "미국"
  - key: china
    name: "중국"
    description: "중국 · 홍콩 · 대만"
  - key: japan
    name: "일본"
    description: "일본"
  - key: europe
    name: "유럽"
    description: "유럽 나라들과 유럽연합 · 러시아"
  - key: middle-east
    name: "중동"
    description: "중동 · 북아프리카(이스라엘 · 팔레스타인 · 이란 · 걸프 국가 등)"
  - key: other-foreign
    name: "기타 해외"
    description: "위 지역 밖의 해외(동남아시아 · 중남미 · 사하라 이남 아프리카 · 오세아니아 등)"
```

```yaml
lineage:
  - kind: region
    change: split
    from: [other-foreign]
    to: [other-foreign, middle-east]
```

확인하면 `READY` 이고 `changes` 에 고친 키 `other-foreign`(설명)과 계보 하나가 있다 — `middle-east` 는 계보의 새 키라 더한 키(`added`)에 나오지 않는다. `other-foreign` 을 선호하던 사용자는 두 키를 모두 선호하는 것으로 이어진다.

## 재평가 기간

- 활성화의 `recentDays` 가 1 이상이면, 활성화 시각에서 그 일수 × 24시간 전부터 처음 본 기사를 새 버전으로 다시 평가한다. 요약문이 없는 기사도 제목으로 평가한다
- 그 기간의 기사 가운데 평가가 실패로 남은 기사도 다시 평가한다
- 재평가하는 기사는 그 뒤에 들어온 새 기사보다 먼저 평가한다. 하루 4,000건 · 1분에 50건이면 기간 하루마다 새 기사가 약 80분 늦어진다(측정 전 추정). 확인의 `recentArticles` 로 건수를 먼저 본다
- 다시 평가하는 기사마다 평가 비용이 든다 — [공유 평가](configuration.md#공유-평가)

## 저장 기준을 낮춘 뒤 빠진 태그 채우기

저장 기준을 낮추면, 낮추기 전에 평가된 기사에는 낮춘 구간의 태그가 저장돼 있지 않다 — 태그 기준을 그 구간으로 내려도 그 기사에는 붙지 않는다. 저장된 평가 원본 응답에는 모든 태그의 확률이 있어, 평가 모델을 다시 부르지 않고(비용 없음) 빠진 태그를 채울 수 있다. 규칙은 [빠진 태그 채움 · 저장 바닥](../specs/evaluation.md#빠진-태그-채움--저장-바닥)에 있다.

1. **저장 기준을 낮추고 30분 지난 뒤** 채운다. 낮춘 직후 30분 안의 평가는 옛 기준으로 저장됐을 수 있어, 그 전에 채우면 그 구간이 덮이지 않고 경고가 남는다
2. **확인한다** — 아무것도 쓰지 않고 지금부터 `days` 일(1 ~ 180) 안에 평가된 평가 수를 버전별로 본다

   ```sh
   curl -s -H "Authorization: Bearer $YOZMNEWS_ADMIN_TOKEN" -H 'Content-Type: application/json' \
     -d '{"days":30}' http://127.0.0.1:8000/api/admin/tag-backfill-reviews | jq
   ```

3. **요청한다** — 같은 본문을 `/api/admin/tag-backfills` 로 보낸다. 그 순간 버전마다의 지금 저장 기준이 채울 기준으로 기록되고(`REQUESTED`), 작업 역할이 1분쯤 뒤에 시작한다. 끝나지 않은 채움이 있으면 새로 기록하지 않고 그 채움이 `ALREADY_OPEN` 으로 온다
4. **진행 · 결과를 본다** — `GET /api/admin/tag-backfills` 의 `state`(`WAITING` · `RUNNING` · `DONE`)와 처리한 평가 · 더한 태그 · 건너뛴 평가 수. 개발 기기에서 30일치(평가 120,000건)는 1분이 안 걸렸다

- 범위 안의 모든 버전의 평가를 채운다 — 은퇴한 버전의 평가도 그 버전의 저장 기준까지 채운다
- **건너뛴 평가가 있는 버전**(다른 평가기 · 읽을 수 없는 원본 응답)은 채움이 끝나도 경고 · 평가 현황 표시가 그대로다 — 그 평가에는 빠진 태그가 남아 있을 수 있다
- 다시 채워도 결과는 같다 — 있는 태그는 그대로 두고 없는 태그만 더한다
- **채움이 끝나지 않고 머물면** 새 요청도 그 채움을 돌려받는다. 앱 로그의 오류 `빠진 태그 채움 {ID} 을 멈췄다` 를 본다 — DB 오류였으면 DB 가 돌아온 뒤 다음 회차가 이어 간다. DB 가 정상인데 같은 오류가 회차마다 되풀이되면 그 채움은 이어 가지 못하는 경우다([evaluation-R31](../specs/evaluation.md#빠진-태그-채움--저장-바닥)). 취소하는 API 는 없다

## 활성화의 결과

- **확인과 활성화 사이에 다른 활성화가 있으면** 활성화는 바뀐 활성 버전과 다시 대조한다. 그래서 확인 때와 다른 결과(`UNCHANGED` · `INVALID_TAG_SET` 이나 다른 변경 목록)가 올 수 있다 — 응답의 결과를 기준으로 판단한다
- 활성화하는 동안 평가 결과 쓰기와 태그 기준 · 저장 기준 변경이 잠시 기다린다. 이미 시작한 평가 회차는 결과를 쓰기 전에 이전 버전으로 읽은 것을 알아차리고 멈춘다 — 그 기사는 다음 회차가 새 버전으로 평가한다
- **평가가 멈추면** — 체계가 커서 평가 모델 Jev 의 한도(요청 전체 64k 토큰 · 질문 하나 32k 토큰, 형식 선택지 255개)를 넘으면 모든 기사의 평가가 멈추고 앱 로그에 경고 `평가기를 쓸 수 없어 회차를 멈췄다` 가 남는다. 기사는 평가 대기에 남는다. 질문 · 태그를 줄인 원문으로 새 버전을 활성화하면 이어서 평가한다. 한도에 가까운 체계는 긴 기사를 실패로 남길 수 있다 — 그 기사는 다음 활성화의 재평가 기간에 들면 다시 평가한다
