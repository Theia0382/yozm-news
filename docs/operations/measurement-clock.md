# 측정용 시계 쓰기

지난 데이터를 복원한 일회용 인스턴스에서 앱의 시계를 지난 시각에서 출발시키고 하루씩 넘겨, 여러 날에 걸친 동작(일정 생성 · 관심도 감쇠 · 기간 계산)을 실제 날짜를 기다리지 않고 확인하는 방법이다. 운영 인스턴스에서는 쓰지 않는다. 규칙은 [platform Spec "앱 시계"](../specs/platform.md#앱-시계) platform-R26 ~ R30, 판단의 이유는 [ADR-0251](../adr/0251-the-measurement-clock-starts-only-with-the-measurement-profile-and-a-clock-row-and-moves-forward-through-the-operator-api.md)에 있다.

## 켜기

측정용 시계는 profile `measurement` 와 DB 의 시계 행이 함께 있을 때만 뜬다. 켜는 설정 키 · 환경 변수는 없다.

1. 측정 인스턴스의 DB 에 덤프를 복원한다. 운영 DB 에는 하지 않는다 — 시계 행이 생긴 DB 는 측정 profile 없이 뜨지 않는다
2. 출발 시각을 시계 행으로 넣는다. 시각은 측정 시각(앱이 지금이라고 볼 시각)이다

   ```sql
   INSERT INTO measurement_clock (started_at) VALUES ('2026-11-10T07:05:00+09:00');
   ```

   표가 없으면 profile 을 `web` 하나로 띄워 마이그레이션만 끝내고 내린 뒤 넣는다 — 작업 역할이 없으면 작업 서버가 뜨지 않아 수집 · 일정 회차가 돌지 않는다. 두 역할로 띄우면 시계 행이 없는 동안 실제 시간으로 수집 · 일정이 돌아 측정 데이터에 오늘의 기사 · 다이제스트가 섞인다
3. 배포 정의의 profile 에 `measurement` 를 더해 띄운다 — 덧씌우기 파일로 `SPRING_PROFILES_ACTIVE: web,worker,measurement`. 한 프로세스가 두 역할을 함께 해야 한다
4. 기동 로그에 warn 한 줄 "측정용 시계로 뜬다 — 지금 …, 출발 …, 넘긴 기록 …건. 수집하지 않는다"가 남는다. 처음 뜰 때 출발에 대응하는 실제 시각(`anchored_at`)이 채워진다

기동하지 않으면 로그의 까닭을 본다 — 측정 profile 인데 시계 행이 없음(2), 두 역할이 아님(3), 시계 행이 있는데 측정 profile 이 없음(측정 DB 를 운영 profile 로 띄웠다)이다.

## 넘기기

운영자 API 로 앞으로만 넘긴다. 운영자 토큰([설정 "운영자"](configuration.md#운영자))이나 운영자 계정 세션으로 부른다.

```bash
curl -s -H "Authorization: Bearer $YOZMNEWS_ADMIN_TOKEN" https://<주소>/api/admin/measurement-clock
curl -s -X POST -H "Authorization: Bearer $YOZMNEWS_ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"by":"PT24H"}' https://<주소>/api/admin/measurement-clock/advance
```

- 본문은 넘길 길이 `by`(ISO-8601 기간 — `PT24H` · `PT2H`)와 도착 시각 `to`(`2026-11-11T07:05:00+09:00`) 가운데 하나다. 응답은 넘긴 뒤의 지금 · 출발 시각 · 넘긴 기록이다
- 둘 다 주거나 둘 다 없거나, 길이가 0 이하이거나 도착 시각이 지금 이하면 400, 측정용 시계가 아닌 인스턴스면 409 다
- 넘기기 사이에는 실제 속도로 흐른다. 앱이 내려 있던 동안의 실제 시간도 흐른 것으로 친다
- 진행 중인 다이제스트 생성 · 대기열 점유는 넘긴 시간 때문에 멈춘 것으로 보이지 않는다 — 임대 · 기한은 넘긴 시간을 뺀 경과로 잰다(platform-R28)

## 일정 생성과 넘기는 폭

일정은 사용자가 정한 생성 시각 뒤 2시간(따라잡기 창) 안에서만 그 날짜의 다이제스트를 만든다([digest Spec](../specs/digest.md#5-규칙과-불변식) digest-R29). 넘기는 폭은 제한하지 않으므로, 넘긴 구간에 창이 든 사용자는 그 날짜를 건너뛴다.

- 하루씩 넘길 때는 시험 사용자의 생성 시각을 같게(2시간 안으로) 맞추고, 넘긴 뒤 시각이 그 창 안에 들게 한다 — 첫날은 `to` 로 생성 시각 바로 뒤에 맞추고 그 뒤로 `PT24H` 씩 넘기면 된다
- 생성 시각이 다른 사용자를 섞으면 2시간 이하로 나눠 넘긴다
- 일정 회차는 실제 1분마다 돈다. 넘긴 뒤 회차가 다이제스트를 만들기까지 실제 1분 남짓을 기다린다
- 덤프에 출발 시각보다 늦은 다이제스트가 있으면 그 사용자의 일정은 시계가 그 날짜를 지날 때까지 다이제스트를 만들지 않는다

## 측정 중에 달라지는 것

- **수집하지 않는다** — 수집 점유 · 점유한 수집 · 피드 상태 확인이 돌지 않는다. 덤프에 남은 점유 · 예약 작업도 실제 피드를 요청하지 않는다. 피드 켜기 · 원문 미리보기처럼 실제 피드를 요청하는 운영자 조작은 409 다. 새 기사는 들어오지 않고 피드 상태는 덤프 시점 그대로 남는다([source Spec](../specs/source.md#측정용-시계) source-R58)
- **지난 상태는 재현되지 않는다** — 사건 · 흐름처럼 현재 상태만 두는 표는 덤프 시점의 모습이다. 사건의 대표 기사, 흐름의 소속 · 관계와 거기서 나오는 흐름의 대표 사건 · 타임라인 화면, 흐름 상태(진행 · 잠잠 · 끝남 — 마지막 기사 시각으로 정한다)에 측정 시각 뒤의 기사가 드러날 수 있다
- **흐름 정리는 측정 시각까지의 사건만 싣는다** — 사용자의 흐름 정리는 첫 기사 시각이 측정 시각 이하인 사건으로 쓰고, 측정 시각이 지나면 그 뒤의 사건을 새 사건으로 더한다([user Spec](../specs/user.md#사용자-스토리라인의-정리) user-R70)
- **미래 시각의 행** — 출발 시각이 덤프의 가장 늦은 행보다 앞서면, 미래 시각의 평가 대기 · 임대 등은 시계가 그 시각을 지날 때까지 멈춘다. 후보 선별은 기간으로 거르므로 미래 기사는 들어오지 않는다
- **하루 간격 작업** — 사건 정리 · 후보 행 정리 · 읽은 알림 정리는 실제 하루에 한 번 돈다. 측정 날짜마다 돌지 않는다
- **앱 밖의 시간은 실제 시간이다** — 로그 시각, 이벤트 발행 기록, 세션 만료, JobRunr 대시보드는 실제 시각이다. 측정 보고는 DB 의 측정 시각과 로그의 실제 시각을 구분해 적는다
- **운영자 화면** — 화면의 기간 기본값은 브라우저 시계라 측정 시각과 다를 수 있다. 기간을 직접 고른다

## 끄고 버리기

측정이 끝난 인스턴스와 DB 는 버린다. 시계 행이 남은 DB 는 측정 profile 없이 뜨지 않으므로 운영에 다시 쓸 수 없다 — 운영에 쓸 데이터는 측정 전의 덤프에서 복원한다.
