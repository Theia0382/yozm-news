# 시스템 개요

요즘뉴스의 1층 문서다. 목적 · 범위 · 품질 목표 · 시스템 구성 · 모듈 지도 · 횡단 규약 · 용어를 담는다. v1 전체의 시스템 지도라 아직 코드가 없는 모듈 · 의존 · 이벤트도 담고, 아직 설계되지 않은 부분은 항목 앞에 **(미설계)** 를 적는다 — 그 부분을 설계하는 이슈가 표시를 지운다. 모듈 하나의 계약 · 내부 구조 · 규칙은 [모듈 Spec](specs/README.md)이, 결정의 이유는 [ADR](adr/README.md)이 소유한다.

## 1. 목적

매일 확인할 만한 관심 뉴스를 짧은 시간 안에 파악하게 해 주고, 그 기록을 오래 쌓아 뉴스의 흐름과 관심의 변화를 보여 주는 **셀프 호스팅 개인화 뉴스 다이제스트 소프트웨어**다. 핵심 가치는 둘이다 ([ADR-0025](adr/0025-long-term-personal-news-history-in-v1.md)).

- **매일 다이제스트** — 단순한 기사 목록이 아니라, 사용자 관심에 맞춰 여러 기사를 종합한 요약과 주요 뉴스 정리. 사용자가 매일 들어오는 기본 기능이다
- **개인 뉴스 히스토리** — 기사 · 사건 · 사용자 반응을 쌓아, 사건들이 이어진 흐름(스토리라인)의 전개와 관심의 변화를 보여 준다. 쌓일수록 가치가 커지는 장기적인 차별점이다

- 어떤 소스를 켜고 누구와 함께 쓸지, 소스의 이용조건을 어떻게 판단할지는 인스턴스를 띄운 운영자가 정한다 ([ADR-0047](adr/0047-self-hosted-software-run-by-instance-operators.md))
- 한 인스턴스를 운영자가 허락한 몇 사람이 함께 쓴다. 운영자가 인스턴스를 인터넷에 열 수 있고 여러 사람의 데이터와 LLM 키가 한곳에 모이므로, 인증 · 데이터 격리 · 키 보관 · 악용 방지는 공개 서비스 수준으로 한다
- 대규모 인프라를 쓰지 않는다. 같은 컨테이너 구성을 운영자의 호스트(집 서버 · VPS · 관리형 클라우드) 어디에든 올린다

```
[운영자 큐레이션 RSS 피드]
        │  주기적 수집 · 정규화 · 중복 제거
        ▼
[기사 저장소] ──► [Jev 공유 평가] 주제·지역 태그 · 형식 · 중요도
        │        └─► [사건 묶기] 한 번 일어난 일의 기사 묶기
        │                 └─► [스토리라인] 사건을 스토리라인으로 잇기 · 큰 판정
        │                       (사용자와 무관, 운영자 비용)
        ▼
[사용자별 후보 선별] 사건 단위 — 구독 주제 · 제외 조건 · 사건 중요도 × 관심도 · 큰 스토리라인 · 기간
        │        └─► [항목 묶기] 고른 사건을 스토리라인 포함 나무로 묶고 주요 뉴스 · 헤드라인으로 가르기
        │
        ▼
[사용자 LLM으로 종합 다이제스트 생성] 항목마다 제목 · 요약 (사용자 BYOK 키, 사용자 비용)
        │        ├─► [사용자 스토리라인의 정리] 관심이 쌓인 사용자 스토리라인의 제목 · 요약 (사용자 BYOK 키, 사용자 비용)
        │        └─► [변화 리포트] 주간 · 월간 (사용자 BYOK 키, 사용자 비용)
        ▼
[웹 UI] 주요 뉴스 · 헤드라인 항목(좋아요/싫어요) + 출처 기사(원문 링크)
        사건 흐름(정리된 내 흐름) · 타임라인 · 관심사 히스토리 · 변화 리포트
```

## 2. 범위

### v1 포함

- 운영자가 켠 소스의 RSS 피드에서 기사 수집, 정규화, 중복 제거, 피드 상태 모니터링(실패 · 방치된 피드 감지). 소스는 수집 프로필로 등록하고, 주요 언론사는 프리셋으로 제공한다([ADR-0015](adr/0015-source-presets-and-collection-profiles.md))
- 운영자가 관리하는 태그 체계(주제 2단계 · 지역 · 형식)와 Jev 공유 평가(주제 · 지역 다중 태그, 기사 형식, 중요도)
- 가입 · 로그인: 운영자의 초대 링크 · 계정 생성으로 가입(공개 가입은 운영자 화면에서 연다, 첫 운영자는 환경 변수), 자체 로그인(이메일 · 비밀번호, 복구 코드 재설정, 첫 로그인의 비밀번호 변경)
- LLM API 키 등록(BYOK — OpenAI · Anthropic · 중계 공급자 OpenRouter). 키가 없는 사용자는 키 등록 · 계정 설정 · 알림 · 관심 설정 화면만 쓴다
- 관심 설정: 구독 주제, 지역 · 형식 제외, 제외할 소스, 다이제스트 생성 시각
- 한 번 일어난 일을 다룬 기사의 공유 묶기(사건) ([ADR-0026](adr/0026-event-clustering-with-local-embeddings-and-jev.md) · [ADR-0102](adr/0102-an-event-is-the-reports-of-one-happening-narrowed-by-the-event-membership-question-wording.md))
- 사용자별 일일 다이제스트 생성(고른 사건을 스토리라인으로 묶은 항목마다 여러 기사를 종합한 주요 뉴스 + 헤드라인)과 열람(오늘 · 지난 날짜), 출처 기사의 원문 링크
- 스토리라인: 사건들을 이은 흐름을 모든 사용자가 공유하도록 잇기(운영자 비용), 큰 판정(구독과 무관하게 알릴 만한 스토리라인), 사용자가 관심 신호를 준 스토리라인을 따라가는 사용자 스토리라인과 흐름 추적(스토리라인 구독) · 해제, 관심이 쌓인 사용자 스토리라인을 사용자 LLM 으로 간추린 정리(사용자 비용 — 그 사용자에게만 보인다), 타임라인 ([ADR-0101](adr/0101-shared-storylines-connect-events-and-the-personal-side-is-storyline-subscriptions-and-interests.md) · [ADR-0103](adr/0103-big-judgement-on-storylines-and-the-storyline-milestone-right-after-event-clustering-takes-over-big-events.md))
- 관심도를 반영한 사건 단위 후보 선별, 구독과 무관하게 넣는 큰 스토리라인, 항목별 선정 이유 표시, 구독 제안 ([ADR-0028](adr/0028-explicit-signals-and-interest-weighted-candidates.md) · [ADR-0103](adr/0103-big-judgement-on-storylines-and-the-storyline-milestone-right-after-event-clustering-takes-over-big-events.md) · [ADR-0260](adr/0260-digest-candidates-are-events-and-only-assigned-events-with-an-article-first-evaluated-in-the-period-enter.md) · [ADR-0262](adr/0262-chosen-events-are-grouped-into-items-by-containment-tree-top-code-splits-top-stories-and-headlines-the-llm-writes-per-item-and-an-item-has-one-badge.md))
- 관심 신호(다이제스트 항목에 누르는 좋아요 / 싫어요 — 그 항목의 사건마다 기록 · 주제와 스토리라인의 구독 변경)의 이력과 관심사 히스토리
- 변화 리포트: 주간 · 월간
- 운영자 화면: 피드 · 태그 체계 · 평가 결과 · 사건 · 스토리라인
- 운영자가 설정하면 보이는 개인정보처리방침 · 이용약관 링크

### v1 제외

- 외부 API(제3자 조회용)와 MCP 어댑터 — [로드맵](roadmap.md)
- 외부 로그인(OIDC 공급자 로그인 · 외부 계정 연결) — [로드맵](roadmap.md)
- 사용자 피드 추가, 기사 본문 추출(파이프라인 자리만 둔다)
- 분기 · 연간 변화 리포트, 키워드 구독
- 메일 발송(이메일 인증 · 메일 기반 비밀번호 재설정 · 알림 — [ADR-0011](adr/0011-no-email-in-v1.md)), 메신저 알림, 모바일 앱

## 3. 품질 목표와 제약

1. **교체 가능한 경계** — 뉴스 공급원(`ArticleSource`), 본문 추출(`ContentExtractor`), 모델 평가(`ArticleEvaluator` — 태그 판정 · 사건 소속 판정), 기사 임베딩(`ArticleEmbedder` — `evaluation` 의 임베딩 공개 API 뒤), 다이제스트 생성(`DigestGenerator`), 변화 리포트 생성(`ReportGenerator`)은 인터페이스 뒤에 둔다. 특정 공급자의 API 형태가 도메인 모델로 새어 들어오지 않는다
2. **셀프 호스팅 가능** — 외부 서비스(로그인 · 메일 · 봇 차단 · Cloudflare 등)는 표준 프로토콜(OIDC · SMTP · S3)이나 자체 인터페이스로 연결하고, 설정으로 교체하거나 끌 수 있다. 개발과 테스트는 외부 계정 없이 로컬 대체물로 돈다 ([ADR-0012](adr/0012-swappable-external-dependencies.md))
3. **도메인은 관심 분야를 모른다** — 다루는 주제는 코드가 아니라 태그 체계와 사용자 설정으로 정해진다
4. **비용 주체에 따라 단계를 나눈다** — 사용자 수와 무관한 일(수집 · 공유 평가 · 사건 묶기 · 스토리라인 잇기)은 운영자 비용, 사용자 수에 비례하는 일(다이제스트 · 사용자 스토리라인의 정리 · 변화 리포트 생성)은 사용자 비용이다. 운영자는 생성형 LLM 을 쓰지 않는다. 운영자 비용은 사용자 수가 늘어도 일정하다 ([ADR-0002](adr/0002-shared-evaluation-with-jev.md) · [ADR-0003](adr/0003-byok-personalized-digest.md) · [ADR-0025](adr/0025-long-term-personal-news-history-in-v1.md) · [ADR-0101](adr/0101-shared-storylines-connect-events-and-the-personal-side-is-storyline-subscriptions-and-interests.md))
5. **판단 근거를 남긴다** — Jev 의 태그별 확률, 모델 버전, 태그 체계 버전, 사건 소속 판정 원본, 임베딩 모델 버전, LLM 토큰 사용량을 저장해 임계값 조정과 품질 분석에 쓴다
6. **원문은 원문 사이트에서** — 기사 본문을 재게시하지 않는다. 사용자에게는 종합 요약 · 원문 링크 · 출처 표기만 제공하고, RSS 요약문 원문은 운영자 화면에서만 보인다 ([ADR-0068](adr/0068-rss-summaries-shown-only-on-operator-screens-and-users-get-processed-information.md))
7. **LLM 출력은 데이터로 다룬다** — 링크와 기사 정보는 LLM 이 아니라 DB 에서 가져와 렌더링한다. LLM 은 이번 요청의 항목 별칭으로만 항목을 가리키고, 인용은 코드가 정한 그 항목의 표본 기사다([ADR-0262](adr/0262-chosen-events-are-grouped-into-items-by-containment-tree-top-code-splits-top-stories-and-headlines-the-llm-writes-per-item-and-an-item-has-one-badge.md))
8. **작게 운영 가능하게** — v1 은 PostgreSQL 하나 외에 별도 상태 저장소(Redis · 메시지 브로커 · 벡터 DB)를 두지 않는다. 벡터는 pgvector 확장에 둔다 ([ADR-0027](adr/0027-pgvector-for-vector-storage.md))
9. **관심 신호는 명시적 행동만** — 좋아요 / 싫어요 · 구독 변경(주제 · 스토리라인)만 관심 신호로 쓰고, 클릭 · 열람은 추적하지 않는다 ([ADR-0028](adr/0028-explicit-signals-and-interest-weighted-candidates.md))
10. **장기 기능은 RSS 요약문에 기대지 않는다** — 요약문은 기본으로 무기한 보존하지만 운영 설정으로 지울 수 있다. 스토리라인 · 관심사 히스토리 · 변화 리포트 · 검색은 요약문이 없는 기사에서도 동작한다 ([ADR-0029](adr/0029-indefinite-summary-retention-with-optional-deletion.md))

## 4. 시스템 구성

```mermaid
flowchart LR
    user([사용자 브라우저])
    admin([운영자])
    subgraph CF[Cloudflare]
        edge[DNS · CDN · WAF]
    end
    subgraph Host[운영자의 호스트: 집 서버 / VPS / 관리형 클라우드]
        tunnel[cloudflared]
        proxy[proxy<br/>SPA 정적 파일 + 리버스 프록시]
        web[app: web 역할<br/>REST API · 인증]
        worker[app: worker 역할<br/>수집 · 평가 · 사건 묶기 · 스토리라인 · 다이제스트 · 리포트]
        db[(PostgreSQL)]
    end
    feeds[[언론사 RSS 피드]]
    jev[[Jev<br/>TypeSafe System One API]]
    llm[[LLM 공급자<br/>OpenAI · Anthropic · OpenRouter]]

    user --> edge --> tunnel --> proxy
    admin --> edge
    proxy -->|/api| web
    web --> db
    worker --> db
    worker --> feeds
    web -->|피드 켜기 미리보기| feeds
    worker --> jev
    worker -->|사용자 키| llm
    web -->|키 검증| llm
```

- 브라우저에는 **단일 오리진**으로 서비스한다. `proxy` 가 React SPA 정적 파일을 내려주고 `/api/**` 를 `web` 으로 넘긴다
- `web` 과 `worker` 는 **같은 컨테이너 이미지**를 Spring profile 로 역할만 나눠 실행한다. 기본 배포 구성은 두 profile 을 함께 켠 프로세스 하나(서비스 `app`)이고, 나눠 띄울 때는 `web` · `worker` 두 서비스로 둔다 ([operations/deployment.md](operations/deployment.md#서비스))
- 역할 profile 을 하나도 켜지 않으면 두 역할을 함께 하고, 다른 profile 만 켜 역할이 하나도 없으면 기동하지 않는다. 어느 구성요소가 어느 역할에 속하는지는 [platform Spec](specs/platform.md#역할)(platform-R8 · R9, [ADR-0042](adr/0042-app-roles-as-web-worker-profiles-marked-by-platform-annotations.md))에 있다. `web` 도 피드 켜기의 미리보기로 피드에 요청한다([ADR-0041](adr/0041-activation-gate-previews-a-feed-on-enable-and-judges-by-code-constants.md))
- Cloudflare 는 권장 구성이며 필수가 아니다 — 일반 리버스 프록시나 다른 터널로 대체할 수 있다 ([operations/deployment.md](operations/deployment.md#공개-경로와-외부-서비스))

| 역할 | 하는 일 | 확장 |
|---|---|---|
| `web` | 화면용 REST API, 로그인(자체), 세션, 키 등록 · 검증, 운영자 API | 무상태(세션은 DB). 여러 개로 늘릴 수 있다 |
| `worker` | 백그라운드 작업: 피드 수집, Jev 평가, 사건 묶기, 스토리라인 잇기, 다이제스트 · 변화 리포트 생성, 정리 작업 | 작업 큐가 DB 로 작업을 분배하므로 여러 개로 늘릴 수 있다 |

## 5. 모듈 지도

- `event` → `article` 의 공개 API 의존은 기사 표현 · 배정 · 기간 집계의 입력이다 — 기사의 제목 · 요약문 · 발행 시각, 채우기 대상(처음 본 시각이 기간 안인 기사), 기간 집계의 소스 수를 셀 기사의 엔트리 소스(`sources`)는 `article` 의 `ArticleDirectory` 가 낸다. 그 소스의 값 타입(`SourceId`)이 `event` → `source` 의존이다
- `event` → `evaluation` 의 공개 API 의존은 기사 임베딩(`TextEmbedding`)과 사건 소속 판정(`EventMembership`), 평가기 시간(`EvaluatorTiming`)이고, `event` → `tag` 의 공개 API 의존은 기간 집계의 중요도다 — 사건 배정이 애매한 구간의 기사를, 사건 병합이 애매한 구간의 사건 쌍을(바뀐 사건의 서술 기사 하나를 판정할 기사로) 작업 역할에서 트랜잭션 밖으로 묻고, 기간 집계의 중요도 평균 · 합을 셀 기사의 중요도는 `tag` 의 `ArticleEvaluations.importances` 가 낸다. 표현 회차가 표현 텍스트 묶음을, 배정 회차가 지금 모델 버전을 작업 역할에서 트랜잭션 밖으로 임베딩에 묻는다 — 임베딩 결과는 `evaluation` 이 기록하지 않고 `event` 가 저장한다([ADR-0114](adr/0114-article-embedding-is-a-gateway-operation-of-evaluation-taking-callers-texts-checking-results-and-recording-nothing.md)). 요청 · 결과 타입(벡터 값 타입 `Embedding` 포함)은 `evaluation` 이 소유한다
- `admin` 은 운영자 기능을 가진 모듈의 공개 운영 API 를 부른다 — 지금은 `source` 의 `SourceAdministration`(소스 · 피드 관리 · 숨김 · 삭제 · 수집 상태), `article` 의 `ArticleAdministration`(엔트리 집계 · 삭제하면 함께 지워질 기사 수), `tag` 의 `TagSetAdministration`(태그 체계 버전 목록 · 원문 · 확인 · 활성화, 태그 기준 · 저장 기준의 상태 · 미리보기 · 변경) · `EvaluationAdministration`(평가 대기 · 평가 현황) · `TagBackfillAdministration`(빠진 태그 채움의 확인 · 요청 · 목록) · `EvaluationReview`(평가 결과 목록 · 표본 · 상세), `event` 의 `EventIntakeAdministration`(사건 묶기 채우기), `storyline` 의 `StorylineLinkingAdministration`(스토리라인 잇기 채우기) · `BigStorylineAdministration`(큰 판정 기준의 지금 값 · 변경 · 이력 · 미리보기), `platform` 의 `EventPublicationAdministration`(남겨진 이벤트 발행의 다시 처리 · 폐기). 운영자 화면에 기사 정보를 맞붙이려고 공개 조회도 부른다 — `tag` 의 `TopicCoverage`(주제별 보도량), `evaluation` 의 `EventJudgementLog`(사건 소속 판정 원본) · `RelationJudgementLog`(관계 판정 원본과 다시 읽은 확률), `event` 의 `EventDirectory`(사건 목록 · 사건 · 대표 기사) · `EventReview`(사건 배정 기준 · 합쳐진 사건 · 판정 원본의 쓰임), `storyline` 의 `StorylineDirectory`(스토리라인 목록 · 스토리라인 · 타임라인 · 사건의 스토리라인 · 큰 스토리라인 · 소속 없는 사건) · `StorylineReview`(소속 근거 · 관계의 확률 · 물은 기록 · 지금 기준), `article` 의 `ArticleDirectory`(제목 · 요약문 · 정규 URL · 발행 시각 · 엔트리 · 헤드라인), `source` 의 `FeedLabels`(출처 이름 · 섹션). `account` 의 `AccountAdministration`(운영자 계정 생성 · 초기 비밀번호 다시 정하기) · `InvitationAdministration`(초대 발급 · 목록 · 취소) · `SignUpPolicyAdministration`(가입 정책 · 이력 · 변경)도 부른다. 운영 결과의 타입은 그 모듈이 공개하고 HTTP 응답 모양은 `admin` 이 정한다. 오류 응답은 `platform` 의 `ProblemResponses` · `ApiProblem` 으로 쓴다([ADR-0045](adr/0045-admin-module-serves-operator-api-over-module-public-operation-apis.md))
- `reader` 는 독자 화면의 응답을 공개 조회로 엮는다 — 지금은 `storyline` 의 `StorylineDirectory`(스토리라인 · 여럿 찾기 · 타임라인 · 관계 · 포함 나무의 꼭대기), `event` 의 `EventDirectory`(대표 기사 `representativesOfAll` · 사건 여럿의 기사 ID `articleIdsOf`), `article` 의 `ArticleDirectory.headlines`(제목 · 출처 이름 · 발행 시각 · 원문 링크), `digest` 의 `ReceivedArticles`(받은 소식 — 세션 사용자의 것) · `DigestDirectory`(다이제스트 조회 · 스토리라인에 묶인 지난 항목 — 세션 사용자의 것) · `DigestRequests`(수동 생성 요청) · `InterestHistory`(관심사 히스토리 — 세션 사용자의 것) · `TopicSuggestions`(구독 제안 — 세션 사용자의 것), `tag` 의 `TagSetDirectory.names`(주제 이름 · 대분류 · 체계 순서), `user` 의 `UserStorylineSummaries`(정리된 사용자 스토리라인 — 세션 사용자의 것), `report` 의 `ReportDirectory`(변화 리포트 목록 · 한 편 — 세션 사용자의 것) · `ReportRequests`(실패한 리포트 다시 만들기 — 세션 사용자의 것) · `ReportConditions`(생성 조건의 값)를 부르고, `user` 의 그 밖의 것은 값 타입(`TopicSubscriptionAction` · `GenerationFailureCause`)만 쓴다. 응답 모양은 `reader` 가 정하고, 판단(상태 · 대표 · 받은 소식의 뜻 · 무엇이 정리된 사용자 스토리라인인지 · 리포트의 비교와 숨기기)은 그 모듈이 갖는다. 어느 모듈도 `reader` 를 모른다([ADR-0192](adr/0192-reader-screens-are-composed-by-the-reader-module-over-module-public-queries.md))
- **(미설계)** 여러 모듈의 데이터에 걸친 작업(보존 정리)의 소속은 아직 설계되지 않았다
- `event` 는 사건을 열고 · 고치고 · 지우고 · 합치고 · 닫을 때마다 바뀐 사건 ID 를 `EventsChanged` 로 알린다. `storyline` 은 그 알림을 받아 사건을 잇기 대기에 넣고, `storyline` → `event` 의 공개 API 의존은 잇기와 조회의 재료다 — 잇기는 사건의 지금 상태(`find`), 사건 표현 · 이웃 사건 · 말 수 · 채우기 대상(`EventDirectory` 의 `profiles` · `neighbors` · `termCounts` · `lastArticleSince`), 조회는 기간 안 사건 · 사건 묶음의 기간 집계 · 기간 전체 집계 · 사건들(`articleCountsIn` · `tallies` · `total` · `views`)이다. 큰 판정의 재료인 기간 집계는 `event` 가 세고 `storyline` 은 구성 사건 ID 만 넘긴다([ADR-0117](adr/0117-big-judgement-materials-are-tallied-by-event-per-group-of-events-and-storyline-passes-only-event-ids.md)). `storyline` → `evaluation` 의 공개 API 의존은 스토리라인 소속 판정(`StorylineMembership`)과 관계 판정(`StorylineRelation`), 평가기 시간(`EvaluatorTiming`)이다 — 잇기 회차가 띠 안 후보를(판정할 사건의 대표 기사 ID 와 후보마다 서술 기사 ID) 작업 역할에서 트랜잭션 밖으로 묻고 소속 · 잇기 물은 기록이 판정 원본 ID 를 가리킨다([ADR-0194](adr/0194-storyline-linking-asks-jev-only-for-band-candidates-and-reuses-recorded-probabilities-until-either-side-doubles.md)). 관계 판정은 관계 회차가 후보 쌍의 두 스토리라인(스토리라인 ID 와 서술 사건의 대표 기사 ID · 시각)을 작업 역할에서 트랜잭션 밖으로 묻고, 관계와 물은 기록이 판정 원본 ID 를 가리킨다([ADR-0132](adr/0132-storyline-relations-are-judged-by-jev-on-candidate-pairs-and-linked-only-above-a-probability-threshold.md)). `storyline` → `article` 의 의존은 기사 ID 타입(`ArticleId`) 하나다 — `event` 의 대표 기사 ID 를 받아 스토리라인 소속 판정 · 관계 판정에 넘기기만 하고 저장하지 않는다. 스토리라인은 사건 ID 만 가리키고 기사를 읽지 않는다 — 기사 삭제는 `event` 가 사건을 줄이거나 지워 알리는 것으로 따른다([ADR-0105](adr/0105-storylines-link-incrementally-from-event-change-notifications-and-events-publish-changed-event-ids.md)). `storyline` → `platform` 의 공개 API 의존은 벡터의 pgvector 텍스트 표현(`VectorText`)이고, `event` 도 같은 타입을 쓴다
- 모듈 사이 순환 의존은 Modulith 검증 테스트가 실패로 판정하고, 다른 모듈의 이벤트 타입을 받는 것도 의존으로 센다. 그래서 관심도는 노출 기록을 가진 `digest` 가 내주고, `storyline` 은 `digest` · `user` 를 모르며(구독은 `user` 가 스토리라인 ID 로 갖는다), `report` 는 다른 모듈을 읽고 실패만 `user` 가 선언한 이벤트로 알린다. 사건 소속 판정 · 스토리라인 소속 판정 · 태그 판정 · 관계 판정 · 임베딩의 인자 · 반환 타입은 `evaluation` 이 소유한다 ([ADR-0025](adr/0025-long-term-personal-news-history-in-v1.md) · [ADR-0026](adr/0026-event-clustering-with-local-embeddings-and-jev.md) · [ADR-0101](adr/0101-shared-storylines-connect-events-and-the-personal-side-is-storyline-subscriptions-and-interests.md))

코드가 있는 모듈의 공개 인터페이스 · 작업은 그 모듈 Spec 에, 아직 모듈이 없는 포트 · 백그라운드 작업의 초안은 [architecture.md](architecture.md)에 있다.

|---|---|
| 인스턴스 | 운영자가 자기 서버에 띄운 요즘뉴스 한 벌 |

| 수집 프로필 | 소스의 피드 목록과, 그 피드를 읽고 형식을 보정하는 방법을 선언형으로 적은 것 |
| 프리셋 | 개발팀이 저장소에서 관리하고 테스트로 검증한 주요 언론사의 수집 프로필. 운영자는 참조해서 켜고 끈다 |
| 운영자 프로필 | 운영자가 쓴 완결된 수집 프로필. 프리셋 원문을 복사해 고친 것일 수 있지만, 프리셋 수정을 따라가지 않는다 |
| 기사(Article) | 중복 제거된 기사 1건. 여러 피드에서 같은 기사가 들어와도 1건으로 저장한다 |
| 공유 평가 | 사용자와 무관하게 기사마다 한 번만 수행하는 Jev 평가(태그 · 형식 · 중요도). 비용은 운영자가 부담 |

| 태그 기준 | 주제 · 지역 태그가 기사에 붙었는지 가르는 확률 값. 조회할 때 적용하므로 바꿔도 다시 평가하지 않는다 — 규칙은 [tag Spec](specs/tag.md) |

| 주요 뉴스(`top_stories`) | 다이제스트에서 항목 하나의 여러 기사를 종합한 섹션 — 큰 화제 항목과 순위가 높은 항목이다. 그 밖의 항목은 헤드라인(제목 · 짧은 코멘트)이다 |
| 주제 | 태그 체계의 주제 태그(대분류 · 중분류). 보도량과 관심도를 세는 단위이고, Topic 이라는 별도 용어를 두지 않는다 |
| 관심도 | 명시적 신호로 계산한, 기간 × 주제별 · 스토리라인(사용자 스토리라인 — 그 꼭대기에 펼치고, 묶음 여럿에 든 꼭대기는 평균)별 관심의 크기. 후보 순위 · 거름과 관심사 히스토리에 쓰인다. 계산 방법은 [pipeline.md](pipeline.md) |
| 관심사 | 한 사용자의 관심과 그 변화 — 관심도 · 관심사 히스토리로 나타낸다. 스토리라인 구독과 다른 개념이다 |
| 관심사 히스토리 | 쌓인 명시적 신호로 계산한 관심도의 기간별 변화 — 주제 중분류의 관심 · 새로 생긴 관심 · 사라진 관심과 사용자가 바꾼 주제 구독을 보인다 |
| 선정 이유 | 후보 사건이 들어간 이유(`SUBSCRIBED` · `INTEREST` · `MAJOR_STORYLINE` — 화면 이름은 구독 주제 · 관심 반영 · 큰 화제). 사건마다 기록하고, 화면은 항목마다 하나 — 구독 주제가 아닌 것만 보인다([ADR-0241](adr/0241-selection-reasons-mark-only-citations-outside-subscribed-topics-named-interest-and-big-topic.md) · [ADR-0262](adr/0262-chosen-events-are-grouped-into-items-by-containment-tree-top-code-splits-top-stories-and-headlines-the-llm-writes-per-item-and-an-item-has-one-badge.md)) |
| 구독 제안 | 구독하지 않은 주제 중분류의 지금 관심이 제안 기준 이상일 때 다이제스트 홈에서 그 주제의 구독을 권하는 것. 구독 여부는 사용자가 정하고, 거절한 제안은 기간이 지나고 관심이 더 커져야 다시 권한다([digest Spec](specs/digest.md#구독-제안) · [ADR-0245](adr/0245-a-topic-suggestion-is-made-when-the-current-interest-of-an-unsubscribed-subtopic-reaches-its-own-threshold.md)) |
| 변화 리포트 | 한 사용자의 한 기간(주간 · 월간)에 무엇이 달라졌는지 LLM 이 정리한 결과물 |
